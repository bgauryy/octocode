# Feature reference

Detailed behavior of every Octocode for Pi feature. Start with the [README](../README.md) for an overview; configuration lives in [CONFIGURATION.md](CONFIGURATION.md) and the external API in [API.md](API.md).

## File tool

One `file` tool replaces Pi's `edit` / `write`: batched edit / write / delete queries, each with a reasoning line, running on Pi's own engines (exact-match edits, diffs). At session start `file` replaces `edit` / `write` once, unless `--tools` or the `defaultTools` setting names them. A change to a file that moved on disk since the agent read it with `read` (or last changed it with `file`) is refused until it is read again, and so is a change to a file whose read left the context (a rewind, compaction or `/tree` move): size, mtime, ctime and inode are compared, and when the content the agent saw is known (a whole-file `read`, or the tool's own last write) its SHA-256 too. Reads through MCP tools are not tracked: the extension does not depend on any server's tool shapes. Writes are atomic (sibling temp file, fsync, rename, directory fsync), keep the file's mode, write through symlinks, and fail if the file no longer holds the bytes that were checked.

## Bash

Replaces Pi's `bash` (honoring Pi's `shellPath` and `shellCommandPrefix` settings, foreground and background) with the same streaming output and live `Elapsed` timer, plus a deadline: a waited-for command is stopped after 15 minutes (`OCTOCODE_BASH_TIMEOUT` seconds; the call line shows it, and a `timeout` argument can only shorten it), so a server, watcher or prompt never hangs the turn. `background: true` starts the command as a job in its own process group and returns at once with its id, pid and log file (`<Octocode home>/agent/pi/sessions/<session>/bash/`); the exit status, run time and the last 40 lines arrive later as a message that wakes an idle session. Background jobs have no deadline unless the call gives a `timeout`; at most 8 run at once; a job's log is capped at 16 MB (past that it restarts with its tail); the status bar counts them; `/octocode jobs` lists them with their elapsed time, `/octocode jobs kill <id>` stops one, and all are stopped when the session ends, each reported first without waking the session (a resumed session's brief names any job that never reported, e.g. after a crash). In print, JSON and subagent runs, which end with the agent's run, jobs with a timeout are waited for and jobs without one are stopped at the end of the run; either way their report arrives as one more turn instead of being lost. When output is truncated, Pi's full-output file is moved from the temp dir into the same folder; logs older than 30 days are swept (see [Retention](CONFIGURATION.md#retention)).

## Bash safety

Always on: bash calls that would wipe `/` or the home directory (`rm -r` on `/`, `/*`, `~`, `$HOME`, or `--no-preserve-root`), format a disk (`mkfs`), power off (`shutdown`, `reboot`, `halt`, `poweroff`), write to a device with `dd of=/dev/…` or fork-bomb are refused with a reason, even inside `&&`, `;`, pipes and `$(…)`. A last-resort guard against accidents, not a sandbox; the environment is passed through unchanged.

## Checkpoints

A turn is one user prompt (typed or sent over RPC); runs woken by team messages or job reports are not turns of their own. Before `file` first changes a path in a turn, its bytes are saved under `<Octocode home>/agent/pi/sessions/<session>/checkpoints/` (content-addressed; files over 8 MiB are skipped with a note; at most 256 entries / 128 MiB per session, oldest turns dropped first; removed with the session's folder, see [Retention](CONFIGURATION.md#retention)). `/octocode rewind [turns]` (default 1) restores the last turns newest first, but only files still exactly as the agent left them; files changed since (by you, bash or a peer) are listed and left alone. `/fork` offers the same restore for the turns after the fork point, and so does `/tree` when navigating away from turns that changed files. Shell writes are not checkpointed.

## File review

`/octocode review on` (or `OCTOCODE_REVIEW=1`) asks before every `file` batch is applied: it lists each change with the model's reasoning, then Apply all, Review one by one (a preview of the text per change) or Reject all. Rejected changes fail with "do not retry" and are never written; the status bar shows `review on`. Off by default; subagents never prompt.

## MCP

Registers the built-in [Octocode MCP](https://github.com/bgauryy/octocode) server (local code search, reading, structure and AST search, LSP, GitHub code/PR search and repositories, packages) with Pi's built-in MCP; see [MCP](CONFIGURATION.md#mcp). Its tools are named `mcp__octocode__<tool>`, and the prompt tells the model to prefer them for searching and researching code, ahead of Pi's generic "use bash for ls, rg, find" rule. Pi's `read` stays available, and bash stays for builds, tests, git and commands. Local and LSP tools are declared directly; GitHub tools and `artifactSearch` load through `tool_search` unless `OCTOCODE_MCP_DIRECT=1`. Their results are sanitized (terminal controls, bidi overrides, invisible characters) before the model or the terminal sees them.

## Prompt

A short Octocode section in Pi's structured system prompt covers research routing, verification and delegation. Active tool descriptions own their usage instructions. Delegation mechanics (the subagent limit, report delivery, report files) stay in the `agent` tool description; the section keeps only when to delegate. An agent without `file`, `write` or `edit` gets one "investigate and report; do not modify files" rule instead of the rules about changing files. Subagents get guidance for parent steering, peer information and automatic reports. The section is rebuilt when active tools, profiles or agent identity change; identical inputs reuse the cached section.

## Skills

Pi loads skills from `~/.agents/skills`, `~/.pi/agent/skills` and the project's `.agents/skills` / `.pi/skills`; Octocode also picks up `~/.claude/skills` (except claude.ai's synced skills in its `synced/` folder, which need connectors Pi does not have), `~/.codex/skills`, `~/.octocode/skills` (Octocode home) and, in trusted projects (see [Trust](CONFIGURATION.md#trust)), `.claude/skills` (from the working directory up to the repository root) and `<repo root>/.octocode/skills`, in the main session only: subagents skip these extra directories, and `OCTOCODE_EXTRA_SKILLS=0` turns them off everywhere. Pi loads these skills and reports any name conflict. Install Octocode skills with `npx octocode skill install <name>`.

## Subagents

`agent` runs a task in a fresh Pi process and returns its answer; several calls in one turn run in parallel, at most 3 at once (`OCTOCODE_MAX_SUBAGENTS`); calls over the limit are refused with the running ids. `collaborate: true` (or `OCTOCODE_SUBAGENT_COLLABORATE=1` as the default) starts a subagent in team mode: its task lists the collaborating siblings already running (later ones find it with `coordinate list`), and its prompt tells it to message teammates directly when its work affects theirs and to ask them instead of redoing their work. Its final report still goes to the parent. `isolate: true` runs the subagent in a private git worktree under `~/.octocode/pi-worktrees/`: when it finishes, its changes are committed to `refs/octocode/pi/<id>` (or `<id>-2`… when that ref is taken; the report names the actual ref, with a `diff --stat`) and the worktree is removed — if saving fails the worktree is kept and the report names its path; `/agents merge <id>` merges that ref with repository hooks disabled, aborting and listing the files on a conflict. It is refused outside a git repository and warns when the main tree has uncommitted changes (the worktree starts from `HEAD`); worktrees left by a crashed Pi process are committed to their ref and removed at the next start (one that cannot be saved is kept, with a warning naming its path). `/agents kill <id>` (a shortcut for `/octocode agents kill <id>`) stops a background or foreground subagent. A watchdog stops a hung child: no output for 10 minutes while its model generates (`OCTOCODE_SUBAGENT_IDLE_MINUTES`; a running tool or the settle after its answer gets 15 more minutes) kills its process tree and fails the run with `no output for …; last activity: …`; `OCTOCODE_SUBAGENT_MAX_MINUTES` adds an optional wall-clock limit. A child that dies on a signal is reported as `killed by SIGTERM` (not `code null`). Results come back without polling: a background subagent's report arrives as a message when it finishes, and the prompts tell the parent not to poll and the subagent not to announce it is done. Each subagent gets a handoff folder, `<workspace>/.octocode/tmp/agents/<id>/` (the `tmp` folder carries its own `.gitignore` of `*`; the path is passed as `OCTOCODE_AGENT_SCRATCH`; a folder the subagent left empty is removed when it ends, and folders untouched for 7 days are swept at session start). Subagents pick the channel: the report for a short result, `sendMessage` for a blocker or urgent finding, and a Markdown doc in that folder for long or reusable material, reported by path. The parent keeps at most 8 KB / 200 lines of a report in context; a longer one is saved whole as `report.md` there and the kept part ends with its path, so read-only profiles lose nothing. Long reports spill incrementally during execution, so follow-up answers do not accumulate in parent-process memory; retries replace the current report section. A child JSON event over 16 MiB stops the run with an explicit error. Tasks are capped at 16,384 characters. Subagent output is stripped of terminal escape sequences, control characters and bidi overrides before it is drawn. Profiles: `researcher` and `reviewer` (no `file`, `browser` or `askUser`), `implementer` (no `browser`), `webHeadless` and `webLive` (no `file`, no MCP: `mcp: false`). Subagents start with `--no-extensions`, this extension, Pi's built-in MCP and tool search (`-e builtin:mcp -e builtin:tool-search`, both left out for `mcp: false`).

Bundled profiles describe their purpose and evidence requirements in the `agent` tool's profile list. Choose from the profiles actually available in the session:

| Profile | Use for | Capability boundaries |
| --- | --- | --- |
| `researcher` | Uncertain facts, root causes and source evidence | Read-only work, including shell and MCP calls; no file or browser tool |
| `reviewer` | Actionable defects and verification gaps in a specified change | Read-only work, including shell and MCP calls; no file or browser tool |
| `implementer` | A scoped code change with checks and an integration handoff | Guarded file changes, shell and configured MCP; no browser tool |
| `webHeadless` | Rendered public pages and authorized browser interactions | Headless browser and static web; no file tool or MCP |
| `webLive` | Visible browser flows and user-assisted authentication | Visible Octocode browser profile and static web; no file tool or MCP |

Every child starts without the parent's conversation. Its task must carry the goal, scope, relevant paths, evidence, accepted decisions and expected result. Children cannot ask the user directly or delegate again. Their memory schema exposes only reads; their backlog schema allows proposals and permitted updates. Profile instructions make researcher and reviewer shell/MCP work read-only; those instructions are not an operating-system sandbox. The parent owns user communication, missing approvals, review and integration. Questions and replies through `sendMessage` wake idle agents; FYIs wait for their next turn. Completed handoffs arrive automatically, with a saved path for full reports that exceed the context preview.

## Background subagents

`agent` with `background: true` returns at once, so the parent keeps working, talks to the subagent (`sendMessage`, `coordinate list`) and gets its answer later as a message. The parent can end one it started with `coordinate stop <id>` (the user with `/agents kill <id>`): the subagent's process tree is killed and its report says who stopped it, arriving without waking the parent for another turn and drawn as a stop, not a failure. Every background report starts with its `Task:`. Reports that finish within 1.5 s of each other arrive together and cost one wake; a report whose `report.md` the parent already read (`read` or `localFetch`) arrives without one. When a notice (a finished bash job, a team message) wakes a subagent after it answered, its report keeps that answer and adds the later reply after a `---` line. The most recent 128 completed-subagent receipts are kept for this session: `sendMessage` to one says it finished and names its handoff folder. Older ids receive the usual unknown-agent response. In print/JSON runs the process stays open until background subagents finish; interactive sessions are never held.

## Subagent screenshots

Screenshots a subagent takes (`browser`) are saved under `~/.octocode/pi-team/shots/` (newest 30 kept). The `agent` tool row draws the latest one live and shows its path; the report ends with `(Last screenshot: path)`. They never enter the parent's context unless it reads the file.

## Agents UI

While this session has live subagents, a panel under the input lists them as a tree (a subagent's own subagents indented under it, working ones first among siblings) with aligned columns: status glyph (teal `●` working, dim `○` idle), id, state, elapsed time, tools, `↑input` `↓output` tokens, cost, flags (`✉ n` unanswered messages, `locks n`), then the task and the tool it is running now. A header sums them (`2 working · 1 idle · 3 in this session · ↑16k ↓4k · $0.04`); at most 6 rows, then `+n more`; recent messages between these agents follow. On narrow terminals cost, tokens, tools, flags and age drop out before the activity does. Other sessions' agents never show, and an agent whose heartbeat stopped for 15 s (killed or hung) leaves the panel at once; the store forgets it when its process is gone. Static text only, so scrolling stays stable.

## Team

Agents in the same repository (the main session, its subagents, other Pi sessions that `join`) share the team tables of the agent database (`OCTOCODE_AGENT_DB`, see [Sessions, backlog and memory](#sessions-backlog-and-memory-usage-and-privacy)), scoped by git root. Entities follow the octocode-agents-communication skill: **agents** (status, task, current tool, tokens, heartbeat), **messages** (immutable, may `replyRequired`, may answer another via `replyTo`), **deliveries** (delivered when injected, completed when answered) and **leases** (file/tree reservations). `coordinate` (`list` / `join` / `leave` / `lock` / `unlock` / `changes` / `stop`) shows each agent with join and last-seen time, unanswered messages and held paths, and reserves files all-or-nothing (a trailing `/` reserves a tree; case/Unicode aliases collide). Leases last 90 s past the owner's heartbeat and are released on leave, so a crashed agent frees its files; a subagent's are released when its run ends, and an idle session stops renewing them after 30 minutes (`OCTOCODE_LEASE_IDLE_MINUTES`). A refusal names the holder, its reason and how long ago it locked; `file`, `edit` and `write` are refused on paths a peer holds, and also when the database cannot be read (fail closed, with SQLite's reason; a process that never joined and has no database is not blocked). An agent whose own reservation lapsed is told once and must lock again before editing. Delivery is two-phase: a message is marked delivered only after it was injected, so one that fails to inject is retried. Each tick delivers at most 32 messages in order; the rest remain queued. Heartbeats prune message history older than a day, with pruning checked at most once per minute. Messages a departed agent never read are kept as dead letters (`dead-lettered` in the panel); the sender is told once, without a wake (`Message #N to X was not read: X left`), and sending to an agent that already left is refused. A headless subagent leaves the team when its run settles, so a late message is dead-lettered instead of falsely acknowledged. `coordinate changes` lists the files agents changed recently with `file`, `edit` or `write` (successful changes only; a partly failed `file` batch records only its OK queries), newest first, one row per file with the agent, tool, age and change count; `paths` narrows it to prefixes, `withinMinutes` (default 60, at most a day) and `limit` (default 20) bound it. Changes are kept a day; changes made by you, bash or git are not tracked, so use `localSearch` (`operation: "files"`, `time.modifiedWithin`, `sort: "modified"`) for what changed on disk. When the database is refused, `/agents` and the status bar show `team off` with the reason. `OCTOCODE_TEAM_WORKSPACE` (absolute path) overrides the git-root scope, so an isolated worktree subagent joins its parent's team. `sendMessage` (to an id, a unique role, `parent` or `all`) is queued (`Queued message #N for …`) and arrives within a second as a message from the sender: a busy agent reads it at its next step; an idle one wakes only for a message that requires a reply, the answer to its own still-open question (`replyTo`), or a message from the user or the API (an FYI, or a reply to a reply, waits for its next turn). An unknown `replyTo` id is refused. `all` reaches the sender's session tree (its top session and every subagent under it), not other sessions in the repository; `/agents tell all` and the API's `agents.tell all` reach the current session's tree. Messages over 8,000 characters are rejected before queueing; send a summary and a file path for larger content. An oversized body written by another process is withheld from model context with an explicit delivery-error notice, rather than injected as a partial instruction. API messages are labelled as from an external, untrusted client; `agents.tell` takes at most 8,000 characters and a refusal is an RPC error. `/agents` (also `/octocode agents`) lists the team (task, activity and message text stripped of terminal escapes) and `/agents tell <agent\|all> <text>` messages agents as the user. Reservations are cooperative: they do not cover arbitrary shell writes.

## Sessions

`/sessions` (same as `/octocode sessions`) lists sessions from Pi's `SessionManager` (so sessions from before Octocode was installed too), with what Octocode keeps in the local agent database (`<Octocode home>/agent/pi/octocode.db`): branch, git HEAD, cost, tokens, files changed, and whether its process is running. Octocode does not name sessions. It lists this repository's sessions newest first (`all` for every repository, or words to match name, first prompt, repository, branch or id; each line ends with the tail of the session id, and a fork with no prompt of its own shows `↳` and its parent's first prompt) and offers Resume (Pi's `switchSession` on the session file), Details, Rename (the current session only: Pi owns session names) and Forget Octocode data (deletes the session's Octocode folder and extras row; Pi's session file stays; refused while another Pi process has the session open). Resuming a session (or restarting Pi on one that already has prompts) adds a short brief before the next prompt, read when that prompt is sent, only when there is something to say: the git branch or HEAD moved, this session has ongoing backlog items, or you were away over an hour (the to-do count and uncommitted changes are then added as context, but never cause a brief alone). Its first line carries the away time and the most important change, so the collapsed transcript line shows both. Pi's own `/resume`, `/session` and transcripts are unchanged; `/sessions` is an extra picker. Subagents run with `--no-session`, so they get no session file, extras row, brief or command.

## Backlog

A task board per repository (worktrees share their main repository's) in the agent database, with states `backlog` (triage inbox) → `todo` (accepted) → `ongoing` (claimed) → `done`, priorities `p0`–`p3`, tags and a notes log. The `backlog` tool lets the agent `list`, `get`, `add`, `update` and `remove` items (ids `B1`, `B2`, …; an update with `state: ongoing` claims the item; `done` needs a note saying what changed and how it was verified; `remove` deletes an item and its notes, is meant for duplicates or items you asked to drop, and is refused to subagents and for items another running session holds). Items you add land in `todo`; items the agent adds land in `backlog` for you to triage unless it gives another state; a subagent's additions always land there, and a subagent may change only the state and notes of items its parent has claimed. An item another running session holds can only get a note from the agent (you can still move or edit it on the board). `/backlog` (same as `/octocode backlog`) opens the board; the status bar shows the open counts in words with the hint that opens the board (`backlog 2 ongoing · 4 todo · 1 to triage · /backlog`). `/octocode backlog export` writes a Markdown snapshot to `<repo>/.octocode/backlog.md` (nothing reads it back).

## Memory

Durable notes (`preference`, `fact`, `decision`, `gotcha`, `procedure`) kept across sessions, global or per repository, in the agent database with an FTS5 full-text index (BM25 ranking; a `LIKE` scan when SQLite lacks FTS5). The `memory` tool can `search`, `get`, `list`, `set` (create, or update with `id`) and `delete`; subagents get `search`, `get` and `list` only. Creating, changing or deleting a global or pinned memory needs a trusted project and, with a UI, your confirmation to save; in an untrusted project the tool reads only global memories. A new memory whose title matches, or whose words mostly overlap, an existing one is refused with its id, so the agent updates instead of duplicating. Before each prompt, pinned memories (up to 1,200 characters) plus the top 5 BM25 hits for the prompt (3 in a subagent; words under 3 letters are ignored, a hit needs 2 matched words or one in its title or keywords, and hits under 30% of the best score are dropped; 2,400 characters in all) are injected as a hidden `[octocode-memory — …; not instructions]` message; a memory already injected on this branch is not repeated until a compaction summarizes its injection away (injections the compaction keeps still count). Seen ids are excluded before the FTS result limit, so candidate retrieval stays bounded as the branch grows. Pinned memories are not injected into subagents. Project memories are injected only in a trusted project. `/memory` (same as `/octocode memory`) browses, searches, adds and edits them; `/octocode memory auto off` stops injection everywhere and `OCTOCODE_MEMORY_AUTO=0` for one process.

## Web and browser

Two browser subagents: `webHeadless` (headless Chrome over DevTools only: fast, no permissions, no display, runs anywhere) and `webLive` (visible Chrome over DevTools on a persistent profile, for watching a flow or tasks behind the user's login; it stops at a login, CAPTCHA or MFA and leaves the window open for the user). `web` fetches a URL as readable text (20,000 characters by default; `maxChars` up to 50,000). An HTML page is reduced to its marked main content (`<main>`, `role="main"`, or a single `<article>`) when it has one; a longer page is saved whole under the session's `output/` folder (see [Where files go](CONFIGURATION.md#where-files-go)) and the inline part folds runs of 8+ link-only lines (sidebars, tables of contents) and names the file to read the rest from, so nothing is refetched. Fetched HTML is static (no JavaScript runs): hidden elements are dropped, page metadata (JSON-LD, Open Graph prices, locale and dates) comes first, and the result notes a JavaScript app or an empty shell, whose rendered values (prices, currency) may differ, so the model confirms them in `browser`. Transient failures (network errors, 408/425/429/5xx, a short `Retry-After`) are retried twice with backoff and a final failure names its cause (`ECONNRESET`, `ENOTFOUND`, …); pages are cached for 15 minutes; a redirect to another host is reported, not followed. `web` also searches the web (Tavily / Serper / Exa / Brave with an API key; without one DuckDuckGo, then Bing, then DuckDuckGo lite, with the skipped providers and why named in the result). It refuses loopback, private, link-local (cloud metadata), CGNAT, multicast and reserved addresses, checking the resolved host and every redirect hop (`OCTOCODE_WEB_ALLOW_PRIVATE=1` turns this off). Residual risk: `fetch` resolves the host again after the check, so DNS rebinding between the two lookups is not caught. `browser` is the in-process CDP tool for both. It opens only `http(s)` URLs; a private, loopback, link-local or cloud-metadata host given to `navigate` or `tab` needs the user's confirmation (or `OCTOCODE_WEB_ALLOW_PRIVATE=1`), and so does `upload` of files outside the workspace. Limit: redirects, link clicks and page requests after that are not checked yet. It never connects to a running Chrome on its own: `attach(port)` drives an already open DevTools browser in place, and `OCTOCODE_CHROME_PORT` opts in to working in a tab of the Chrome on that port (a headless Chrome is launched when nothing listens). Deep checks can reuse the reported port with the `octocode-chrome-devtools` skill's scripts. Actions: navigate (after the load event it waits until content and requests are quiet for 500 ms, at most 6 s, and notes a page still changing; with `text` it also waits for that text), snapshot (with `text`, waits for it first; a `Locale:` line names the page language, browser language, time zone and the currency symbols on the page; footer links are listed compactly on one line) (capped at 8 KB: numbered elements first, with each field's value and state, then page text; a cut snapshot is saved whole to a file), click (a real mouse press at the element's centre, so mousedown/pointer handlers run; it reports an element covering the target), hover (a bare mouse move, for hover menus and tooltips), drag (`ref` onto `to`, or onto the smallest element showing `text`: an HTML5 drag is intercepted and finished with dragEnter/dragOver/drop, a pointer drag gets paced moves and a release), type (replaces a text field's or contenteditable's text, picks a `<select>` option by label, and is refused when focus does not land on a text field), fill (several fields in one call; checkboxes, radios and switches take `true`/`false` and are clicked only when they differ; failed fields are listed), press (a key or a combo such as `Control+A`, `Shift+Tab`; editing shortcuts are sent as Chrome commands so select-all works), wait (until `text` appears, or with `gone` disappears, up to `timeout` seconds, default 10, max 60; a timeout fails with the current page attached), tabs and tab (list tabs with stable numbers; switch by `index` or open `url` in a new one), evaluate, screenshot, console, `dialog` (answer an open alert/confirm/prompt; while one is open, snapshot reports it instead of blocking), `upload` (sets files on a file input, or on the chooser a click opens), `download` (optionally clicks, waits, and lists the files saved in `<cwd>/downloads/`); aborting the tool call cancels its pending page calls. Elements come from open shadow roots and same-origin frames too (cross-origin frames are counted, not shown), and include `draggable` elements and the outermost `cursor: pointer` elements holding no other control (framework click handlers leave no attribute). An element keeps its number while it stays in the page (new ones get new numbers; a new document starts at 1), so numbers from earlier results stay valid. Mouse actions move first and measure the element again, since a move can shift the layout (a hover menu closing). After an action the tool waits about 150 ms for a navigation, for its load if one started, then until the DOM is quiet for 150 ms (at most 3 s); a tab the action opened (`window.open`, a popup) becomes the driven tab. On the same page, actions return only the new or changed elements, the numbers no longer shown, and new text lines, instead of a full snapshot. A headless Chrome gets a 1366×900 window, so sites keep their desktop layout. A headless Chrome that `browser` launches gets a fresh profile under `<Octocode home>/pi-browser/`, removed when it closes (and swept at the next launch if the Pi process died). In `webLive` the Chrome is visible and uses the persistent profile `<Octocode home>/pi-browser-profile/`, so a login survives between runs; the window stays open when the subagent ends (`browser close` quits it), and the next `webLive` reuses it through the profile's `DevToolsActivePort` file. A Chrome open on that profile without DevTools is refused with a clear error.

## askUser

Ask for missing user decisions or facts (1–4 related questions per call). Choices, descriptions and short tab labels are optional; a question without choices opens a text editor directly. The inline dialog shows progress, retains typed drafts, and reviews answers before submitting a batch. Single-choice questions answer on Enter; multi-select questions toggle choices with Space or Enter and answer only from their **Submit selection** row (at least one choice or a written answer). RPC hosts use numbered choices and text inputs. Cancellation, interruption and an unavailable user are distinct; unanswered questions never supply approval. Continue independent work within existing authorization when a required decision is missing.

## Hooks (opt-in)

With `OCTOCODE_HOOKS=1`, Claude Code / Codex command hooks run on Pi events: `PreToolUse` (exit 2 or a `block`/`deny` decision blocks the tool), `PostToolUse` (feedback and `additionalContext` are appended to the result), `SessionStart` (runs in the background so startup is not held up; its output is added to the next prompt's context, which waits for it), `PreCompact`, `Stop` (when a run completes; exit 2 or `{"decision":"block","reason":…}` continues it with the reason as `Stop hook feedback`, with `stop_hook_active` and `last_assistant_message` as in Claude Code, and at most 8 continuations in a row until a tool runs; `continue: false` is not a block) and `Notification` (in the background, never blocking: `permission_prompt` for a confirm dialog, `elicitation_dialog` for other dialogs, `idle_prompt` after an answer sat unread for a minute; the matcher is the type). All matching hooks run in parallel, and one listed in several files runs once. Pi checks every call of a batch before any runs, so a slow `PreToolUse` hook holds the whole batch: the working line shows `Checking bash …` while it runs, the row shows `checks 1.2s` afterwards, a hook over 5 s is reported once, and `/hooks` lists runs, average and slowest time per command. Read from `~/.claude/settings.json`, `~/.codex/hooks.json`, `~/.octocode/hooks.json` and, in trusted projects only (see [Trust](CONFIGURATION.md#trust)), `<repo root>/.claude/settings.json`, `.claude/settings.local.json`, `.codex/hooks.json` and `.octocode/hooks.json`. Matchers accept Pi or Claude tool names (`Bash`, `Edit\|Write`); the payload is Claude-shaped: `bash` is `Bash` (same `command` input), `read` is `Read` with `tool_input.file_path`, and each `file` query is its own `Edit`, `MultiEdit`, `Write` or `Delete` call with `tool_input.file_path`; other tools keep their Pi name, and `pi_tool_name` is always the Pi name; hook text added to the context is capped at 16 KB.

## Compaction

Old, large tool results are trimmed (in batches, so the prompt cache survives). Summaries are Pi's own, written with the session model; Octocode adds the paths its `file` tool changed to Pi's file lists. See [docs/COMPACTION.md](COMPACTION.md).

## UI

In the TUI Octocode draws the header as the "OCTOCODE CODE" banner: a 6-row block font (2-row half-block font, then plain text on narrow terminals) painted along the theme's accent → link → operator gradient with box-drawing shadows, a tagline with the version, and key hints. It has a fixed height, writes nothing to the session (so `/new`, `/resume` and `/fork` keep it in place), and a light band sweeps across it once per process. The footer has two lines: model, thinking level, a context bar coloured by fullness, review mode, running agents and bash jobs, `tok/s` and cost; then cwd, branch, session name, tokens and other extensions' statuses (Pi's MCP, hooks, backlog), dropping the least important parts on narrow terminals. The spinner cycles braille dots along the same gradient; hidden thinking shows `✻ Thinking… (ctrl+t)`; the terminal title is `octocode · <session name> · <dir>`. Octocode also adds a generation-speed (`tok/s`) status and one `/octocode` command (see [Commands](../README.md#commands)). The working indicator names what the agent is doing now: `Thinking`, `Writing`, `Preparing tool calls`, `Running bash yarn test`, `Running 3 tools: bash · localSearch ×2` (every top-level call of a parallel batch; calls a tool makes itself are part of it) `Checking bash …` while a call's `tool_call` checks (reservations, the bash guard, PreToolUse hooks) run, or `Waiting for you: <title>` during a dialog (`(+N queued)` when more wait), with the elapsed time once a step passes 2 s; Pi's default comes back when the run ends. The same line, without the time, is the agent's activity in the agents panel. Messages Octocode queues while the agent works (subagent reports, background bash reports, teammate messages) show as `✉ n queued` until the agent reads them. Pi's Esc clears its whole queue but restores only your typed text; Octocode adds the queued messages it cleared to the conversation without starting a turn and says so (TUI only; RPC keeps Pi's queue for the next run). A tool row whose call waited before it ran adds `checks 1.2s` (its `tool_call` checks) or `queued 2.0s` (other calls' checks or the tool's lock) once the wait passes 250 ms.

**One dialog at a time.** Pi's TUI draws one dialog; a second one replaces the first, whose answer then never comes. Every interaction that asks (`askUser`, file review, the `browser` and `memory` confirms, `/octocode` subcommands, leave and checkpoint prompts) holds one shared queue, so a batch with `askUser` and a reviewed `file` asks one after the other. A call aborted while it waits stops waiting at once.

**Answer-ready notifications.** When the agent finishes an answer or opens a dialog while the terminal is in the background, Octocode sends a desktop notification (OSC 9, OSC 777, Kitty's OSC 99, or the bell; see `OCTOCODE_NOTIFY` and `OCTOCODE_NOTIFY_METHOD` in [CONFIGURATION](CONFIGURATION.md)) and puts `●` in the terminal title until you are back. Focus comes from terminal focus reports, which Octocode turns on in the regular TUI; in fullscreen mode Pi keeps them to itself, so Octocode notifies only after runs of 30 s or more with no key pressed for 30 s. Aborted runs, subagents and print, JSON and RPC modes never notify.

Tools batched in one assistant message run in parallel. `file`, `browser`, `askUser`, `memory` and `backlog` keep their own calls in order with a per-tool lock instead of Pi's `executionMode: 'sequential'`, which would make every other call in the batch (MCP searches, bash) wait too. Put dependent steps, such as an edit and the test that checks it, in separate messages. Every tool renders compactly like Pi's built-ins: a one-line call, a short result preview, full output on ctrl+o. `file` shows each change's reasoning under it, with +/- counts and inline diffs. An `agent` row names only the profile (`● Agent(researcher) · background`) and a background report names the agent id; the prompt given to the subagent shows in full above its progress or report when the row is expanded. A row the user interrupted (Esc, `/octocode jobs kill`, a stopped subagent) is drawn `◼` in the warning colour, not as a failure. The working line and the shared team database show a call's path, command, query, URL or element ref (never typed text), with credential-looking spans replaced by `[redacted]` and `user:pass@` removed from URLs.

## External API (opt-in)

Other programs can message a running session and follow it. `OCTOCODE_API=1` serves JSON-RPC 2.0 (one JSON line per message, the framing MCP, ACP and Codex's app-server use) on a Unix socket (`0600`, in a `0700` directory); `OCTOCODE_API_HTTP=<port>` (`0` = any free port) adds loopback HTTP; `/octocode api on [http]` and `/octocode api off` toggle it at runtime. Each instance writes `~/.octocode/pi-api/instances/<id>.json` (`OCTOCODE_API_DIR` overrides; pid, cwd, socket, HTTP URL and bearer token, mode `0600`), swept when the process dies. Subagents never serve one. See [External API](API.md).

## Sessions, backlog and memory: usage and privacy

**Working a backlog item.** Pick it on `/backlog` and press `d` (or Enter → Do it now), or run `/backlog do B12`: the item is claimed as ongoing for this session and the agent gets a prompt with its title and body, asking it to mark the item done with a note when finished (queued as a follow-up while the agent is busy). Delegate to a subagent asks the agent to hand the item to a subagent with the `agent` tool. You can also just say so: "work on backlog item B12", "add a backlog item to…", "what is on the backlog?" — the agent uses the `backlog` tool. Likewise "remember that…" or "forget memory M3" use the `memory` tool.

**Privacy.** The agent database and every session folder are private to your user (files `0600`, folders `0700`) and stay on this machine. Backlog titles, bodies, notes and tags, and memory titles, bodies and keywords that look like credentials (AWS access key ids; GitHub, GitLab, npm, Slack, Stripe, Google and `sk-…` API tokens; private keys; JWTs; bearer tokens; passwords in URLs or `password=…` assignments) are refused, checked on the text as stored: store where a secret lives, not the secret. Injected memories and the resume brief are labelled as data, not instructions, and the tool guidelines tell the model to verify memories against the code. A database file that is not an Octocode agent database (another app's SQLite file or not SQLite at all), or was written by a newer schema, is refused (set `OCTOCODE_AGENT_DB` to another file) rather than changed, down to its journal mode; opening the database tightens the file (and the default folder) back to owner-only; a missing or refused database never blocks a prompt.
