= Recommended practices for the Octocode Pi extension
:toc:
:toclevels: 3
:sectnums:

Status:: Research and implementation guidance
Research date:: 2026-09-10
Baseline:: Current Octocode working tree and the supported Pi host version, `0.84.4`

== Purpose

This document turns local implementation evidence, Pi's extension contracts, and useful patterns from other Pi extensions into recommendations for Octocode's tools, subagents, and terminal UI.

It is not another tool reference. Use link:TOOLS.md[Tools] for current behavior, link:SUBAGENTS.md[Subagents] for worker operations, and link:UI.md[UI] for the existing rendering contract.

The central recommendation is to preserve Octocode's explicit capability, recovery, and verification model while improving its interoperability and ergonomics. Community extensions are useful prior art, but they are not a reason to copy features that weaken bounded execution or duplicate existing surfaces.

== Executive recommendation

Keep these foundations:

* one direct tool facade per capability with strict schemas and explicit error channels;
* one gateway for the larger Octocode research catalog instead of registering every research tool directly;
* lossless result recovery when model-visible output is truncated;
* self-contained worker packets, least-capability profiles, no recursive worker spawning, and parent verification of handbacks;
* one immutable UI snapshot feeding transcript, footer, inspector, and semantic event output;
* bounded, cell-width-safe terminal rendering with text carrying meaning independently of color.

Improve these areas first:

. Prove file-mutation interoperability with Pi and other extensions, then use Pi's shared mutation queue if the current private queue can overlap it.
. Measure and introduce progressive activation for infrequent direct tools to reduce prompt cost without harming tool selection.
. Evaluate predicate monitors for background jobs and workers against the existing heartbeat wait path.
. Expose a bounded, versioned status projection for integrations rather than encouraging terminal scraping.

Avoid detached cross-session agents, invisible full-context clones, a second always-on status surface, or recursive subagents until a separate architecture decision demonstrates that their value exceeds their security and lifecycle costs.

== Decision model

[cols="1,2,3",options="header"]
|===
|Decision |Meaning |Examples

|Keep
|The current implementation already follows Pi guidance or expresses a deliberate Octocode advantage.
|Strict query envelopes, thrown execution errors, result spill and recovery, capability grants, verified handbacks, the shared UI snapshot, and idempotent shutdown.

|Improve
|The architecture is sound, but an interoperability, prompt-cost, lifecycle, or interaction gap is measurable.
|Shared mutation serialization, progressive tool activation, background UI ownership, worker completion grouping, graceful wrap-up, and renderer reuse.

|Avoid
|The feature duplicates an existing owner, hides authority, or adds durable state without a proven requirement.
|A second permanent worker roster, automatic raw-handback memory, recursive workers, silent transcript cloning, and fake progress percentages.
|===

=== Promising ideas to watch

The catalog also contains task sidebars, durable background runners, dynamic workflow engines, context-pruning tools, and generative UI extensions. These projects are useful discovery leads, but several are new, materially expand authority, or overlap Octocode's existing plan, Awareness, browser, and result-budget systems. Keep them on a watchlist until exact source, lifecycle tests, and a concrete Octocode workflow justify deeper integration.

The https://github.com/earendil-works/pi/discussions/7474[Pi extension-hardening discussion] identifies two ecosystem-wide needs that fit Octocode: testing the packaged extension through Pi's real loader and declaring host compatibility before runtime. Octocode already rejects unsupported host versions and exercises the real Pi SDK. Add a packaged-loader smoke test alongside those checks rather than relying on unit imports alone.

== Ideas selected from the landscape

=== Create one runtime owner

Introduce one session-scoped runtime owner with:

* one abort signal combined with per-operation signals;
* a last-in, first-out cleanup stack;
* idempotent stop behavior and aggregated cleanup failures;
* late-cleanup handling for resources registered after shutdown starts;
* an owned UI wrapper that ignores callbacks after the owner stops.

Route browser sessions, local servers, background Bash jobs, watchers, overlays, and worker completion callbacks through this owner. This consolidates lifecycle behavior that is distributed across `index.ts`, the runtime renderer, and individual tools. It also gives the overlay cancellation work one documented boundary even while Pi lacks a complete dismissal contract.

=== Add a freshness contract for evidence

Apply one delivery policy to cached facts that can outlive their evidence:

Live:: The source generation, file version, or worker state still matches. Present the fact at full authority.
Demoted:: The source changed or cannot be revalidated cheaply. Preserve the finding, remove stale coordinates or blocking language, and label the required recheck.
Retired:: The evidence target disappeared or the fact can no longer be verified. Remove it from ambient UI and record the retirement in bounded diagnostics.

Attach `observedAt`, source generation, and an appropriate file or task fingerprint to cached findings and handbacks. Apply the policy once before data reaches the footer, inspector, plan verifier, or model. This extends Octocode's stale-event rejection into an explicit evidence-authority contract.

=== Make approval decisions attributable

Return a structured decision receipt whenever Octocode allows, asks about, or denies a sensitive operation. A minimal receipt contains:

* a unique request ID;
* the requesting session or worker ID;
* the normalized operation and scope;
* the matched policy or approval reason;
* the resolution, such as policy allow, policy deny, user approve once, user approve for session, or user deny;
* the decision source and timestamp.

Use the same receipt in the transcript, Awareness events, diagnostics, and worker forwarding. Do not expose raw secrets or complete tool arguments. This makes a human decision distinguishable from automatic policy and lets tests correlate one prompt with one terminal outcome.

=== Add a fresh reviewer profile

Add an optional read-only `reviewer` profile that receives the immutable objective, acceptance criteria, modified scope, and claimed evidence. The reviewer returns `PASS`, `WARN`, or `FAIL` per criterion and cannot edit files or mark the plan complete.

The parent remains responsible for selecting checks, resolving findings, and completing the plan. Run this phase for consequential changes or explicit user requests, not every trivial edit. Measure false-positive rate, missed regressions, additional tokens, and time to verified completion.

=== Extend the existing review page with annotations

Octocode already writes `plan.html`, serves a live loopback bridge, preserves unsent feedback, and returns explicit Start or Request changes actions. Extend that owner instead of creating another review service.

Useful additions are:

* comments anchored to stable plan-step IDs;
* optional annotations on diff hunks or file paths;
* typed approve, revise, reject, and comment-only outcomes;
* orphan handling when a new revision removes an annotated target;
* a portable read-only artifact with interactive actions disabled when the live bridge is absent.

Start with plan-step annotations. Add code-diff review only after the plan workflow shows lower clarification latency or fewer misunderstood revisions.

=== Replace polling with monitor predicates

Allow a background job or worker wait to register a bounded condition such as process exit, quiet period, output pattern, file change, or explicit attention event. Record a small ordered event history and wake the parent only when the condition fires or the monitor stops.

Keep polling available for manual inspection, but do not spend model turns repeatedly checking unchanged work. Every monitor must have a stable ID, stop reason, owner, result cursor, and shutdown cleanup.

=== Enrich file mutation receipts

Octocode already preflights every query, rejects duplicate target paths, supports multiple edits in one same-file operation, serializes canonical paths, checks native file versions, and returns diffs and patches. Preserve those contracts.

Add machine-readable fields that make conflicts and truncation recoverable:

* pre-mutation and post-mutation version fingerprints;
* `applied`, `noop`, `conflict`, or `aborted` classification;
* `diffTruncated` and `patchTruncated` flags;
* changed-line and byte counts;
* a bounded current-range or refetch continuation after a stale-state rejection.

Do not persist full pre-edit content merely to offer general undo. That expands the sensitive-data footprint; prefer versioned receipts and the repository's normal history unless a separate encrypted undo design is approved.

=== Publish and test the extension surface manifest

Generate one manifest of tools, commands, shortcuts, status keys, widgets, footer ownership, event channels, and required Pi APIs. Use it to:

* detect duplicate names inside Octocode;
* identify likely collisions with an installed extension set;
* calculate direct prompt-contract cost;
* drive documentation inventory checks;
* load the packaged build through Pi's real extension loader in CI;
* compare the declared and observed surfaces before a Pi version bump.

`registerUniqueTool` already protects direct tool names. Extend the same evidence model to the other public surfaces rather than adding unrelated registration wrappers one at a time.

== Tools

=== Keep the direct palette small and explicit

Octocode registers a compact direct palette and routes the larger research catalog through `MCPTool`. This is the correct boundary: common actions remain discoverable while the full research catalog does not inflate every prompt.

Continue to require:

* a strict `queries` envelope and bounded per-query reasoning;
* preflight validation before side effects;
* explicit sequential or bounded-parallel execution;
* receipts that distinguish success, failure, and not-run work;
* thrown errors for failed execution so Pi receives the correct error channel;
* complete output recovery through a private artifact when the model-visible result is shortened.

Do not register each Octocode research tool as a separate direct Pi tool. That would duplicate discovery logic and increase the stable prompt prefix without improving capability.

=== Prove cross-extension file serialization

Pi's extension guide requires custom file-mutating tools to use its exported `withFileMutationQueue` across the complete read-modify-write window. Octocode has strong canonical-path queues and stale-snapshot checks, but its queue is owned inside the extension. That does not prove serialization with another extension that uses Pi's shared queue.

Recommended implementation:

. Add an adversarial integration test that runs an Octocode edit concurrently with a Pi or test-extension edit against the same canonical path.
. Assert that both operations cannot enter their mutation windows together and that no accepted write loses another accepted update.
. If the test exposes overlap, wrap the Octocode mutation window in Pi's shared queue while retaining Octocode's canonical-path and stale-snapshot protections.
. Exercise edit, write, delete, symlink aliases, and failure cleanup.

This is a high-confidence risk based on the two queue ownership models, not evidence that a lost update has occurred in production.

=== Activate infrequent tools progressively

Pi `0.84.4` supports registering tools once and changing the active set with `setActiveTools`. Octocode uses active-tool control for disabling weak built-ins and enforcing worker grants, but the main session exposes the full direct palette.

Run an experiment before choosing a permanent core set:

* record the current direct-tool contract characters using the existing contract metrics;
* classify tools by invocation frequency, selection ambiguity, and setup cost;
* keep the loader and common recovery path active;
* activate a requested tool additively instead of replacing the current set;
* avoid prompt snippets and guidelines on lazily activated tools unless they are necessary;
* compare prompt size, prefix-cache behavior, tool-selection accuracy, validation failures, and task completion.

Media conversion, browser diagnostics, and local-server management are likely candidates for deferred activation. The exact tier should come from usage evidence; `file`, `bash`, `MCPTool`, and the recovery path should not be deferred without a separate usability test.

=== Reuse renderer components where it pays

Pi recommends reusing `context.lastComponent` when a renderer can safely update an existing component. Octocode already centralizes renderer construction and supplies width-aware cached components for fixed content, but many result renderers construct a new component on each call.

Benchmark high-frequency and streaming paths first, especially `bash`, `agent`, and `MCPTool`. Adopt component reuse only when it reduces allocation or repaint cost without retaining stale theme, width, expansion, or partial-result state. Live spinners and the footer should remain uncached where their content changes with time.

=== Keep contracts and documentation generated from one baseline

The source pins the fallback MCP package to a semver range, while link:TOOLS.md[Tools] still describes an `@latest` fallback. Correct that drift and add a documentation assertion or generated value so the runtime fallback, architecture guide, and tool reference cannot silently diverge.

Treat link:AGENT_TOOL_AUDIT.md[Agent tool audit] as its dated snapshot, not as the current tool count or prompt baseline. Prefer live contract metrics for future activation decisions.

== Subagents

=== Preserve explicit authority and verified handbacks

The current worker model is a strength:

* every spawn packet carries goal, context, scope, ownership, acceptance criteria, and return shape;
* named profiles receive bounded capability grants;
* custom workers must declare both instructions and tools;
* workers cannot receive the `agent` tool and therefore cannot recursively spawn;
* results are pulled into the parent, normalized, and verified before plan completion;
* session shutdown terminates owned workers and releases their capabilities.

Do not replace this with implicit transcript inheritance. If an optional clone mode is ever considered, it should be separately named, visibly disclose inherited context, remain capability-bounded, and exclude unrelated secrets and tool output.

=== Add graceful wrap-up before hard termination

Silence-window waits and explicit abort or kill operations handle liveness, but there is no general soft turn budget that asks a worker to summarize before termination.

Add a versioned policy with three states:

. At the soft limit, steer the worker with a concise wrap-up request that names the required handback format.
. Allow a small, fixed grace budget for evidence and cleanup.
. At the hard limit, abort and return a typed partial handback that distinguishes incomplete work from failure.

The parent must still verify files, tests, or cited evidence. Never convert a budget expiry into `[DONE]`.

=== Group completion signals by spawn cohort

Parallel workers can finish close together. Emitting one ambient notification per success adds noise without changing the parent's next action.

Associate workers spawned by one query or plan step with a cohort identifier. Batch ordinary success notices for the cohort, but surface failures and requests for attention immediately. Keep the complete per-worker record in the inbox and preserve pull-based retrieval.

Choose batching windows from replay tests and interactive measurements rather than copying another extension's timing constants.

=== Add stable human-facing worker handles

The agent ID should remain the authority, but users benefit from a stable short name in commands, completion, steering, and inspection. Resolve a handle to exactly one session-owned agent ID and reject ambiguous or stale handles.

A leading-mention syntax can be explored, but it must not consume ordinary file mentions or silently start a new worker. Command completion is the safer initial implementation.

=== Publish one bounded machine-readable status projection

Octocode already has a normalized worker ledger, UI snapshot, inspector, and semantic events. Expose a versioned, redacted projection from that same state for integrations and tests. It should contain stable IDs, lifecycle state, parent or cohort relationship, attention state, and bounded summaries; it should not expose private artifact paths or raw transcripts.

Snapshots should be authoritative. Events are delivery hints and may be coalesced or missed. This avoids terminal scraping and prevents a second source of worker truth.

=== Do not expand autonomy by default

These patterns require an RFC and threat-model review before implementation:

* recursive subagents;
* detached workers that survive the owning session;
* separate persistent worker stores;
* automatic insertion of raw handbacks into durable memory;
* shared background and foreground capacity that can deadlock or starve interactive work.

Octocode's differentiator should remain evidence-backed delegation with recoverable state, not the largest possible worker fleet.

== Widgets and terminal UI

=== Keep one owner for each fact

The `UxSnapshotV1` and pure status policy are the right foundation. Transcript entries, footer rows, inspector detail, and semantic output should continue to derive from shared state rather than interrogating processes during render.

Maintain these rules:

* register a footer or widget once, then request a render when its state changes;
* do no I/O, session scans, or tool polling in the render closure;
* reject stale events and coalesce low-value heartbeat updates;
* reserve ambient space for active work and attention, with full history in the inbox or inspector;
* truncate by terminal cell width and sanitize untrusted terminal text;
* never use color as the only signal;
* show percentages or ETAs only when progress has a defensible denominator.

=== Offer one ambient worker surface, not two

A richer fleet view can help when several workers are active, but a permanent fleet widget next to the existing footer would violate the one-owner rule and consume scarce rows.

If implemented, make the presentation a mode:

* compact footer roster for ordinary work; or
* interactive fleet view for navigation and steering.

Do not render both simultaneously. Bound visible worker rows by viewport, prioritize failures and blocked work, and route omitted detail to the inbox. Foreground work should not be repeated in a background-only widget.

=== Centralize remaining background UI ownership

Most extension UI state is owned by the runtime renderer and shared store. The background `bash` path still directly owns a widget, status entry, controller, and timer.

Move that state behind the same session-generation and disposal boundary used by other runtime UI. The migration should prove:

* no timer or callback survives `session_shutdown`;
* a stale session cannot update a new session's UI;
* clearing one job cannot erase another owner's status;
* repaint requests are deduplicated;
* `NO_COLOR`, narrow widths, and non-TUI hosts remain correct.

=== Treat cancellable overlays as a host dependency

The ask-user and plan overlays can remain awaited after a tool turn is aborted. The supported Pi `custom()` surface exposes an overlay handle callback but no documented `AbortSignal` or guaranteed programmatic-dismiss contract. The same limitation is visible in the newer `0.85.1` type surface examined during this research.

Do not invent an untyped dismissal call. Keep the local lifecycle guard, create a minimal upstream reproduction, and request or adopt a documented cancellation handle. Any local workaround should be version-gated and covered by abort, session-switch, and shutdown tests.

== Extension lifecycle and compatibility

Pi extension factories may be awaited before interactive startup. Continue to avoid starting timers, watchers, or child processes in the factory. Acquire long-lived resources from lifecycle events or an explicit tool action, and make shutdown safe to call more than once.

Octocode intentionally accepts one exact Pi host version. Preserve that guard, but add a compatibility suite before a version bump:

* compile against the candidate Pi types;
* replay direct-tool rendering for partial, final, expanded, and error results;
* verify mutation-queue behavior;
* abort overlays and workers during session switches;
* exercise footer and widget cleanup;
* confirm dynamic activation and capability grants;
* load the packaged build through Pi's real extension loader;
* compare the documented host APIs with the adapters actually used.

The exact-version policy makes compatibility failures explicit; the suite makes upgrades cheaper and less dependent on manual discovery.

== Evaluation plan

Measure changes against explicit sensors rather than preference.

[cols="2,3",options="header"]
|===
|Area |Measures

|Tool surface
|Contract characters and estimated tokens; prefix-cache reuse; correct first-tool selection; schema failures; recovery-path success; total task completion.

|File safety
|Concurrent mutation-window overlap; lost-update count; alias handling; queue cleanup after thrown errors and aborts; stale-conflict recovery rate; receipt completeness.

|Workers
|Time from completion to parent verification; reviewer precision and recall; notification count per cohort; partial-handback usefulness; leaked processes; unresolved capabilities after shutdown.

|UI
|Render duration and allocation; repaint count; footer rows at widths 20 through 160; duplicate facts; stale-session update attempts; `NO_COLOR`, CJK, and emoji behavior.

|Evidence and approvals
|Live, demoted, and retired classification accuracy; stale blocking claims; request-to-decision correlation; missing or overexposed receipt fields.

|Compatibility
|Supported-host contract tests; packaged-loader success; manifest drift; adapter/type drift; overlay and worker abort settlement; session-switch cleanup.
|===

Use held-out workflows that include ordinary coding, parallel research, browser work, media tools, large output recovery, and simultaneous file edits. A prompt-size improvement should be reverted if it causes a meaningful fall in correct tool selection or task completion.

== Implementation sequence

. Reconcile the documentation, capture live contract metrics, and generate the public surface manifest.
. Add the packaged-loader smoke test and the mutation-contention test before changing runtime or queue code.
. Introduce the runtime owner and consolidate background UI ownership.
. Run the tool-activation experiment behind a local setting or test harness.
. Add evidence freshness and attributable decision receipts.
. Add the reviewer profile, worker wrap-up, and cohort notifications, then measure verification quality and noise.
. Prototype plan-step annotations, mutation recovery receipts, and monitor predicates as separate experiments.
. Add handles and the status projection before considering a fleet view.
. Require an RFC for detached, recursive, or cross-session execution.

== Anti-patterns

Do not:

* render the same worker state in both a permanent footer and a permanent widget;
* poll tools, workers, or files from a render function;
* use a mutable rendered string as the source of truth;
* equate worker success with verified task completion;
* expose artifact paths or complete transcripts through a status API;
* hide context inheritance or capability escalation;
* invent progress percentages for dynamic plans;
* retain timers, watchers, or child processes beyond their owning session;
* copy community timing, concurrency, or storage constants without an Octocode evaluation.
