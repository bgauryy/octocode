# Compaction

How Octocode keeps long Pi sessions within the context window, and why it is built this way.

## Two layers

1. **Tool-result trimming (every turn, no model call).** At `turn_end`, old tool results over 3,000 characters (all text parts together) are cut with append-only `context_edit` entries to their first 800 and last 300 characters (about 1,200 with the note). The tail is kept because spill pointers, exit codes and summaries sit at the end. Any line in between that points at the full text on disk (`Full output: …`, `Full report: …`, `Log: …`, as written by spilled output, Pi's bash truncation note, background job reports and subagent reports) is kept too, up to 3, and the trim note names the saved file so the model reads it instead of rerunning the call. The recent window stays verbatim: at least the 4 newest results, and up to 12 while their text fits 80,000 characters (~20k tokens), so a few huge results cannot fill the context. Edits change the cached prompt prefix, so they are proposed only when worthwhile: a batch of 10 or more that saves at least 20,000 characters, or any batch that saves 60,000. The same batch also shrinks the arguments of old *successful* calls whose JSON exceeds 2,000 characters: each string over 320 characters (a written file's `content`, edit `oldText`/`newText`, a long `agent` task) keeps its first 160 characters and a note, since the result is on disk; paths, keys and short values stay, and a call is left alone unless this saves at least 1,000 characters. Each call's verdict is remembered by tool-call id only while the call remains in the active branch (cleared on session start, compaction and tree moves), so a turn stringifies only calls it has not judged before. Calls whose result failed keep their arguments verbatim, and so do calls in the recent window, except successful `file` changes, whose text is already on disk. Images are replaced with a placeholder. User answers (`askUser`) and subagent (`agent`) reports stay verbatim during tool-result trimming because they cannot be safely regenerated. Pi owns their later summary compaction. Subagent previews are bounded; they are capped at 8 KB (200 lines), with full reports saved incrementally to disk, and team messages at 8,000 characters, since neither is ever trimmed. Pi keeps the raw entries in session history. Without a saved file, trim notes advise repeating only safe reads, since replaying a tool that changed files or sent a message can repeat its side effects. When the trimmed result was the latest read of a file (Pi's `read`, or a whole-file `fullContent` read with Octocode MCP's `localGetFileContent`), the file guard forgets that read: its content left the context, so the `file` tool asks for a fresh read before changing the file. A later verbatim read of the same file keeps it in view. Only tool results are trimmed. Custom messages are never trimmed: background bash job reports (output tail capped at 4 KB / 40 lines, terminal escapes stripped), background subagent results, team messages, memory injections, hook context, the resume brief and the running-work note below; each is bounded when it is written. This is the cheap layer: research on SWE-agent–style agents found that masking old observations matches LLM summarization at about half the cost ([JetBrains, 2025](https://arxiv.org/html/2508.21433)).
2. **Summary compaction (when Pi decides to compact): Pi's own.** Pi writes the summary with the user's session model, its prompt, auth, routing and retry policy, and reports failures itself; `/compact <focus>` passes the focus to Pi. Octocode only adds, at `session_before_compact`, the paths its `file` tool changed to Pi's file tracking (`preparation.fileOps`), so the summary's `<modified-files>` list is complete and Pi carries it forward to later compactions. `/tree` branch summaries are Pi's too. After a compaction the file guard forgets every read: a file read before it must be read again before the `file` tool changes it. Octocode then re-surfaces what the summary may have dropped and the model must not forget:

   - **Running work.** At `session_compact`, a non-waking custom message (`octocode-running-work`, hidden from the UI, at most 500 characters) lists the background bash jobs (id, command, log) and background subagents (id, task) started since this session started in this process that have not reported yet, and this session's ongoing backlog items. Running work is read from the session's own entries: a `bash` result with `details.job` and no `octocode-bash-job` report for its log, and an `agent` result with `details.status: 'background'` and no `octocode-agent-result` message for its id.
   - **SessionStart hooks.** With `OCTOCODE_HOOKS=1`, SessionStart hooks run again with source `compact` (as in Claude Code), and their context comes with the next prompt.
   - **Memory.** Memory injections from the compaction's first kept entry on are still in context, so only the ids injected before it may be injected again.

## Continuation across sessions

Background work reports back as a message. A job that session end (quit, `/new`, `/resume`, reload) stops is reported before it stops, without waking the session, so the record shows it did not finish; background subagents do the same. Work that never reported (Pi crashed or was killed) is named on resume: the resume brief lists it (``Stopped when the session ended, without a report: bash-3 (`yarn test`, log …); general-ab12 (task "…")``), and that alone is worth a brief. A log the retention sweep already removed is shown as `log deleted`, never as a path to read.

## Tests

`tests/compaction.test.ts` and `tests/compaction-trim.test.ts` cover the trim plan, its per-session memo, head/tail trimming with spill pointers, the guard forgetting trimmed reads, and the file-tool paths added to Pi's file ops. `tests/sessions.test.ts` covers the running-work note and the unreported work in the resume brief, `tests/bash.test.ts` the session-end job report, `tests/hooks.test.ts` the `compact` SessionStart source and `tests/memory.test.ts` the injected ids kept across a compaction. `tests/e2e.test.ts` › `compaction` runs a real Pi session with a scripted provider. It checks that:

- Pi summarizes on the session model (a cheaper model is never picked) with the user's `/compact` focus;
- the summary's file lists include files changed with the `file` tool and carry across compactions;
- the file guard requires fresh reads after compaction.
