# Package MCP and typed CLI

Load when setting up the Chrome package or using structured tool inputs. Why: MCP and CLI share one spec and engine through `octocode-mcp-cli`.

The package executable starts MCP by default; `/cli` selects the typed CLI and `/raw` selects the original argument-oriented engine CLI. Set the host server cwd to the workspace. The built package contains its bundled adapter, browser scripts, shared config and operating guides. The separate skill contains no implementation.

```json
{"mcpServers":{"chrome":{"command":"octocode-chrome-devtools","args":[]}}}
```

Without an installed bin, use command `npx` and args `["-y", "@octocodeai/octocode-chrome-devtools"]`; from a source checkout, use command `node` and args `["/absolute/package/bin/octocode-chrome-devtools.mjs"]`. It requires Chrome and Node.js 24.15.0 or later in the 24.x line (`^24.15.0`).

The default MCP server exports the research preset: `open`, `group`, `cleanup`, `targets`, `run`, `cdp`, `protocol`, `flow`, `schema`, `artifact`, `query` and `skill` (`researchSpec`): 12 tools; `run` plan steps `snapshot` and `screenshot` observe the page, so the standalone `snapshot` and `screenshot` tools are CLI-only (the `/cli` registry keeps them; the page-snapshot and page-screenshot `check` recipes and the plan ops capture the same evidence). `--mcp --preset slim` exports `open`, `cleanup`, `run`, `query` and `skill`. Start with `--mcp --preset full` to export every command except `snapshot` and `screenshot` (`dev-check`, `check`, `script`, `cookies`, `helper` and the rest); `/cli` always exposes every command, `snapshot` and `screenshot` included. Failures set `isError`; their text is a small JSON object that leads with `summary` (first cause), then `ok: false`, `exitCode`, `error`, any `timedOut`, `cancelled` or `outcomeUncertain`, and one `next` call (stderr, else the capture manifest) that reaches the logs, search scope and artifacts; a plan failure also keeps its `flow` summary. Success text is the one-line JSON of the same compact reply as `structuredContent`. Both surfaces use schemas and instructions authored in the shared core contract. `run` takes `{plan, connection}` (plan-level `dialog: accept|dismiss` answers JavaScript dialogs opened by `act` steps, default dismiss with a `JS_DIALOG` finding; plan-level `enable` is not supported yet; `snapshot` and `screenshot` steps take `options` in the recipes' env-style names, listed by `schema --command run --operation snapshot|screenshot`; a plan can end with `snapshot` and `screenshot` steps, and a step marked `optional: true` records its failure and lets the plan continue); a one-step plan replaces the removed `step` tool. `cdp` takes `{method, params, acknowledge?, enable?, scope?, connection}` (`enable`: CDP domain names to enable first; `scope`: `auto`, `page` or `browser`; the engine does not support them yet) (`acknowledge: true` after the user approves a sensitive method; the engine decides which, and raw `Runtime.evaluate` and `callFunctionOn` need it; for reading page state prefer the plan step `evaluate {expression, awaitPromise?}`). `protocol` (plans reach it as a `protocol` step) reads the installed Chrome's live schema and takes optional `{member, search, connection}`: `member` is `Domain` or `Domain.member`, `search` a keyword across domains, methods, events and types. Snapshot/screenshot accept `{options, connection}` and `check` adds `recipe` (capture recipes include `script-sources`, `source-map`, `storage-dump`, `network-events`, `network-conditions`, `coverage`, `trace-capture`, `heap-snapshot`, `page-pdf`, `page-html`, `page-archive`, `page-resources`, `console-log` and `downloads`; `options` is a plain object the contract validates per recipe; `schema` with `command: "check"` lists each recipe's options, and with `recipe` their types, required options and an example). `schema` takes optional `command`, `recipe`, and `operation`; a recipe requires `command: "check"`. The MCP `schema.command` list names only the tools of the connected preset; the CLI `schema --command` accepts every registry command by design (`snapshot` and `screenshot` included), so each preset list is a subset of the CLI list. `skill` takes optional `topic`, `offset`, and `length` (1–20000), and reads complete package guidance. `open` accepts `headless`, `port`, `url`, `allowOrigins` (origins plans may navigate to), `attach` (needs `port` and `acknowledge: true`, set only with the user's explicit consent, for a browser this package did not launch; excludes `url`, `headless`, `noSandbox`, `launch`), `noSandbox`, `emulation` (a plain object the contract validates: viewport `width`, `height`, `deviceScaleFactor`, `mobile`, `userAgent`, `colorScheme`, `reducedMotion`, `timezone`, `locale`, `geolocation` (needs `acknowledge: true`), `cpuThrottle`, `touch`; `{reset: true}` clears it; kept for the browser and meant to apply on every later call: the engine does not store it yet), one `launch` object for advanced launch options (advertised as a plain object; the contract validates its fields `enableFeatures`, `disableFeatures`, `blinkFeatures`, `windowSize`, `userAgent`, `proxy: {server?, bypassList?, pacUrl?}`, `chromePath` and `chromeFlags` at call time; `schema` with `command: "open"` lists them; refused with `attach`; `chromeFlags` refuses isolation-weakening flags and flags a typed field owns; ignored for a port that already has a browser). `open` is browser lifecycle only: tab groups belong to `group`. `group` (default surface) takes `{action: open|add|list|close, name?, urls?, private?, background?, newWindow?, tab?, port}`: `open` creates a named group (generated name when omitted; `private` defaults to true: an isolated browser context with its own cookies and storage, disposed on close; `private: false` uses the default context), `add` opens more `urls` in it, `list` shows groups, `close` ends one `tab` (a targetId) or the whole group; other tools select a group's tab with `connection.group` and `groupIndex`. `cleanup` accepts `port` and `dryRun`; `query` accepts `file`, `format`, `pointer`, `where`, `select`, `cursor`, `limit` and `sha256`; `artifact` accepts `file`, `format`, `pointer`, `offset`, `length` and `sha256`. `cookies` accepts `from` (exactly one of `{port}`, `{profile, sourcePort?, chromePath?}` or `{storageState}`), `to: {port}`, `confirmDomains` (at least one for `from.port` and `from.profile`; plain registrable domains), `urls`, `exportStorageState`, `dryRun` and `acknowledgeSecrets: true` (required; the user approved moving session secrets); it needs `to`, `exportStorageState` or both. `script` accepts `file` and `connection`. `proxy` (full preset only) takes `{action: start|status|stop, port, listenPort?, log?}`: a loopback-only, token-protected CDP passthrough for dynamic clients. `flow` (default surface) takes `{action: list|show|run|save, name?, params?, plan?, connection?}`: named reusable plans, built-in and workspace-saved; `plan` is for `save` only. Open, cleanup, query, artifact, cookies and script also accept legacy `args`, but cannot mix it with typed fields. `helper` (full preset) takes `{name, args}`: `name` is one of `snapshot-query`, `measure-query`, `har-pager`, `har-redact`, `api-replay`, `prune`, `protocol-corpus`, `har-ingest` or `corpus-query`, and `args` the existing CLI arguments passed without a shell (`["--help"]` shows usage; `prune` deletes, so start with `--dry-run`; `api-replay` sends a real request, so ask the user before state-changing methods). `/raw` still runs each helper by its own name.

Connection fields use camelCase and are limited to `port`, `target`, `targetUrl`, `group`, `groupIndex`, `newTab`, `keepTab`, `closeTab` and `stealth`, so the object stays small in every tool. The engine's other connection flags (`--target-type`, `--browser`, `--no-reload`, `--no-stealth`, `--timeout`, `--script-timeout`, `--verbose`, `--dry-run`) are not typed; use `/raw` for them (`/raw run --plan - --dry-run` validates a plan without Chrome); plan steps carry their own `timeoutMs`. Discover exact inputs from tool schemas or typed CLI help.

`schema` answers inline and offline: `command: "run"` lists every operation as one line (required fields and purpose) with the step fields every operation shares; with `operation`, such as `"extract"`, it returns only that operation's guide (own fields with types, the shared field names it accepts, an example) and, for `extract`, the supported extraction fields: `text`, `href`, `value`, `role`, and `name`. It returns command input examples from shared core. `name` reads aria-label or the element name attribute, without computing an accessible name. An ambiguous frame URL error includes every candidate target. Choose one connection target selector: `target`, `targetUrl`, `newTab`, or `browser: true`. Deadlines use milliseconds. Conflicting target selectors, keep/close flags, and stealth flags fail before execution.

```sh
octocode-chrome-devtools /cli cdp --help --json
octocode-chrome-devtools /cli cdp --method Runtime.evaluate --params '{"expression":"document.title","returnByValue":true}' --connection '{"target":"<id>"}' --json
octocode-chrome-devtools /cli run --input /absolute/input.json --json
octocode-chrome-devtools /cli skill --topic browser-execution --json
octocode-chrome-devtools /cli schema --command check --recipe page-snapshot --json
octocode-chrome-devtools /cli schema --command run --operation extract --json
octocode-chrome-devtools /cli cleanup --port 9222 --dry-run true --json
```

Whole-input files/stdin contain the tool input object: `{"plan":{"steps":[{"op":"cdp","method":"Runtime.enable"}]},"connection":{"target":"<id>"}}`. Use `--input -` for stdin and large plans. Inline typed `--plan` takes a JSON object; `/raw run --plan` takes a file containing the plan alone. Raw-engine examples use `octocode-chrome-devtools /raw <command>`. Without a global install, use `npx -y @octocodeai/octocode-chrome-devtools /raw <command>`; from a checkout, use `node /absolute/package/bin/octocode-chrome-devtools.mjs /raw <command>`.

Success returns one compact object (the same JSON is the MCP text and `structuredContent`; `/cli --json` prints it under `structuredContent`). It leads with `ok: true`, then only what applies: `data` (the engine result, or a complete reader page), `snapshot` (inline refs of a complete small page, from the `snapshot` tool or the last `snapshot` step of a `run` plan), `summary` (a `check` recipe's `[METRIC]`/`[FINDING]`/`[WARNING]` lines, at most 12 lines and 1500 bytes; `summaryTruncated: true` with `next.stdout` reads the rest), `flow` (compact plan summary), `stdout` (only when plain text is the answer), `files` (workspace-relative paths of artifacts to read next: screenshots, PDFs, traces, HAR, page-nodes; `{label, path}` entries when more than one kind), `evidence` (the saved capture manifest, which lists every artifact, finding and log), `warnings` (up to 5 `[WARNING]`/`[FINDING]` lines), `stderr` (a path, only when the call wrote diagnostics beyond the sandbox banner) and `next` (only continuations that read more). There is no `exitCode`, `signal`, `isPartial`, `capture`, `logs`, `search`, `root` or `hints`: a present `next` says more exists. Browser actions return completion counts and verified postconditions without input-event payloads. `flow.steps` lists reads, postconditions and failures; `next.steps` appears only when the page stops before the last step. `flow.events` reports listener counts and boundaries. Small CDP results and the first extraction page appear directly in `flow.steps`; oversized data and later steps have continuations. `flow.sources` hoists shared URL/frame identities. `flow.coverage` states executed and unvisited steps and the capture boundary. Plan bookkeeping (`browser-plan.json`, `browser-steps.jsonl`, `browser-result.json`) is not in `files`; the manifest at `evidence` lists it. `next.artifacts` pages `files` beyond the first 8; `next.findings` pages `warnings` beyond 5. JSON reader pages appear directly in `data`. Oversized values and later pages have executable continuations; source digests prevent mixing captures. Errors set MCP `isError`; the text block contains the failure payload (`summary`, `ok: false`, `exitCode`, `error`, one `next`). The typed CLI preserves the engine exit status; choose `--json` for machine-readable success.

Package continuations are `{tool, query}`. Relative continuation and search paths resolve from the workspace cwd; keep that cwd for CLI continuations. Absolute source paths remain in full captures. In MCP call `{name: next.tool, arguments: next.query}`. In the typed CLI save `next.query` to a file and run `<next.tool> --input file --json`, or pass its `args` through `--args`. Paths in `files`, `evidence`, `stderr` and `data` are workspace-relative (absolute only outside the workspace) and feed Octocode `localSearch`/`localFetch` or `rg`/`jq` unchanged. Captures live in a hidden, git-ignored `.octocode/` folder: search them with `includeHidden: true`, `includeIgnored: true`, `defaultExcludes: false`. Only remaining rows have `next.artifacts`; the manifest holds full paths. Run Octocode from the same workspace so its allowed-root boundary includes captures. Native Octocode tools take their own query envelope, not the browser helper `args` input.

Calls serialize within one server. Separate servers must coordinate a shared tab. An MCP cancellation notification aborts active engine execution and rejects queued calls before they launch. Captured partial logs survive cancellation; an in-flight mutation remains uncertain. Explicit engine deadlines also bound calls. Retry per [bounded retry](recovery.md#bounded-retry).

Maintainers use `yarn workspace @octocodeai/octocode-chrome-devtools build` and `verify`. The build bundles `octocode-mcp-cli` once and refreshes shared config; the extracted archive needs no runtime dependencies. Real-browser behavior, across MCP, the typed CLI and the raw engine CLI, and the extracted archive are checked by hand from the README's browser checklist.

Next: steps, event references and sessions → [browser execution](browser-execution.md); failed target/request → [recovery](recovery.md).

For repeated calls, keep one MCP client connected to the same server and workspace, then close it when the task ends. Reconnecting for each call repeats server initialization. Calls still serialize, and each browser operation runs its bounded engine; a persistent client does not create a browser daemon or relax cancellation and ownership boundaries.

Typed query predicates reject numeric integers outside the safe JavaScript integer range. Use an integer string such as `"9007199254740993"` for exact comparisons. Raw helper predicate JSON preserves original numeric lexemes. Returned numeric-filter continuations use legacy `args` to preserve those lexemes; copy the whole continuation unchanged.

## MCP flags

| Flag | Effect |
|---|---|
| `--mcp` | stdio MCP server (research preset, 12 tools) |
| `--preset slim\|research\|full` | pick the base tool set |
| `--tools <group\|tool>[,..]` | add groups or single tools to the preset; a tool the preset already holds is a no-op; an unknown name fails fast listing the valid names |

Groups (`toolGroups` in `src/adapter.ts`, together exactly the tools `full` has beyond `research`): `data` = `cookies`, `session`, `script` (about +0.9k tokens on research); `devtools` = `dev-check`, `helper`, `proxy` (+0.7k); `capture` = `check` (+0.4k). Example: `--mcp --preset research --tools data,proxy`. Instructions and the MCP `schema.command` list name only the resulting tools. `node tools/measure-surface.mjs` prints each group's cost on top of research.

## Token budget

Every MCP client loads each exposed tool's name, description and input schema on connect. `node tools/measure-surface.mjs` (after `yarn build`) starts each preset and prints the tool count and an estimated token cost (characters / 4, not a tokenizer count), then per-tool rows for the full surface. `tests/unit/surface-budget.test.mjs` guards the invariants: slim < default < full, default at most 78% of full, slim at most 52% of default, `flow`'s schema no larger than `run`'s, one identical compact `connection` copy in every tool, and a ceiling on the default. It also checks that `open` and `check` advertise `launch` and `options` as plain objects while the contract still refuses denylisted flags and bad recipe options.

| Preset | Tools | Est. tokens (was) |
|---|---|---|
| slim (`--preset slim`) | 5 | 1.5k (3.7k) |
| default (`research`) | 12 | 3.9k (7.2k) |
| full | 21 | 7.4k (9.5k) |

How it stays small: the shared `connection` object lists only nine fields (about 210 tokens, repeated in every tool that takes one); `open.launch` and `check.options` are advertised as plain objects with a one-line description, and the contract validates them in full at call time (`schema` serves their fields, types, required options and an example, read from the validating schema); `run.plan` advertises only `steps` (each an object needing an `op` from the one operation list) and the plan options; the contract validates every step against the strict plan schema at call time, and `schema --command run [--operation <op>]` serves each operation's fields, types, enums, required flags and an example; `flow.plan` is an opaque object (the engine validates a saved plan with the real plan validator before writing); the plan fields shared by every operation (`after`, `frame`, `session`, `timeoutMs`, `optional`) and the option types `flag` and `number` are defined once as `$defs` and referenced; field text that `schema --command run` already serves is not repeated in the tool schema. `dev-check` is full-preset only; `cdp` and `protocol` are in the default preset, and a plan ending in `snapshot` or `screenshot` steps replaces the standalone capture tools. The server instructions carry a compact plan-op cheat sheet (the common ops with their fields) whenever `run` is present.
