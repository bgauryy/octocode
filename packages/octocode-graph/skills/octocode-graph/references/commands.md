Load when building, serving or replaying a graph, reading events, or interpreting build progress.

# Commands

Requires Node 24.15+ and a browser for the viewer; `rsync` supports the frozen-copy fallback. The viewer serves its bundled renderer locally. `octocode-graph preflight` reports available layers.

Every `octocode-graph <command>` below also runs as `npx -y @octocodeai/octocode-graph <command>`, with nothing installed: use it when `octocode-graph` is not on PATH. The CLI's own hints, usage lines and `brief.txt` name `octocode-graph` only when the first `octocode-graph` on the shell's PATH runs this package (a package runner's `node_modules/.bin` does not count), and the npx form otherwise.

Pass a file to build or serve a graph of that file alone. Pass its enclosing directory when you need cross-file imports and calls. Run from the target workspace, which defines paths and allowed roots. Use the command’s `--help` for options. The graph package gets its engine from its `octocode` dependency. Set `OCTOCODE_CLI` to select a specific engine. The build and viewer validate options before starting work. In a channel with multiple viewers, each result directory records the tool calls for its own build and refreshes. Use a new output directory for each build and `--replay` to reopen a saved run. The selected CLI’s full catalog identifies the executable and each tool’s batch limit. The pipeline freezes that executable in a private directory under the OS temp directory, keyed by its SHA-256 digest. Runs can reuse the same image and warm language servers. An image no run used for a day is removed, unless a running process pinned it. An incompatible schema stops the build before file listing.

| Goal | Command |
|---|---|
| What runs here | `octocode-graph preflight [--json]` |
| Live viewer | `octocode-graph serve <section> [--out <dir>] [--whole] [--lsp smart\|all\|off] [--jobs N] [--ingest-jobs N] [--exclude a,b] [--port N] [--no-open] [--exit-when-done]` |
| Headless result | `octocode-graph build <section> [same flags] [--progress] [--no-cache] [--explain-cache]`. A section inside a workspace (an ancestor with package.json `workspaces`, `pnpm-workspace.yaml`, a Cargo `[workspace]` or `go.work`) whose imports name packages of that workspace outside the section leaves them as externals: stderr, `brief.txt` (`SCOPE`) and `data.json` `workspaceExternals` in data.json `coverage` name each package with its member directory and import count, and the build of the workspace root that stitches them |
| Ask a saved graph | `octocode-graph query <result-dir\|data.json\|project-dir> "<query>" [--json] [--stdin] [--refresh]`. A project directory answers from its newest graph under `.octocode/octocode-graph` (of the current directory or the project), else the newest the graph registry lists for that root. `--refresh`: when graph files changed since the graph was written, the chunks holding them refresh first (as `refresh`) and the answer comes from the refreshed graph; unchanged, it answers directly. Exit 0 answered, 1 a query error or a broken rule (`failed: true`, `reach --forbid`), 2 a usage error or no saved graph |
| What changed structurally | `octocode-graph diff <result-dir>` (the graph the last refresh replaced, kept as `previous.json`, against `data.json`) or `octocode-graph diff <before> <after> [--json]`. [Diff snapshots](diff.md) |
| Update a saved result after edits | `octocode-graph refresh <result-dir\|project-dir> [--lsp smart\|all\|off] [--progress] [--no-cache]`: rebuilds only the chunks holding a change (an added or removed package manifest rebuilds the whole root), then stitches, checks and measures again. The LSP pass probes only functions an edit could change: one whose file changed, or one that calls into a changed file; the rest keep their previous answers (`callStats.carried`). Events append to `events.jsonl`. A run a viewer serves refreshes through `octocode-graph reply <dir> --refresh` |
| Dependency rules for CI | `octocode-graph check [<result-dir\|project-dir>] [--rules <file>] [--format text\|json\|sarif] [--baseline <file>] [--write-baseline] [--since <rev>]`: exit 1 on a new error violation, 2 when the rules or arguments cannot be used. [Rules](rules.md) |
| Reopen a finished run | `octocode-graph serve --replay <result-dir>` |
| The shared graph cache | `octocode-graph cache stats` (entries and bytes by kind, JSON) or `octocode-graph cache prune --max-bytes N` (evicts the least recently used until the entries hold at most N bytes) |
| Briefs again (after `model.json`) | `octocode-graph render --data <dir>/data.json` |
| Tool calls, errors and time of a run | `octocode-graph events <result-dir\|project-dir> [--json]`: summarizes `events.jsonl` (below) |

Every build and refresh registers its result for its root in the per-user graph registry: `graph-registry/` in the Octocode home (`OCTOCODE_HOME`, else `~/.octocode`), one small file per result. `query`, `refresh`, `diff`, `openGraph` and MCP `query_graph`, `refresh_graph` and `diff_graph` with a project directory consult it after the default places, newest graph first, and drop entries whose result directory is gone. A registered result answers only for the root its own `events.jsonl` header names.

Builds and refreshes share `graph-cache/` in the Octocode home, keyed by content: a chunk whose files, the configs the engine read, the engine executable, this package and the options that change output are unchanged is restored without paging (its snapshot is still built, cheaply, so freshness checks query a live one), and a declaration whose file, the files its answer points into, its directories' configs and the language server route are unchanged keeps its callees answer (`callStats.cached`, not probed). Every lookup is a `cache` event in `events.jsonl`; a miss names the first key part that changed (`file b.ts 1a2b… → 3c4d…`, `input ../package.json …`, `engine`, `option exclude`, `callee <file>`); `--explain-cache` prints them, and the build's JSON summary counts hits and misses. `--no-cache` neither reads nor writes it.

Use `--lsp smart` (default) for callable declarations in hub files and callers crossing a chunk boundary. Use `--lsp all` to probe every indexed function, method and constructor with a declaration line, including those with no static calls. `off` skips confirmation. The saved probe totals and unanswered reasons describe coverage.

## Pipeline

1. **Files**: `structureSearch` (`operation: files`, `view: paths`) pages the section; each page is a `skeleton` event, so nodes appear before any ingest finishes (`git ls-files` when the tool is unavailable).
2. **Plan** package and loose chunks from the listed files whose extensions the CLI advertises for graph facts. Source-bearing fixtures participate. The skeleton keeps the full listing. Use `--whole` for one native snapshot over the section.
3. **Graph**: chunks build with `graphBuild`, with concurrency controlled by `--ingest-jobs`; `--jobs` controls query workers. Stderr progress (`parsed N/M files`, `linked`, `published`) updates each chunk. Paused builds follow `next.expandScan` unchanged until a snapshot is published. A `scopeTooBroad` refusal splits that chunk and queues its parts. The reply's `next` is followed to its end and `rowPart` fragments reassemble before evidence lists or cycle-member pages; rows stream once with root-relative IDs. Independent operations share a call up to the published batch limit. Each query keeps its result index across pages and follows its own evidence branches. When a chunk has more files than a source-target list can hold, the viewer uses its complete native file inventory to partition witnesses and symbols among query workers. Each file belongs to one group, and the worker follows each issued continuation in order. A partial inventory falls back to the full snapshot walk. A witness walk preserves separate occurrences with identical displayed fields. A tree that changes during a build is graphed from a frozen copy under the chunk's `tmp/`.
4. **Stitch**: imports between chunks from out-of-root relative imports, Rust paths into other workspace crates (`octocode_io::memo::Memo` to that crate's deepest module file; the crate name is the Cargo `[lib] name`, else the package name) and workspace package names; calls bound by exact top-level name through those imports or by a workspace crate path to its module file (`stitched`, medium). Call gaps are read only for the files that import another chunk: one graphQuery `unresolved` per group of files (as many as the schema's `target` list allows) with `edges: ["calls"]` and `reasons: ["not-declared-in-repo", "external-package"]`, filtered before paging; none for a single chunk. Cycles and findings stay per chunk.
During a large build the live map groups files by folder. Folder labels show parsed files over listed files. Click a folder to open it, or search for a file to jump directly to it. When metrics arrive the overview switches to dependency communities. The Folders or Communities button switches between grouped and individual files.

After stitching the pipeline atomically publishes `stitched.json` and emits `graph-ready`. The live query endpoint reads the current graph, including completed LSP batches. Each answer labels pending confirmation until the LSP phase finishes. The final `data.json` is published atomically after verification and metrics and replaces the checkpoint.

5. **LSP**: the selected callable declarations are batched by the published `lspSearch` limit, with continuations followed per query. Each probe asks one function for its callees. The probed functions are those in hub files, the sources of calls bound between chunks, and every function holding a receiver call no rule bound to a method declared here (`client.open(..)` on a receiver the graph cannot type): the server resolves that receiver. `callStats.receiverSources` counts the functions selected only for such a call. Same-line declaration collisions and moved anchors remain unanswered. Graph calls it confirms become `both`, unconfirmed probed ones stay `graph`, callees only the server reports join as `lsp`. A language without a server is reported and skipped; no step has a fixed timeout. When the only gap is `locationsWithheld`, a returned definition can confirm a call by file, name and declaration line. The probe stays incomplete. Each batch streams newly incomplete probes, and `callStats.unanswered` in the final graph lists all of them.
6. **Verify** each file against its declarations, recorded edge lines and the snapshot. For status and line problems, read the `check` object on each saved file. Freshness queries share batches up to the native limit. A failed batch is retried by snapshot. Files with unknown freshness are marked `unverified` unless a disk or line check has already found a problem. Insights shows affected files and the reason.
7. **Metrics** weight production imports and call sites by binding evidence and compute cycles, dependency depth, PageRank, betweenness, communities, k-core and package coupling. Values land on `files[].metrics`, sets on `metrics`, weighted edges on `fileEdges`, then in the briefs. They measure structure, not runtime frequency.

## Viewer and server

The viewer can chat with the agent that opened it (click a node, ask; the reply appears in the drawer) and refresh after code changes: `octocode-graph reply <dir> "answer" --chat <id>`, then `octocode-graph refresh <dir>`, or the channel's `reply`/`refresh_graph` tools. Details and the security notes: [chat](chat.md).

Event batches travel as lossless gzipped WebSocket frames, decoded in arrival order. `octocode-graph serve` binds 127.0.0.1 on a random (or `--port`) port, serves only its own assets, and requires the run token in the page and WebSocket URLs plus a same-server `Origin`. The pipeline starts with the server; a reconnecting page sends `hello {since}` to recover missed events. The server remains available after `done` for AST outlines (`astSearch symbols`) and LSP `callers`, `callees` or `references`; those answers are events too.

Each line of `events.jsonl` records an event with a sequence number and elapsed milliseconds. `octocode-graph events <dir>` summarizes it: per tool and in total, the calls (each tool id once), cursor pages, failed calls, calls answered with an error row, unfinished calls, rows, bytes and summed call time; per run (the build, each refresh, then later events), the wall time from its first event to its last and each phase's duration; and whether every id started exactly once. `--json` writes every field.

| type | Carries |
|---|---|
| `run`, `phase`, `progress` | Root and options; phase start/done/skipped with notes; done/total per phase |
| `skeleton`, `plan`, `chunk` | Listed paths per page; planned chunks; chunk state (ingesting, paging, done, split, error) with counts, and `build`: the latest graphBuild progress line while ingesting |
| `rows` | `files`, `witnesses` or `symbols` rows of one graph page, root-relative |
| `findings` | One chunk's ranked issues, cycles, health, detector counts |
| `stitched`, `graph-ready`, `lsp` | Cross-chunk imports and calls, package nodes, gaps; per-batch call provenance updates and LSP-only calls |
| `tool` | Every octocode call: tool, detail, page (first or cursor), rows, total, continues, ms, bytes, error |
| `metrics`, `done`, `error`, `note` | Per-file metric columns aligned to one id list, weighted edges as index columns, cycles, communities, packages, timings; result paths; failures; warnings |
| `ast`, `lspResult` | On-demand answers from the page |

A viewer connection resumes after its last applied sequence number. Replay and live traffic use ordered gzip batches sized to the socket write target. A larger event travels whole. A slow connection resumes as its socket drains.

For a standalone HTML file, use the installed package command `octocode-graph html <result-dir> <new.html>` after the build finishes. The file embeds the saved events, graph evidence, renderer and query engine. New AST and language-server requests require a live viewer.
