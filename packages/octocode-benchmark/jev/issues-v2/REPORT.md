# Issues-v2 campaign report

## Verdict: INVALID — infrastructure failure, no efficacy result

This report closes the frozen v2 campaign as a sensor failure. It does not grade either arm and provides no evidence for or against Jev treatment efficacy.

## Goal and frozen subject

- **Goal:** compare issue-triage and safe-fix quality for Octocode alone versus Octocode plus the updated Jev logical-if skill.
- **Suite:** six public issues, paired baseline/treatment arms, one fresh `gpt-5.6-terra` high-effort host per arm.
- **Primary KPI:** independently judged solution quality `/10`, with paired mean, pass count, major false claims, and attribution diagnostics.
- **Loop level:** exploratory public pilot; report-only even if valid.
- **Frozen protocol:** `CONTRACT.md`, `EXECUTION-AMENDMENT.md`, `frozen.json`, and `execution-frozen.json`.

## Integrity and execution

Generated by `node inspect.mjs --save` after all scheduled processes terminated:

| Check | Result |
|---|---:|
| Frozen file hashes valid | 2 / 6 |
| Host slots terminal | 12 / 12 |
| Host slots complete | 0 / 12 |
| Complete required artifact sets | 0 / 12 |
| Gradeable baseline/treatment pairs | 0 / 6 |
| Successful Jev calls | 0 |
| Answers available | 0 |
| Receipt hash errors among recorded events | 0 |

The contract and wrapper hashes still match. The frozen skill files and built Octocode CLI no longer match their v2 hashes, so v2 cannot represent the current treatment or tool surface. This mismatch occurred after the attempted run and independently invalidates any replacement continuation under the v2 identity.

All twelve host processes report the external Codex usage-limit failure. The first pair performed partial research before termination but produced no complete answer/result pair. The other slots failed at startup. Per the frozen protocol, invalid pairs are not scored as zero improvement and failed slots are not replaced in place.

Raw machine-readable metrics are preserved in `metrics.json`; per-slot prompts, host receipts, stderr, and partial wrapper events remain under `runs/`.

## Metrics intentionally not computed

Routing accuracy, macro-F1, baseline/treatment correctness, paired quality delta, correction rate, corruption rate, unsupported-claim rate, initial-hunch recovery, and model cost are all **N/A**. Computing any of them from zero valid pairs would manufacture a benchmark result.

## Decision

- **REJECT v2 as efficacy evidence.** This is not a rejection of the skill or of optional Jev routing.
- Preserve v2 unchanged except for generated inspection metrics and this closure report.
- Do not retry, replace workers, grade partial prose, or reuse the v2 suite ID.

## Next decision-changing experiment

Create `issues-v3` only after all gates below pass:

1. Run an excluded host-capacity canary before freezing; do not consume a benchmark case.
2. Freeze the current skill, routed references, schemas/policy, builder/apply scripts, benchmark wrapper, and built Octocode CLI by hash.
3. Update treatment instructions to use `route-decision.mjs`, `build-decision-packet.mjs`, `validate-decision-packet.mjs`, the pinned Jev call, and `apply-response.mjs`; never serialize `DecisionBrief`.
4. Preserve byte-identical evidence and matched retrieval budgets between arms.
5. Run at most two workers concurrently and retain the no-replacement rule.
6. Seal hidden grading before answers are exposed. Reuse prior gold only if its immutability, independence, and non-exposure to fresh workers are verified; otherwise curate new gold.
7. Require complete answer/result/before/after receipts and protocol-valid treatment calls before grading.

Until a valid v3 pilot exists, the deterministic 15/15 routing suite and standalone 27/27 tests are implementation guardrails only, not semantic-efficacy evidence.
