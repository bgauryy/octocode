**Short answer:** `ImmutableSet` builds its elements in an open-addressed, linear-probing hash table. It bounds how long a probe run can get. If a run is too long, it abandons the table and switches to a `java.util.HashSet`-backed implementation, `JdkBackedImmutableSet`. The JDK set has its own flooding protection. All line numbers below are in `guava/src/com/google/common/collect/ImmutableSet.java`, except the `JdkBackedImmutableSet` ones.

**Mechanism**

1. **Hash spreading.** `insertInHashTable` runs `Hashing.smear(e.hashCode())` and then probes linearly (`:703-706`).
2. **Online check on every insert.** The probe loop is `for (i = i0; i - i0 < maxRunBeforeFallback; i++)` (`:711`). If it never finds an empty slot or an equal element within that many probes, it falls back. The fallback is `new JdkBackedSetBuilderImpl<E>(this).add(e)` (`:725`, comment "long run; fall back to JDK impl"). This catches many identical or colliding hash codes. Without the bound, construction would take O(n²), as the Javadoc notes.
3. **Run limit.** `maxRunBeforeFallback(tableSize) = MAX_RUN_MULTIPLIER * log2(tableSize)` (`:878-879`), with `MAX_RUN_MULTIPLIER = 13` (`:815`). The comment says the value was "determined experimentally" to keep false positives acceptable.
4. **Whole-table check at the end.** `review()` calls `hashFloodingDetected(hashTable)` (`:744`) and switches to `JdkBackedSetBuilderImpl` if it returns true. The method (`:835-870`) scans the table for any run of filled slots longer than the limit. It takes O(n) worst case and O(n / log n) on average. Its Javadoc says the online check can't catch hashes "adversarially designed to go into ascending table locations". Those keep construction O(n) but could make later queries O(n). If the scan returns false, no query takes more than O(log n).
5. **Fallback implementation.** `JdkBackedSetBuilderImpl` (`:886-928`) copies the elements into a `HashSet` (`:891`). `build()` returns `new JdkBackedImmutableSet<>(delegate, asImmutableList(...))` (`:927`). `JdkBackedImmutableSet` is documented at `JdkBackedImmutableSet.java:23` as the defense against apparent hash flooding. The fallback comment (`:809`) says `HashSet` "has built-in flooding protection".
6. **Where it applies.** `of(...)` with 2–5 elements and with more than 6 elements, and `copyOf`, all go through `RegularSetBuilderImpl` (`:111-154`, `:273`). `Builder` also uses it (`:433`), and `forceJdk()` exists for tests (`:444-446`).

**Related, not asked about:** `RegularImmutableMap` and `RegularImmutableMultiset` use a different defense, a maximum hash bucket length (`MAX_HASH_BUCKET_LENGTH`, 8 for the map at `RegularImmutableMap.java:70` and 9 for the multiset at `RegularImmutableMultiset.java:119`). I did not check how those fall back.

**Uncertainty:** I read the code but did not run it. I did not read the `ImmutableSetTest` false-positive tests that the Javadoc mentions.
