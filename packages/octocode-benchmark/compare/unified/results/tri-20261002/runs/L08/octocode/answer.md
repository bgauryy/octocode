**Short answer:** the scrape loop wraps its storage appender in a `limitAppender`. That wrapper counts the samples added in one scrape and returns `errSampleLimit` once the count passes `sample_limit`. The loop keeps parsing after that, and it fails the scrape at the end.

**Evidence (commit ea954809ce):**
- **Config to loop:** `sampleLimit: int(opts.sp.config.SampleLimit)` is set when the scrape loop is built (`scrape/scrape.go:1349`). The field is declared at `scrape/scrape.go:962`.
- **Wrapping the appender:** `appenderWithLimits` adds the limit layer only if `sampleLimit > 0` (`scrape/scrape.go:718-723`). A comment there says the limit applies after relabeling has dropped metrics (`scrape/scrape.go:717`). The scrape loop calls it at `scrape/scrape.go:1827`. The V2 appender path has the same logic in `appenderV2WithLimits` (`scrape/scrape_append_v2.go:37-47`, called at `:140`).
- **The counter:** `limitAppender` is defined at `scrape/target.go:378-383`. `Append` increments `app.i` and returns `errSampleLimit` when `app.i > app.limit` (`scrape/target.go:388-392`). `AppendHistogram` does the same (`scrape/target.go:404-408`). The error is defined at `scrape/target.go:373`.
- **Staleness markers:** the check is skipped for a stale-NaN marker when the series already exists (non-zero ref). That way the markers are always written (`scrape/target.go:386-388` and `:402-404`).
- **Handling the error:** `checkAddError` catches `errSampleLimit`, stores it in `sampleLimitErr`, and returns `false, nil`. Parsing continues so the total sample count is still reported correctly (`scrape/scrape.go:2163-2167`). After the loop, `sampleLimitErr` becomes the scrape error if no other error is set (`scrape/scrape.go:2055-2058`). The `targetScrapeSampleLimit` metric is incremented once per scrape (`scrape/scrape.go:2060`).
- **Reporting the limit:** the configured limit is exposed as the `scrapeSampleLimitMetric` report sample (`scrape/scrape.go:2320`).
