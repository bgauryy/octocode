A scrape job's sample limit is enforced by a wrapper appender, `limitAppender`. It counts the samples appended during one scrape and returns `errSampleLimit` once the count passes the limit.

- **Wiring:** `appenderWithLimits` (`scrape/scrape.go:711`) wraps the storage appender when `sampleLimit > 0` (`scrape/scrape.go:718`). A comment there says the limit is applied after relabeling may have dropped metrics. `scrapeLoop` builds it from `sl.sampleLimit` (`scrape/scrape.go:1827`). The V2 append path does the same through `appenderV2WithLimits` (`scrape/scrape_append_v2.go:37,44,140`).
- **Counting:** `limitAppender` (`scrape/target.go:376-381`) has a counter `i` and a `limit`. `Append` and `AppendHistogram` increment `i`, and when `i > limit` they return `0, errSampleLimit` without writing (`scrape/target.go:391`, `407`). The error is defined at `scrape/target.go:373` as "sample limit exceeded".
- **Staleness markers:** These are exempt when the series is already known (`ref != 0`). The check is `ref == 0 || !value.IsStaleNaN(v)`, and the comment says a series already in TSDB always gets its marker written.
- **Handling the error:** `checkAddError` (`scrape/scrape.go:2163-2167`) catches `errSampleLimit`, stores it in `sampleLimitErr`, and returns `false, nil`. Parsing carries on so the total number of scraped samples is still reported. After the loop, `sampleLimitErr` becomes the scrape error if no other error occurred. `targetScrapeSampleLimit` is incremented once per scrape (`scrape/scrape.go:2055-2060`). The V2 path does the same (`scrape/scrape_append_v2.go:374-379`).
- **Reporting:** The configured limit is exposed as the `scrape_sample_limit` report series (`scrape/scrape.go:2272,2320`).

Uncertainty: I did not read the code that rolls back or commits the appender after the error. So I can't say from what I saw whether the samples appended before the limit was hit are discarded. I also did not read the config-side plumbing that sets `sampleLimit` per job, or the second page of search matches.
