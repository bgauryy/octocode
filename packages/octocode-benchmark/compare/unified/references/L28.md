# L28 reference
## Question
redis/redis issue #15874 reports that ARLASTITEMS can leave existing elements out of its reply. In redis/redis at commit 20bb2cfc54, where is the code that causes this, why does it drop elements, and how did the fix change the command's behavior?

## Key facts (graded)
1. Location: `arlastitemsCommand` in `src/t_array.c:1802` (local checkout at 20bb2cfc54). Its comment says it walks positions, not only existing items, and may return NULLs (`t_array.c:1795-1801`).
2. Cause: the walk length is capped by the number of existing elements, not positions: `uint64_t effective_count = (uint64_t)count > ar->count ? ar->count : (uint64_t)count;` (`t_array.c:1837-1838`). The loop walks backward from the anchor (`insert_idx`, or `ar_len - 1` when it is `AR_INSERT_IDX_NONE`) for `effective_count` steps, collecting `arGet(...)` for each position, holes included (`t_array.c:1855-1870`). Each hole uses one step, so when the walk crosses a hole it stops before the oldest existing elements, which are silently left out (issue example: `ARINSERT log a b c d e`, `ARDEL log 1`, `ARLASTITEMS log 10` returns `nil c d e` without `a`).
3. Fix: PR #15875 ("Fixes #15874"), merged as `790d459f0970ac6eedf1cbe808a45d8460475610` (descendant of 20bb2cfc54), changes `src/t_array.c` (+18 −6) and adds tests in `tests/unit/type/array.tcl`. — evidence: https://github.com/redis/redis/pull/15875
4. Behavior after the fix (PR body):
   - the walk is capped by `arLen(ar)`, so the reply has `min(count, arLen)` positions with NULL for holes;
   - `ARGETRANGE_MAX_ITEMS` (`t_array.c:45`, 1,000,000) is renamed `AR_MAX_REPLY_ITEMS` and also applied to ARLASTITEMS: the command replies with an error when the walked positions exceed both that limit and the number of existing elements;
   - the walk starts from the last existing element when the insert cursor is past it (for example after deleting the last inserted element), so `ARLASTITEMS` returns `a b c d` instead of `b c d (nil)` in that case.

## Acceptable variations
- Line numbers ±3.
- Explaining the cause as "count is bounded by `ar->count` (populated items) instead of the array length".
- Short SHA `790d459`.

## Common wrong answers
- Blaming the reply-emission loop, the `REV` handling, or `arGet`.
- Saying the fix simply removes the cap (it caps by `arLen` and adds the hard limit).
- Pointing at ARGETRANGE's code as the bug site.
