# L04 reference
## Question
In langchain-ai/langchain at commit 67ee6cb63d, how does LangChain core's tool decorator build a tool's argument schema and description from a plain function when docstring parsing is enabled?

## Key facts (graded)
1. Chain: `@tool(parse_docstring=True)` returns `_partial` (`libs/core/langchain_core/tools/convert.py:398-404`) → `_create_tool_factory(name)` → `_tool_factory` (convert.py:270-349), which for a non-coroutine function sets `func = dec_func` (311-314) and, since `infer_schema` defaults True, calls `StructuredTool.from_function(...)` (convert.py:316-329) → `create_schema_from_function(...)` (`libs/core/langchain_core/tools/structured.py:258-266`) → `create_schema_from_function` in `libs/core/langchain_core/tools/base.py:263`, which builds a model via pydantic `validate_arguments` (base.py:292-303) and finally `_create_subset_model(...)` (base.py:362-368; `libs/core/langchain_core/utils/pydantic.py:284`).
2. Excluded params: `from_function` passes `filter_args=_filter_schema_args(source_function)` (structured.py:265), which is `FILTERED_ARGS` = `("run_manager", "callbacks")` (base.py:74) plus any parameter annotated as RunnableConfig (structured.py:317-322); `create_schema_from_function` keeps only fields not in that list (base.py:359-360) and also drops pydantic's placeholder `args`/`kwargs` (unless the function has *args/**kwargs) and `v__duplicate_kwargs` (base.py:351-357).
3. Descriptions: `_infer_arg_descriptions` (base.py:170-201) reads `get_type_hints(fn, include_extras=True)`; with parse_docstring it calls `_parse_python_function_docstring` (base.py:126-149) → `_parse_google_docstring` (`libs/core/langchain_core/utils/function_calling.py:735`), then validates that every documented arg exists in the annotations (`_validate_docstring_args_against_annotations`, base.py:152-167, raising "Arg {x} in docstring not found in function signature.").
4. Precedence: annotation-derived descriptions (`_get_annotation_description`) are only added for args NOT already described by the docstring (`if arg in arg_descriptions: continue`, base.py:196-200) — the docstring wins. `_create_subset_model_v2` then prefers these descriptions over the field's own (`descriptions_.get(field_name, field.description)`, utils/pydantic.py:247).
5. Tool description: the parsed summary (docstring blocks before `Args:`, skipping after `Returns:`/`Example:`) is passed as `fn_description` and stored as the model's `__doc__` (utils/pydantic.py:276). In `from_function`, because `parse_docstring` is True the raw `__doc__` is skipped (structured.py:268-269) and the description comes from `args_schema.__doc__` (structured.py:270-272), then dedented/stripped (291-297).
6. Errors: only when `error_on_invalid_docstring=True`, `_parse_google_docstring` raises `ValueError("Found invalid Google-Style docstring.")` if there are args other than run_manager/callbacks/runtime/return and the docstring has fewer than `_MIN_DOCSTRING_BLOCKS` (=2, function_calling.py:732) blank-line-separated blocks or no later block starting with `Args:` (function_calling.py:756-767), or if the docstring is empty (784-786). The doc-arg-vs-signature ValueError (fact 3) applies whenever parse_docstring=True.
## Acceptable variations
- Omitting the `_partial` wrapper step, or describing `@tool` without args going through `_create_tool_factory(name_or_callable.__name__)` (convert.py:370-375), is fine as long as `from_function` → `create_schema_from_function` is named.
- Not mentioning pydantic v1 branch (`_function_annotations_are_pydantic_v1`, base.py:221-250 / `validate_arguments_v1`).
- Mentioning `include_injected` / injected-arg filtering (base.py:331-341) is a bonus.
- Line ranges ±2.
## Common wrong answers
- Claiming `self`/`cls` stripping (base.py:324-329) applies on this path — it does not, because `from_function` always passes a non-empty `filter_args`.
- Claiming annotation (`Annotated[..., "desc"]`) descriptions override docstring descriptions.
- Claiming the tool description is the raw full docstring (including the Args section) in parse_docstring mode.
- Claiming invalid docstrings always raise (they only raise with error_on_invalid_docstring=True, except the unknown-arg check).
- Placing schema inference in `BaseTool.args_schema` / `tool_call_schema` instead of `create_schema_from_function`.
