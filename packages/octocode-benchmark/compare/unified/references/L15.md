# L15 reference
## Question
In google/guava at commit 4d41665af1, how do Guava's immutable hash sets defend against many elements with colliding hash codes?

## Key facts (graded)
1. Online check during insertion: `RegularSetBuilderImpl.insertInHashTable` linearly probes from `Hashing.smear(hashCode)` only while `i - i0 < maxRunBeforeFallback`; if it falls out of the loop without finding an empty slot or an equal element (a probe run of length `maxRunBeforeFallback`), it returns `new JdkBackedSetBuilderImpl<E>(this).add(e)`. — evidence: `guava/src/com/google/common/collect/ImmutableSet.java:706-726` (loop condition at 711, fallback at 724-725)
2. Whole-table check at finalization: `Builder.build()` sets `forceCopy = true`, calls `impl = impl.review()` then `impl.build()`; `RegularSetBuilderImpl.review()` optionally shrinks/rebuilds the table (if `chooseTableSize(distinct) * 2 < hashTable.length`) and returns `hashFloodingDetected(hashTable) ? new JdkBackedSetBuilderImpl<E>(this) : this`. `hashFloodingDetected` scans for any run of `maxRunBeforeFallback` consecutive non-null slots (wrapping around), catching adversarial codes that go to ascending locations which the online check cannot. — evidence: `ImmutableSet.java:517-523`, `ImmutableSet.java:733-745`, `ImmutableSet.java:835-871` (Javadoc 817-834)
3. Threshold: `maxRunBeforeFallback(tableSize) = MAX_RUN_MULTIPLIER * IntMath.log2(tableSize, RoundingMode.UNNECESSARY)` with `MAX_RUN_MULTIPLIER = 13`; recomputed whenever the table is created/expanded (`ensureTableCapacity`) or shrunk in `review()`. — evidence: `ImmutableSet.java:815`, `ImmutableSet.java:878-880`, `ImmutableSet.java:741`, `ImmutableSet.java:803`
4. Fallback: `JdkBackedSetBuilderImpl` copies the deduped elements into a `java.util` HashSet (`newHashSetWithExpectedSize(distinct)`, "built in hash flooding protection") and dedups via `delegate.add(e)`; its `build()` returns `new JdkBackedImmutableSet<>(delegate, asImmutableList(dedupedElements, distinct))` for ≥2 elements, instead of `RegularImmutableSet` (which `RegularSetBuilderImpl.build()` would create). — evidence: `ImmutableSet.java:883-929` (build at 927), `ImmutableSet.java:768`
## Acceptable variations
- Line numbers ±3.
- Also mentioning that `ImmutableSet.of(...)` (lines 111-159) and `fromArrayWithExpectedSize`/`copyOf` (line 277) call `builder.review().build()` directly is correct extra detail.
- Describing the check as "detects probe runs longer than 13·log2(table size)" is equivalent.
- Mentioning `SetBuilderImpl.review()` default no-op (`ImmutableSet.java:592-594`) or `Builder.forceJdk()` (test hook, line 443-447) is fine.
## Common wrong answers
- Citing `RegularImmutableMultiset.hashFloodingDetected` or `RegularImmutableMap`'s bucket-length check (`MAX_HASH_BUCKET_LENGTH`) as the ImmutableSet mechanism — those are separate implementations for other collections.
- Claiming the threshold is a fixed constant (e.g. 13 probes) rather than 13 × log2(tableSize).
- Claiming the Android flavor (`android/guava/...ImmutableSet.java`) has this logic — it does not contain `hashFloodingDetected`.
- Saying the fallback produces a `RegularImmutableSet` with a rebuilt table, or throws an exception.
