# L08 reference
## Question
In prometheus/prometheus at commit ea954809ce, how is a scrape job's sample limit enforced?

## Key facts (graded)
1. Declaration + inheritance: `ScrapeConfig.SampleLimit uint` with YAML key `sample_limit` (also on `GlobalConfig`); when the job's value is 0 it is filled from the global value during validation. — evidence: `config/config.go:827` (ScrapeConfig field), `config/config.go:510` (GlobalConfig field), `config/config.go:938-939` (`if c.SampleLimit == 0 { c.SampleLimit = globalConfig.SampleLimit }`)
2. Copy onto per-target state: `newScrapeLoop` sets `sampleLimit: int(opts.sp.config.SampleLimit)` on the `scrapeLoop` (field `sampleLimit int` "Options from config.ScrapeConfig"); the scrape pool's `config` comes from `newScrapePool`/`reload`. — evidence: `scrape/scrape.go:1349`, `scrape/scrape.go:962`, `scrape/scrape.go:1307` (newScrapeLoop), `scrape/scrape.go:182`, `scrape/scrape.go:335`
3. Installed per scrape: each `append` call wraps the storage appender via `appenderWithLimits(sl.Appender, sl.sampleLimit, ...)`, which adds a `limitAppender` only `if sampleLimit > 0` (0 = no limit; comment says the limit applies after metric relabeling). The AppenderV2 path mirrors it (`appenderV2WithLimits` → `limitAppenderV2`). — evidence: `scrape/scrape.go:1827`, `scrape/scrape.go:711-722`; V2: `scrape/scrape_append_v2.go:140`, `scrape/scrape_append_v2.go:37-49`
4. Counting rule: `limitAppender.Append` increments its counter and returns `errSampleLimit` ("sample limit exceeded") once `app.i > app.limit`; staleness markers (StaleNaN) for already-known series (`ref != 0`) are exempt, so a marker for a series already in TSDB is always written. Same in `AppendHistogram` and `limitAppenderV2.Append`. — evidence: `scrape/target.go:373`, `scrape/target.go:385-397` (check at 388-391), `scrape/target.go:401-407`, `scrape/target.go:516-523`
5. On exceed, parsing continues: `checkAddError` treats `errSampleLimit` by storing it in `sampleLimitErr` and returning `(false, nil)` so the loop keeps parsing to report correct totals; after the loop `err = sampleLimitErr` and `targetScrapeSampleLimit` (prometheus_target_scrapes_exceeded_sample_limit_total) is incremented once per scrape. — evidence: `scrape/scrape.go:2159-2166`, `scrape/scrape.go:2055-2061`; V2: `scrape/scrape_append_v2.go:374-379`
6. Rollback + stale markers: in `scrapeAndReport`, a non-nil append error causes `app.Rollback()` (discarding that scrape's appended samples), a fresh appender, and a second `append` with an empty body to trigger stale markers; the append error becomes the scrape error. — evidence: `scrape/scrape.go:1613-1633` (Rollback at 1620, empty re-append at 1625, `scrapeErr = appErr` at 1632-1633)

## Acceptable variations
- Citing either the v1 (`scrapeLoopAppender.append`, `scrape/scrape.go:1778`) or the V2 (`scrapeLoopAppenderV2.append`, `scrape/scrape_append_v2.go:91`) path is fine; both are equivalent.
- Mentioning the `scrape_sample_limit` report series (value = configured limit) at `scrape/scrape.go:2272`, `2320` is a bonus, not required.
- Metric name may be given as the Go field `targetScrapeSampleLimit` (`scrape/metrics.go:52`, `214`).
- ±2 line tolerance on multi-line blocks.

## Common wrong answers
- Claiming parsing stops immediately at the first over-limit sample (it continues; only the error is recorded).
- Confusing this with the remote-read sample limit (`storage/remote/codec.go`, `--storage.remote.read-sample-limit`) or with `target_limit`/`label_limit`.
- Claiming samples below the limit are kept (the whole scrape's appender is rolled back).
- Saying staleness markers count against the limit without the `ref != 0` qualification.
