# G04 reference
## Question
What does pallets/click PR #3866 deprecate, and which parameter declarations now produce a warning?

## Key facts (graded)
1. `Parameter._check_name_is_usable` emits a `DeprecationWarning` when the final name is a Python keyword (`keyword.iskeyword`, e.g. `--from`, `--import`, argument `class`) or is not a valid identifier (`str.isidentifier`, e.g. argument `0foo`, `foo.bar`, `foo bar`, `""`); message: "`<Param type> [decls] uses 'name' as its name, <reason>. This is deprecated and will raise a TypeError in Click 9.0.`" — evidence: `src/click/core.py:2482-2517`; called from Option at `:3418` and Argument at `:3880`
2. Not warned: soft keywords (`match`, `type`) because `keyword.iskeyword` excludes them; hyphenated/mixed-case derived names (`Argument(["foo-bar"])`, `Argument(["Foo_Bar"])`, `--foo-bar`) because names are `replace("-", "_").lower()`-normalized before the check; `--True`/`--None` lower-case to non-keywords; and an explicit valid name overriding a bad flag (`Option(["--0foo", "zero_foo"])`). — evidence: `src/click/core.py:3392-3393,3872-3873`, `tests/test_deprecations.py` (`test_usable_name_not_deprecated`)
3. For `Option`, `_parse_decls` now records `explicit_name` when a decl is an identifier; if it is not already lower-case, `_check_name_is_normalized` warns (`DeprecationWarning`) that Click 9.0 will lower-case an explicit name like any other declaration and name it `name.lower()` instead. Derived names (from `--Foo-Bar`) are already lower-cased and never trigger it; the name is still kept as given in 8.x. — evidence: `src/click/core.py:3335-3353,3361,3368,3415-3416`
4. Unexposed params: `Option` with no derivable name or a non-identifier derived name (`name is None or not name.isidentifier()`) and `expose_value=False` now warns via `_check_name_is_usable(name or "", decls)` before returning `""`; `Argument` with no decls and `expose_value=False` warns with `""`. So even `click.Option([], expose_value=False)` / `click.Argument([], expose_value=False)` emit a DeprecationWarning ("not a valid Python identifier"). Exposed params with no usable name still raise `TypeError` as before. — evidence: `src/click/core.py:3395-3404,3865-3869`
5. The warning uses `stacklevel=_outside_click_stacklevel()`, a new helper that walks `sys._getframe` frames until the first one whose module `__name__` is neither `click` nor starts with `click.`, so the warning points at user code. — evidence: `src/click/core.py:108-125`, used at `:2515` and `:3352`
6. Nothing that worked before now raises: only warnings were added (the name-None / non-identifier branches were merged into one condition with identical TypeError behavior for exposed params); CHANGES lists this under Version 8.6.0 and pyproject bumps to `8.6.0.dev`. — evidence: `src/click/core.py:3395-3404`, `CHANGES.md:1-8`, `pyproject.toml:3`
## Acceptable variations
- Line numbers ±3.
- Exact message wording can be paraphrased if the "TypeError in Click 9.0" consequence is stated.
- Mentioning that tests in `tests/test_arguments.py`/`tests/test_options.py` freeze current naming behavior is a bonus.
## Common wrong answers
- Claiming keyword names like `--from` now raise `TypeError` (they only warn in 8.6).
- Claiming soft keywords (`match`, `type`) warn.
- Claiming `--Foo-Bar` (derived, not explicit) triggers the lower-case warning.
- Claiming the warning uses a fixed `stacklevel=2`.
