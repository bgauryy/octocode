# L21 reference
## Question
In tokio-rs/tokio at commit facc6fc47e, the blocking thread pool has several functions named `begin_shutdown`. When the pool shuts down, which of them run and in what order, and what does each one do beyond the one it calls?

## Key facts (graded)
1. Entry: `BlockingPool::shutdown(&mut self, timeout)` calls `inner.inner_impl.begin_shutdown(&inner.metrics)` and returns early on `None` (shutdown already started; `shutdown` also runs from `Drop for BlockingPool`). — evidence: `tokio/src/runtime/blocking/pool.rs:314-322`, `pool.rs:343-346`
2. Dispatcher: `InnerImpl::begin_shutdown(&self, metrics)` matches the implementation: `Locked(l) => l.begin_shutdown()`, `Sharded(s) => s.begin_shutdown(metrics)`. Which variant exists is chosen in `BlockingPool::new` from `builder.sharded_blocking_queue` (default off; on through `TOKIO_UNSTABLE_SHARDED_BLOCKING_QUEUE` or `enable_sharded_blocking_queue`). — evidence: `pool.rs:576-581`, `pool.rs:286-290`, `tokio/src/runtime/builder.rs:250-258`
3. Locked path: `LockedImpl::begin_shutdown(&self)` locks the mutex, calls `locked.thread_mgmt_state.begin_shutdown()?`, then `self.condvar.notify_all()` to wake idle workers, and returns the handles. — evidence: `pool.rs:740-745`
4. Sharded path: `ShardedImpl::begin_shutdown(&self, metrics)` locks `coord`, calls `coord.thread_mgmt_state.begin_shutdown()?`, stores `is_shutdown = true` (Release), `condvar.notify_all()`, and if `metrics.num_threads() == 0` calls `self.drain_and_seal(metrics, 0)` after dropping the lock, so a racing spawner's push cannot be stranded. — evidence: `tokio/src/runtime/blocking/sharded.rs:336-352`
5. Innermost: `ThreadManagementState::begin_shutdown(&mut self)` returns `None` if `shutdown` is already set; otherwise sets `shutdown = true`, drops `shutdown_tx` (sets it to `None`), and takes `last_exiting_thread` and `worker_threads` to return them as `ShutdownHandles`. Its doc says the caller must wake waiting workers. — evidence: `pool.rs:152-166`
6. Order: `BlockingPool::shutdown` → `InnerImpl::begin_shutdown` → (`LockedImpl::begin_shutdown` or `ShardedImpl::begin_shutdown`) → `ThreadManagementState::begin_shutdown`; afterwards `shutdown` waits on `shutdown_rx` (with the timeout) and joins the returned threads. The only callers of `ThreadManagementState::begin_shutdown` are `pool.rs:742` and `sharded.rs:338`; the only caller of `InnerImpl::begin_shutdown` is `pool.rs:319`. — evidence: `pool.rs:324-340`

## Acceptable variations
- Line numbers ±2.
- Describing `drain_and_seal` as "seals the shards" without its internals.
- Noting that only one of the two middle functions runs for a given pool.

## Common wrong answers
- Treating the four functions as one, or claiming both the Locked and Sharded versions run.
- Saying the innermost function wakes workers (the wrappers do, through `notify_all`).
- Confusing these with runtime/scheduler shutdown functions (`Handle::shutdown`, `Core::shutdown`) or with `Shutdown`'s `shutdown()` in `blocking/shutdown.rs`.
