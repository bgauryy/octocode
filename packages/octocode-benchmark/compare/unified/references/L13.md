# L13 reference
## Question
In redis/redis at commit 20bb2cfc54, what happens when a client runs GET on a string key whose TTL has already expired?

## Key facts (graded)
1. Dispatch: `processCommand` resolves the command (`lookupCommand`) and, outside MULTI, calls `call(c, CMD_CALL_FULL)`; `call` invokes `c->cmd->proc(c)`, which for GET is `getCommand` (command table entry) → `getGenericCommand`. — evidence: `src/server.c:4660`, `src/server.c:4703`, `src/server.c:5036-5037`, `src/server.c:4151`, `src/server.c:4235`, `src/commands.def:13208`, `src/t_string.c:470-472`, `src/t_string.c:456-467`
2. Lookup chain: `getGenericCommand` → `lookupKeyReadOrReply(c, key, shared.null[c->resp])` → `lookupKeyRead` → `lookupKeyReadWithFlags(db,key,LOOKUP_NONE)` → `lookupKey(db, key, flags, NULL)`, which calls `expireIfNeeded(db, key, val, expire_flags)` (expire_flags 0 for a read without LOOKUP_WRITE). — evidence: `src/t_string.c:459`, `src/db.c:402-406`, `src/db.c:373-375`, `src/db.c:366-369`, `src/db.c:296`, `src/db.c:305-319`
3. Expiry + delete decision: `expireIfNeeded` uses `keyIsExpired` (`now > when`, using `commandTimeSnapshot()`; never expired while loading); on a replica (`server.masterhost != NULL`) without `EXPIRE_FORCE_DELETE_EXPIRED` it returns `KEY_EXPIRED` without deleting (and treats the key as valid when the current client is the master link); also skips deletion when `confAllowsExpireDel()` forbids it, with `EXPIRE_AVOID_DELETE_EXPIRED`, or when expire actions are paused; otherwise it calls `deleteExpiredKeyAndPropagate` and returns `KEY_DELETED`. — evidence: `src/db.c:3004`, `src/db.c:3021-3023`, `src/db.c:2946-2955`, `src/db.c:3043-3046`, `src/db.c:3050-3061`, `src/db.c:3063-3071`
4. Deletion step: `deleteExpiredKeyAndPropagate` → `deleteKeyAndPropagate(db, key, NOTIFY_EXPIRED, NULL)`: `dbGenericDelete` with `lazy_flag = server.lazyfree_lazy_expire`, keyspace event "expired", `keyModified`, `propagateDeletion(db, keyobj, lazy_flag)`, and `server.stat_expiredkeys++`. `propagateDeletion` builds `UNLINK` if lazy (lazyfree-lazy-expire yes) else `DEL`, and queues it with `alsoPropagateForced(...PROPAGATE_AOF|PROPAGATE_REPL)` into `server.also_propagate`. — evidence: `src/db.c:2898-2900`, `src/db.c:2847-2895` (2850, 2879, 2884-2886, 2889), `src/db.c:2926-2940` (2929, 2936), `src/server.c:3865-3870`, `src/server.c:3853`, `src/config.c:3458`
5. Client reply: `lookupKey` gets a non-VALID status, sets `val = NULL`, fires the "keymiss" keyspace event and increments `stat_keyspace_misses`; `lookupKeyReadOrReply` replies with the supplied `shared.null[c->resp]` (RESP2 null bulk / RESP3 null). — evidence: `src/db.c:319-322`, `src/db.c:346-351`, `src/db.c:403-404`, `src/t_string.c:459`
6. Flush: the DEL/UNLINK is only queued during the command; at the end of `call()`, `afterCommandEx` → `postExecutionUnitOperationsEx` (returns early while `execution_nesting` is nonzero) → `propagatePendingCommands`, which sends each queued op with `propagateNow` (wrapped in MULTI/EXEC only if more than one op). — evidence: `src/server.c:4411`, `src/server.c:4497-4510`, `src/server.c:4060-4068`, `src/server.c:3993-4045` (4005-4006, 4034)

## Acceptable variations
- Entry via `processCommandAndResetClient` (`src/networking.c:3652-3656`) as the caller of `processCommand` is fine.
- Describing the active-expire cycle as an alternative path is fine but not required; it is not what GET triggers.
- Line tolerance ±2; ranges may be cited by function start line.

## Common wrong answers
- Claiming the replica deletes the expired key on read (it only reports it as missing unless forced by a write lookup).
- Claiming the propagated command is always `DEL` (it's `UNLINK` when lazyfree-lazy-expire is enabled).
- Claiming the propagated command is written to AOF/replicas immediately inside `propagateDeletion`.
- Claiming GET is replicated (GET itself is not; only the synthesized deletion).
- Confusing with the active expiry cycle in `src/expire.c`.
