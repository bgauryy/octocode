# L11 reference
## Question
In tokio-rs/tokio at commit facc6fc47e, how does a spawned task's output get from the task to whoever awaits its `JoinHandle`?

## Key facts (graded)
1. Capture: `poll_future` polls the future inside `catch_unwind`; `Poll::Ready(output)` becomes `Ok(output)`, a panic becomes `Err(panic_to_error(...))` (a `JoinError`), and the result is written with `core.store_output(output)`. Called from `Harness::poll_inner`. — evidence: `tokio/src/runtime/task/harness.rs:523-559` (546 panic mapping, 551 store_output), `tokio/src/runtime/task/harness.rs:210`
2. Storage: the task core's `Stage<T>` enum (`Running(T)` / `Finished(super::Result<T::Output>)` / `Consumed`); `store_output` sets `Stage::Finished(output)` via `set_stage`. — evidence: `tokio/src/runtime/task/core.rs:225-229`, `tokio/src/runtime/task/core.rs:408-413`, `tokio/src/runtime/task/core.rs:432-435`
3. Completion: `Harness::complete` does `transition_to_complete()` (RUNNING→COMPLETE); if the snapshot is not join-interested the runtime drops the output itself (`drop_future_or_output`, which sets `Stage::Consumed`); otherwise, if a join waker is set it calls `trailer().wake_join()` and then unsets JOIN_WAKER. — evidence: `tokio/src/runtime/task/harness.rs:331-365` (334, 339-344, 345-349), `tokio/src/runtime/task/state.rs:184-192`, `tokio/src/runtime/task/core.rs:396-401`
4. Handle side: `JoinHandle::poll` first consumes cooperative budget (`coop::poll_proceed`), then calls `self.raw.try_read_output(&mut ret, cx.waker())`; `RawTask::try_read_output` dispatches through the header vtable (type-erased `*mut ()` dst) to the monomorphized `raw::try_read_output`, which calls `Harness::try_read_output`. — evidence: `tokio/src/runtime/task/join.rs:327-354` (332, 346), `tokio/src/runtime/task/raw.rs:290-293`, `tokio/src/runtime/task/raw.rs:360-369`, `tokio/src/runtime/task/harness.rs:281-285`
5. Not-yet-complete: `can_read_output` checks the state snapshot; if not complete it stores (or swaps) the caller's waker as the join waker and returns false, so the handle returns `Poll::Pending` and is woken later by `wake_join`. — evidence: `tokio/src/runtime/task/harness.rs:422-464`
6. Take: when complete, `*dst = Poll::Ready(self.core().take_output())`; `take_output` `mem::replace`s the stage with `Stage::Consumed` and returns the `Finished` payload, panicking with "JoinHandle polled after completion" if the stage was not `Finished`. — evidence: `tokio/src/runtime/task/harness.rs:283`, `tokio/src/runtime/task/core.rs:420-430`

## Acceptable variations
- Cancellation path (`cancel_task` storing `Err(JoinError::cancelled)`, `tokio/src/runtime/task/harness.rs:502-509`) is a valid additional mention.
- `drop_join_handle_slow` dropping the output when the handle is dropped (`tokio/src/runtime/task/harness.rs:287-304`) is a bonus.
- Line tolerance ±2 on block ranges.

## Common wrong answers
- Claiming the output is sent over a oneshot channel.
- Claiming the output is kept inside the JoinHandle struct itself.
- Omitting the vtable/type-erasure hop or saying `JoinHandle` reads the `Core` directly.
- Saying the runtime always wakes the handle, regardless of JOIN_INTEREST / JOIN_WAKER.
