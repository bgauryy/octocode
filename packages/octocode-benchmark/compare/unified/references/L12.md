# L12 reference
## Question
In tokio-rs/tokio at commit facc6fc47e, the multi-threaded scheduler sometimes runs a task woken by the currently running task next on the same worker. How does that optimization work, and what limits it?

## Key facts (graded)
1. Decision point: `Handle::schedule_task` (reached via `Schedule::schedule` with `is_yield=false`, and `yield_now` with `is_yield=true`) calls `schedule_local` when on a worker of the same runtime that holds its core; otherwise the task goes to the inject (global) queue. In `schedule_local`, if `is_yield || !core.lifo_enabled` the task is pushed to the back of the local run queue; else it is placed in `core.lifo_slot`, with any previous occupant moved to the run queue. — evidence: `tokio/src/runtime/scheduler/multi_thread/worker.rs:1353-1376` (1366, 1373), `tokio/src/runtime/scheduler/multi_thread/worker.rs:1385-1417` (1392-1406), `tokio/src/runtime/scheduler/multi_thread/handle.rs:112-124`
2. Running the slot: in `Context::run_task`, inside `coop::budget(...)`, after the task runs the worker loops taking `core.lifo_slot` and running it directly on the same budget. — evidence: `tokio/src/runtime/scheduler/multi_thread/worker.rs:647`, `tokio/src/runtime/scheduler/multi_thread/worker.rs:695-796` (take at 727)
3. Cap: `MAX_LIFO_POLLS_PER_TICK = 3`; each LIFO run increments `lifo_polls` and when it reaches 3 `core.lifo_enabled = false` (to avoid ping-pong starvation), so further wakes go to the back of the queue. — evidence: `tokio/src/runtime/scheduler/multi_thread/worker.rs:269`, `tokio/src/runtime/scheduler/multi_thread/worker.rs:753-766`
4. Re-enable: `reset_lifo_enabled` sets `lifo_enabled = !config.disable_lifo_slot`; called when the LIFO slot is found empty at the end of `run_task` and at the top of `Context::run` (in case the core was stolen). — evidence: `tokio/src/runtime/scheduler/multi_thread/worker.rs:798-800`, `tokio/src/runtime/scheduler/multi_thread/worker.rs:727-733` (730), `tokio/src/runtime/scheduler/multi_thread/worker.rs:571-573`
5. Budget exhausted: if `!coop::has_budget_remaining()` the LIFO task is not run; it is pushed to the back of the local run queue (`push_back_or_overflow`) and `run_task` returns. The per-task budget is 128 (`Budget::initial`). — evidence: `tokio/src/runtime/scheduler/multi_thread/worker.rs:736-749`, `tokio/src/task/coop/mod.rs:115-116`, `tokio/src/task/coop/mod.rs:223-226`
6. Disabling: `Builder::disable_lifo_slot()` (an unstable, `cfg_unstable!`-gated option) sets `self.disable_lifo_slot = true`; `build_threaded_runtime` copies it into the runtime `Config` (`disable_lifo_slot: bool`), and each worker `Core` is created with `lifo_enabled: !config.disable_lifo_slot`. — evidence: `tokio/src/runtime/builder.rs:1425-1428` (inside `cfg_unstable!` at 1314-1462), `tokio/src/runtime/builder.rs:2217`, `tokio/src/runtime/config.rs:42`, `tokio/src/runtime/scheduler/multi_thread/worker.rs:298`

## Acceptable variations
- Calling it the "LIFO slot" / "next task" optimization is fine.
- `Core::next_local_task` taking the LIFO slot before the run queue (`worker.rs:1158-1160`) is a valid extra detail.
- The current-thread builder also copies the field (`builder.rs:1794`) but has no LIFO slot; mentioning this is fine.
- Line tolerance ±2.

## Common wrong answers
- Claiming the cap is based on time or on the global queue interval (`global_queue_interval` is a different fairness mechanism).
- Saying yielded tasks (`yield_now`) use the LIFO slot (they always go to the back).
- Claiming the LIFO slot can be stolen by other workers (it can't; that's why it exists as an option to disable).
- Saying the budget-exhausted LIFO task is dropped or sent to the global inject queue (it goes to the local run queue, which may overflow to inject).
