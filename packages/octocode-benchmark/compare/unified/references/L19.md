# L19 reference
## Question
In microsoft/TypeScript at commit 4f5ddae224, how does the `moduleDetection` compiler option decide whether a file is treated as a module or a script in the Go-based compiler?

## Key facts (graded)
1. Option parsing: `moduleDetection` is declared as an enum option with `AffectsSourceFile: true` (and `AffectsModuleResolution`), values `auto`/`legacy`/`force` map to `core.ModuleDetectionKindAuto/Legacy/Force`, and it is stored in `allOptions.ModuleDetection`. Effective mode: `CompilerOptions.GetEmitModuleDetectionKind()` returns the explicit value if not `None`; otherwise `Force` when the emit module kind is between `Node16` and `NodeNext` (100–199, i.e. node16/node18/node20/nodenext), else `Auto`. — evidence: `tsc/internal/tsoptions/declscompiler.go:1195-1203`, `tsc/internal/tsoptions/enummaps.go:188-192`, `tsc/internal/tsoptions/parsinghelpers.go:411-412`, `tsc/internal/core/compileroptions.go:243-252`
2. Per-file wiring: `fileLoader.parseSourceFile` gets the file's options via `projectReferenceFileMapper.getCompilerOptionsForFile(t)` and sets `SourceFileParseOptions.ExternalModuleIndicatorOptions = ast.GetExternalModuleIndicatorOptions(t.normalizedFilePath, options, t.metadata)`, which flows through `Host.GetSourceFile` → `parser.ParseSourceFile`. — evidence: `tsc/internal/compiler/fileloader.go:413-428` (call at 422), `tsc/internal/compiler/host.go:97`, `tsc/internal/parser/parser.go:135`
3. Mode semantics in `GetExternalModuleIndicatorOptions`: declaration file names (`.d.ts` etc.) → empty options regardless of mode; `Force` → `{Force: true}`; `Legacy` → `{}` (only imports/exports/import.meta); `Auto` → `JSX` true when `jsx` is `react-jsx`/`react-jsxdev`, and `Force` true when `isFileForcedToBeModuleByFormat` — implied node format for emit is ESNext (ESM) or the extension is `.cjs/.cts/.mjs/.mts`. — evidence: `tsc/internal/ast/parseoptions.go:19-42`, `parseoptions.go:44-54`
4. Storage/order: `Parser.finishSourceFile` calls `ast.SetExternalModuleIndicator(result, p.opts.ExternalModuleIndicatorOptions)`, which sets `file.ExternalModuleIndicator = getExternalModuleIndicator(...)`: JSON script kind → nil; first statement with export modifier / import-equals with external reference / import / export assignment / export declaration, or an `import.meta` → that node; declaration file → nil; if `opts.JSX`, a JSX tag node; if `opts.Force` → the source file node itself; else nil. — evidence: `tsc/internal/parser/parser.go:466`, `parser.go:486`, `tsc/internal/ast/parseoptions.go:56-84`, `parseoptions.go:86-99`
5. Predicate: `ast.IsExternalModule(file)` returns `file.ExternalModuleIndicator != nil` (some callers also test the field directly, e.g. checker isolatedModules check). — evidence: `tsc/internal/ast/utilities.go:1686-1688`, `tsc/internal/checker/checker.go:5263`
## Acceptable variations
- Line numbers ±3; paths may be given relative to `tsc/` (e.g. `internal/ast/parseoptions.go`).
- Mentioning the `moduleDetectionKind` alias case (`parsinghelpers.go:405-406`), `tsc --init` emitting `moduleDetection: force` (`tsc/internal/execute/tsc/init.go:199`), or the language-service auto-import use (`tsc/internal/ls/autoimport/fix.go:915`) is fine extra.
- Describing auto as "ESM-format files under node16+/nodenext plus .mjs/.cjs/.mts/.cts are modules" is equivalent.
## Common wrong answers
- Describing the old TypeScript (JS) implementation (`src/compiler/utilities.ts getSetExternalModuleIndicator`, `program.ts`) — those files do not exist in this checkout.
- Saying `force` makes `.d.ts` files modules (declaration files always get empty options and still need explicit import/export).
- Saying the default mode is `legacy`, or that the Node16..NodeNext default is `auto`.
- Claiming the checker/binder computes module-ness (it is fixed at parse time).
