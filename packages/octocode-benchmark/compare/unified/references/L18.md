# L18 reference
## Question
In nlohmann/json at commit f422b753cc, how does parsing with a parser callback that rejects some elements produce the resulting JSON value?

## Key facts (graded)
1. `parser::parse(strict, result)` constructs `json_sax_dom_callback_parser` (passing the callback) when `callback` is set, otherwise the plain `json_sax_dom_parser`, and drives it with `sax_parse_internal(&sdp)`. — evidence: `include/nlohmann/detail/input/parser.hpp:96-101`, `parser.hpp:135-138`
2. `key()`: calls the callback with `parse_event_t::key` at depth `ref_stack.size()`, pushes the result on `key_keep_stack` and the key on `key_stack`; if kept and the parent exists it writes a `discarded` placeholder `obj[val] = discarded` and remembers `object_element` to be overwritten later by `handle_value`. — evidence: `include/nlohmann/detail/input/json_sax.hpp:620-648` (placeholder at 644), `json_sax.hpp:1074-1086`
3. Rejected values: `handle_value` calls the callback with `parse_event_t::value`; if rejected and the parent is an object, it pops `key_keep_stack`/`key_stack` and calls `remove_discarded_value(parent, key)` if a placeholder was stored. For containers, `end_object`/`end_array` call the callback with `object_end`/`array_end` (depth `ref_stack.size() - 1`); on false the container is overwritten with `discarded`, and after popping, the parent is cleaned: `remove_discarded_value` pops the array's last element if discarded, or erases the object member under the saved key (`container_key_stack`). — evidence: `json_sax.hpp:1024-1046`, `json_sax.hpp:650-703` (discard at 661, cleanup at 696-700), `json_sax.hpp:745-812`, `json_sax.hpp:964-988`
4. Start-event rejection: `start_object`/`start_array` push the callback result for `object_start`/`array_start` onto `keep_stack`, then call `handle_value(..., skip_callback=true)`; `handle_value` returns `{false, nullptr}` whenever `!keep_stack.back()`, so the container is never created (nullptr pushed on `ref_stack`) and all nested values are skipped; the key's placeholder is removed at the matching end event. — evidence: `json_sax.hpp:583-595`, `json_sax.hpp:705-714`, `json_sax.hpp:1010-1015`, `json_sax.hpp:1054-1059`
5. Duplicate keys: when `key()` finds the key already present it stashes the old value in `duplicate_key_stash`; if the new value/container is rejected, `resolve_duplicate_key_stash(slot, true)` restores the previous value instead of erasing the member (used from `remove_discarded_value` and the end_object/end_array discard branches); when accepted the stash entry is dropped. — evidence: `json_sax.hpp:635-643`, `json_sax.hpp:908-927`, `json_sax.hpp:980-985`, `json_sax.hpp:656-663`
6. Top level: after parsing, if the handler errored `result = value_t::discarded` (returned when `allow_exceptions` is false); otherwise if `result.is_discarded()` (root rejected by the callback) it is replaced with `nullptr` (JSON null). — evidence: `parser.hpp:121-133`
## Acceptable variations
- Line numbers ±3. Citing the amalgamated `single_include/nlohmann/json.hpp` copy of the same code is acceptable if the logic matches.
- The callback signature `bool(int depth, parse_event_t event, BasicJsonType& parsed)` (`parser.hpp:52`) and `basic_json::parse(..., parser_callback_t cb, ...)` entry (`include/nlohmann/json.hpp:4903-4914`) are fine extra detail.
- For fact 6, stating that a rejected root scalar is simply never assigned (so `parse()` returns the default null) is also correct.
## Common wrong answers
- Claiming rejected values are filtered in a post-pass over the finished DOM (removal happens incrementally during SAX events).
- Claiming the callback-free `json_sax_dom_parser` handles callbacks, or that `key()` stores nothing until the value arrives (it stores a `discarded` placeholder).
- Claiming a rejected duplicate key deletes the earlier value (at this commit the previous value is restored).
- Saying a discarded root yields `value_t::discarded` in the successful case (it becomes null; `discarded` is only for errors).
