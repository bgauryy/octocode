# L26 reference
## Question
In django/django at commit 4fab678a07, when you call `save()` on a model instance without forcing an insert or an update, how does Django decide whether to run an UPDATE or an INSERT for the instance's table, and what happens when the UPDATE matches no row?

## Key facts (graded)
1. Location: `save()` (`django/db/models/base.py:847`) → `save_base` (956) → `_save_table` (`base.py:1075`, called at 1002 and for parents at 1052). The decision is in `_save_table`.
2. Primary key first: if the pk is not set (and is not a `DatabaseDefault`), `meta.pk.get_pk_value_on_save(self)` may fill it; `pk_set` is then computed. — evidence: `base.py:1103-1108`
3. Skip the UPDATE for new instances with defaulted pk: if not `raw`, not forced, `self._state.adding` is true, and every pk field `has_default()` or `has_db_default()`, then `force_insert = True`. — evidence: `base.py:1111-1120` (comment "Skip an UPDATE when adding an instance and primary key has a default.")
4. Try UPDATE: `if pk_set and not force_insert:` it builds the values with `pre_save(self, False)` and calls `_do_update(base_qs, using, pk_val, values, update_fields, forced_update, returning_fields)`; `updated = bool(results)`. — evidence: `base.py:1121-1157` ("If possible, try an UPDATE. If that doesn't update anything, do an INSERT.")
5. `_do_update`: filters `base_qs.filter(pk=pk_val)`; with no values, it reports success if `update_fields` is not None or the row `exists()`; with `Meta.select_on_save` (and not a forced update) it checks `exists()` first, runs the update, and if that returns nothing re-checks `exists()`; otherwise it returns `filtered._update(values, returning_fields)`. — evidence: `base.py:1214-1252`
6. No row matched: if the UPDATE was forced (`force_update`) it raises `self.NotUpdated("Forced update did not affect any rows.")`; with `update_fields` it raises `NotUpdated("Save with update_fields did not affect any rows.")`; otherwise `updated` stays `False` and Django falls through to an INSERT (filling `_order` for `order_with_respect_to` models, then `_do_insert(cls._base_manager, …)`). — evidence: `base.py:1157-1164`, `base.py:1165-1211`

## Acceptable variations
- Line numbers ±3.
- Describing `NotUpdated` as the model's `DoesNotExist`/`DatabaseError`-style exception without the exact class name, if the messages are right.
- Leaving out `select_on_save` details costs completeness only.

## Common wrong answers
- Saying Django decides only by whether `pk` is `None`, ignoring the `_state.adding` + default-pk shortcut.
- Saying Django runs a SELECT before every UPDATE (only with `select_on_save`).
- Saying a zero-row UPDATE always raises an error (only for `force_update` or `update_fields`).
