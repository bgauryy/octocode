# G07 reference
## Question
In Kludex/starlette at commit 63c5760d8a, how is an application's middleware stack assembled, and how do raised exceptions reach their handlers?

## Key facts (graded)
1. `Starlette.build_middleware_stack` builds `[ServerErrorMiddleware(handler=error_handler, debug)]`, then `RequestBodyLimitMiddleware(max_body_size)` only if `max_body_size is not None`, then `self.user_middleware`, then `ExceptionMiddleware(handlers=exception_handlers, debug)`; it wraps `self.router` iterating `reversed(middleware)`, so the list order is outermost→innermost (router innermost). The stack is built lazily on first `__call__`. `add_middleware` does `user_middleware.insert(0, ...)`, so later-added middleware becomes outermost among user middleware, and raises RuntimeError once the stack is built. — evidence: `starlette/applications.py:63-83,92-96,104-107`
2. Handler split: keys `500` or `Exception` become the single `error_handler` passed to `ServerErrorMiddleware`; every other key goes to `ExceptionMiddleware`, which puts int keys into `_status_handlers` and exception classes into `_exception_handlers` (pre-seeded with `HTTPException → http_exception` and `WebSocketException → websocket_exception`). — evidence: `starlette/applications.py:68-72`, `starlette/middleware/exceptions.py:27-45`
3. Selection + propagation: `ExceptionMiddleware.__call__` stores `(exception_handlers, status_handlers)` in `scope["starlette.exception_handlers"]` and wraps the downstream app with `wrap_app_handling_exceptions`. The same wrapper is applied again per endpoint in `request_response` / `websocket_session` in routing, reading the handlers from that scope key, so endpoint exceptions are handled inside the route. Lookup: for `HTTPException`, first `status_handlers.get(exc.status_code)`; otherwise `_lookup_exception_handler` walks `type(exc).__mro__` and returns the first class present (most specific ancestor wins); no handler → re-raise. Sync handlers run in a threadpool. — evidence: `starlette/middleware/exceptions.py:47-63`, `starlette/_exception_handler.py:16-65`, `starlette/routing.py:65,84`
4. If a handler is found but `http.response.start` was already sent (tracked by a wrapping `sender`), it raises `RuntimeError("Caught handled exception, but response already started.")` from the original exception. — evidence: `starlette/_exception_handler.py:32-39,55-56`
5. `ServerErrorMiddleware` only acts on `http` scopes (websocket/lifespan pass straight through); on exception it builds a response via `debug_response` (traceback, run in threadpool) if debug, else the default `error_response` (`PlainTextResponse("Internal Server Error", 500)`) or the installed 500/Exception handler; it sends it only if the response has not started, and then ALWAYS re-raises the exception (so servers/test clients see it). — evidence: `starlette/middleware/errors.py:149-186,258-259`
## Acceptable variations
- Line numbers ±3.
- Naming the repo as encode/starlette is fine (GitHub redirects).
- Describing the MRO walk as "nearest base class registered wins" is fine.
## Common wrong answers
- Claiming user middleware sits outside ServerErrorMiddleware, or that ExceptionMiddleware is outermost.
- Claiming `add_middleware` appends (making later middleware innermost).
- Claiming a handler registered for `Exception` goes to ExceptionMiddleware.
- Claiming ServerErrorMiddleware swallows the exception after sending the 500.
- Claiming exception lookup uses `isinstance` over insertion order.
