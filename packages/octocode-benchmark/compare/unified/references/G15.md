# G15 reference
## Question
In tokio-rs/tokio, as of commit facc6fc47e the runtime has an unstable, opt-in sharded queue for `spawn_blocking` tasks. Which pull request added that opt-in, and what happened to the earlier attempt to shard that queue?

## Key facts (graded)
1. The opt-in was added by PR #8337 "runtime: add an opt-in sharded spawn_blocking queue", merged 2026-08-09 as `8b13642a1f7346814f189937b2d6e1e80b210db1` (an ancestor of facc6fc47e). Its body: it re-lands the sharded queue from #7757, disabled by default, enabled through the unstable `Builder::enable_sharded_blocking_queue` or the `TOKIO_UNSTABLE_SHARDED_BLOCKING_QUEUE` environment variable. — evidence: https://github.com/tokio-rs/tokio/pull/8337; `gh api repos/tokio-rs/tokio/compare/8b13642a1f7346814f189937b2d6e1e80b210db1...facc6fc47eb2ba13a465a3179f8e34db620561ec` → `ahead`
2. The earlier attempt was PR #7757 "rt: improve spawn_blocking scalability with sharded queue", merged 2026-04-10 as `1604bc335157be9a131e24cfde55cab3c90ebc92` (it closed issue #2528 "Heavy contention on blocking"). — evidence: https://github.com/tokio-rs/tokio/pull/7757
3. It was reverted by PR #8057 "rt: revert #7757 to fix regression in `spawn_blocking`", merged 2026-04-16 as `56aaa43e91c4fbed88f0c2a5b65019ed9a0c3c61`. The reason: the change made programs that use `spawn_blocking` hang (issue #8056, "regression in `spawn_blocking` caused by #7757 causes tests to hang"), and the implementation could not be switched off (the hang still occurred with `NUM_SHARDS` set to 1), so a plain revert was shipped for v1.52.1, with the suggestion to bring it back later as an unstable opt-in. — evidence: https://github.com/tokio-rs/tokio/pull/8057 (body)
4. Before the re-land, PR #8135 "refactor the spawn blocking queue to make adding a new sharded implementation easy" (merged 2026-07-31, `108d6d3dc038332af2af83957748333091e35b3f`) prepared the swap-able queue. — evidence: https://github.com/tokio-rs/tokio/pull/8135
5. Local evidence of the opt-in at facc6fc47e: `sharded_blocking_queue_default()` reads `TOKIO_UNSTABLE_SHARDED_BLOCKING_QUEUE` (`tokio/src/runtime/builder.rs:250-258`), `enable_sharded_blocking_queue` sets the flag (`builder.rs:526-527`), and `BlockingPool::new` picks `InnerImpl::Sharded` or `InnerImpl::Locked` from it (`tokio/src/runtime/blocking/pool.rs:286-290`).

## Acceptable variations
- Short SHAs; dates ±1 day (time zones).
- Key fact 4 is optional context; full credit does not require it.
- Mentioning the tracking issue #8067 "Re-land sharded spawn blocking queue" referenced by #8337.

## Common wrong answers
- Naming #7757 as the opt-in PR (it was the default-on attempt that was reverted).
- Saying #7757 was reverted for performance reasons rather than the hang regression.
- Claiming the sharded queue is on by default at facc6fc47e.
