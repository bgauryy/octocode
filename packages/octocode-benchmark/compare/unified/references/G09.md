# G09 reference
## Question
What is the root cause of pydantic/pydantic issue #13786, and how was it fixed?

## Key facts (graded)
1. Root cause: `ConfigWrapper.core_config()` in `pydantic/_internal/_config.py` sets `config = self.config_dict` and then writes into it: if `populate_by_name` is not None and `validate_by_name` is None, it assigns `config['validate_by_alias'] = True` and `config['validate_by_name'] = populate_by_name`; it also sets `config['validate_by_name'] = True` when `validate_by_alias is False` and `validate_by_name` is None. — evidence: `pydantic/_internal/_config.py:188-222` @ 0384c970 (writes at :216-217, :222)
2. Persistence + inheritance: the model metaclass stores `namespace['model_config'] = config_wrapper.config_dict` (same dict object), so the derived keys become part of the class's `model_config`. `ConfigWrapper.for_model` merges each base's `model_config` into the new config before the subclass namespace, so a child declaring `populate_by_name=False` inherits the parent's derived `validate_by_name=True`, and the `validate_by_name is None` guard then prevents re-deriving from the child's own value → Child accepts field names while an identical Standalone requires the alias. — evidence: `pydantic/_internal/_model_construction.py:119,129` @ 0384c970; `pydantic/_internal/_config.py:133-174` (merge at :158, :168)
3. Direct-config entry points: `prepare_config` returned the caller's dict itself (only class-based configs were converted), and e.g. `TypeAdapter` builds `ConfigWrapper(self._config)`, so `core_config()` mutated the user's mapping passed to `TypeAdapter(config=...)` / `validate_call(config=...)`. — evidence: `pydantic/_internal/_config.py:324-342` @ 0384c970; `pydantic/type_adapter.py:265` @ 0384c970
4. Fix: PR #13825 "Do not mutate `model_config` attribute" (closes #13786), landed on main as commit dae3788547fa8c7c3c78d28d284d3f669ad8c1d3 (GitHub also reports an empty follow-up commit 5da36b5de4f44a572ca5c12104fd2f8669dfeaca with the same title as the PR's mergeCommit). — evidence: https://github.com/pydantic/pydantic/pull/13825
5. Fix design: `ConfigWrapper` gains a separate `effective_config` slot built by new `_build_effective_config(config_dict)` which returns a new dict (`{**config, ...}`) with the derived `validate_by_*` values when it derives them (otherwise it returns its input unchanged) and raises the "At least one of validate_by_alias or validate_by_name" error; `__getattr__` and `core_config()` read `effective_config`, `config_dict` stays as declared; `prepare_config` now copies dict input; the `schema_generator` deprecation warning moved to `check_deprecated`. User-visible: `Model.model_config` for `{'populate_by_name': True}` now stays `{'populate_by_name': True}` instead of gaining `validate_by_alias`/`validate_by_name`. — evidence: `pydantic/_internal/_config.py:65-81,145,196,214,314-332,350-353` @ dae3788547fa8c7c3c78d28d284d3f669ad8c1d3; PR body

## Common wrong answers
- Blaming pydantic-core / Rust validation rather than the Python-side config wrapper.
- Claiming the parent's `ConfigDict` object assigned by the user is itself mutated for models (the class namespace yields the config_new dict; it's the class attribute that changes).
- Naming a different PR (e.g. #13824/#13892).
- Claiming the fix removes the `populate_by_name` backward-compat derivation (it is kept, just not persisted).
