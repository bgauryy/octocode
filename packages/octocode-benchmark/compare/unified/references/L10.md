# L10 reference
## Question
In prometheus/prometheus at commit ea954809ce, how does PromQL compute `rate()` and `increase()` over counter samples?

## Key facts (graded)
1. Shared helper: `funcRate`, `funcIncrease`, `funcDelta` all call `extrapolatedRate(vals, args, enh, isCounter, isRate)` with (true,true), (true,false) and (false,false) respectively; anchored or smoothed selectors branch off at the top to `extendedRate` / `extendedHistogramRate`. — evidence: `promql/functions.go:452`, `promql/functions.go:806-818`, `promql/functions.go:455-465`
2. Reset compensation: the raw result is `last.F - first.F`; for counters, for each consecutive pair where `currPoint.F < prevPoint.F` (or a start-timestamp reset is detected) the previous value is added back (`resultFloat += prevPoint.F`). — evidence: `promql/functions.go:512`, `promql/functions.go:521-535` (condition at 531, add at 532)
3. Extrapolation threshold: `durationToStart = firstT - rangeStart` and `durationToEnd = rangeEnd - lastT` (seconds); `extrapolationThreshold = averageDurationBetweenSamples * 1.1` where the average is `(lastT-firstT)/(n-1)`; if a gap is ≥ threshold it is replaced by half the average interval (the series is assumed to start/end inside the window), otherwise extrapolation goes to the boundary. — evidence: `promql/functions.go:541-549`, `promql/functions.go:588-590`, `promql/functions.go:615-617`
4. No negative counters: for counters, `durationToZero = sampledInterval * (firstValue / resultFloat)` (when result > 0 and first value ≥ 0); if that is shorter than `durationToStart`, it is used instead, so the start extrapolation stops at the estimated zero point. — evidence: `promql/functions.go:591-611` (formula at 602, min at 609-610)
5. Final value: `factor = (sampledInterval + durationToStart + durationToEnd) / sampledInterval`; for rate the factor is additionally divided by the range length in seconds (`ms.Range.Seconds()`), increase is not; the result is `resultFloat * factor`. — evidence: `promql/functions.go:619-631` (621, 623-624, 627)
6. Edge cases: fewer than two samples yields no output unless a valid start timestamp (created timestamp) falls inside the window, in which case a zero-valued sample at that ST is assumed and left-side extrapolation is replaced (`durationToStart = 0`). — evidence: `promql/functions.go:551-575` (single-sample return at 572-574)

## Acceptable variations
- Fact 6: give half credit for "needs at least two samples, else no output" with a correct citation (`promql/functions.go:572-574`) even without the start-timestamp exception.
- Function registry citations (`promql/functions.go:2830`, `2846`, `2873`) are acceptable additions.
- Line tolerance ±2.

## Common wrong answers
- Claiming rate() simply divides (last − first) by the range with no extrapolation.
- Claiming extrapolation always goes to the window boundary, or that the threshold is 10% of the range (it is 110% of the average sample spacing).
- Confusing with irate() (`instantValue`), which uses only the last two samples.
- Saying increase() is computed as rate() × range in a separate function (it is the same helper with isRate=false).
