# G16 reference
## Question
In prometheus/prometheus, as of commit ea954809ce, which pull request added support for scraping targets over Unix domain sockets, which issue did it close, and which later pull request fixed a connection mix-up in that feature, and what was the mix-up?

## Key facts (graded)
1. Feature PR: #18091 "scrape: support scraping targets via Unix Domain Sockets" by IngmarStein, merged 2026-08-06 as `c5fa89db085c9b3855d7916f2ade047066a7a318` (ancestor of ea954809ce). — evidence: https://github.com/prometheus/prometheus/pull/18091; `gh api repos/prometheus/prometheus/compare/c5fa89db085c9b3855d7916f2ade047066a7a318...ea954809ceafceb53ecfa295ab0947753929de9e` → `ahead`
2. Closed issue: #12024 "Support Unix socket for metrics address". — evidence: `gh pr view 18091 -R prometheus/prometheus --json closingIssuesReferences`
3. Fix PR: #19399 "scrape: use a dedicated HTTP client per unix socket target" by roidelapluie, merged 2026-08-14 as `05f9eb8b3b8e10b48c8f4153b0714dbe9bc9a630` (ancestor of ea954809ce). — evidence: https://github.com/prometheus/prometheus/pull/19399
4. The mix-up: the socket path was passed to a shared HTTP client's dialer through the request context, but the transport pools idle connections by scheme and `host:port` only. Two targets with the same address but different socket paths (or a plain TCP target with that address) could reuse each other's pooled connections and scrape the wrong endpoint. The fix gives each socket path its own scrape client, cached per scrape pool and rebuilt on reload. — evidence: PR #19399 body
5. Local evidence at ea954809ce: `scrapePool.unixSocketClients` cache (`scrape/scrape.go:99-101`), per-socket client creation and caching (`scrape.go:210-229`), the cache is dropped and its clients closed on reload (`scrape.go:340-346`) and when a socket is no longer used (`scrape.go:566-569`); the socket path comes from the `__unix_socket__` label (`UnixSocketLabel`, `scrape.go:2474-2477`).

## Acceptable variations
- Short SHAs; dates ±1 day.
- Key fact 5 is supporting evidence; full credit does not require local line numbers.
- Describing the mix-up as "connection reuse across socket paths" or "keep-alive pool keyed only by host:port".

## Common wrong answers
- Naming a Docker or Docker Swarm discovery PR (for example #7604, about the Docker daemon socket) as the scrape feature.
- Naming #18421 (a scrape-failure-logger race) as the Unix-socket fix.
- Saying the bug was in socket path parsing or permissions rather than connection pooling.
