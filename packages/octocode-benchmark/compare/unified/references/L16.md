# L16 reference
## Question
In google/guava at commit 4d41665af1, how do `CacheBuilder`'s `maximumSize` and `concurrencyLevel` settings shape the cache's internal structure?

## Key facts (graded)
1. Default and read: `getConcurrencyLevel()` returns `DEFAULT_CONCURRENCY_LEVEL` (= 4) when unset; `build()` → `new LocalCache.LocalManualCache<>(this)` → `new LocalCache<>(builder, null)`, whose constructor does `concurrencyLevel = min(builder.getConcurrencyLevel(), MAX_SEGMENTS)` with `MAX_SEGMENTS = 1 << 16`, and `maxWeight = builder.getMaximumWeight()` (returns `maximumSize` when no weigher). — evidence: `guava/src/com/google/common/cache/CacheBuilder.java:199`, `CacheBuilder.java:473-475`, `CacheBuilder.java:1060-1064`, `guava/src/com/google/common/cache/LocalCache.java:4833-4835`, `LocalCache.java:150`, `LocalCache.java:248-250`, `LocalCache.java:258`
2. Segment-count loop: starting at 1, doubles `segmentCount` while `segmentCount < concurrencyLevel && (!evictsBySize() || segmentCount * 20L <= maxWeight)` (i.e. with size-based eviction each segment must get ≥ ~10 entries); for maxWeight=100, concurrencyLevel=64: 1→2→4→8, stops at 8 because 8*20=160 > 100 → **8 segments** (segmentShift = 32-3 = 29, segmentMask = 7). — evidence: `LocalCache.java:280-293`
3. Weight split: `maxSegmentWeight = maxWeight / segmentCount + 1`, `remainder = maxWeight % segmentCount`, and it decrements `maxSegmentWeight` when `i == remainder`; for 100/8: segments 0–3 get 13, segments 4–7 get 12 (4·13 + 4·12 = 100). Passed to `createSegment(segmentSize, maxSegmentWeight, ...)`; without size eviction segments get `UNSET_INT`. — evidence: `LocalCache.java:307-322`, `LocalCache.java:1771-1774`
4. Enforcement is per segment: `Segment.evictEntries(newest)` returns early unless `map.evictsBySize()` (`maxWeight >= 0`), evicts the newest entry alone if its weight > `maxSegmentWeight`, then `while (totalWeight > maxSegmentWeight)` removes `getNextEvictable()` (first positive-weight entry in the access queue) with `RemovalCause.SIZE`; called from the put/load paths (e.g. lines 2840, 2854, 2866, 3196). Keys are routed via `segmentFor(hash)` = `segments[(hash >>> segmentShift) & segmentMask]`. — evidence: `LocalCache.java:2657-2679`, `LocalCache.java:326-328`, `LocalCache.java:1766-1769`
5. `getMaximumWeight()` returns 0 when `expireAfterWriteNanos == 0 || expireAfterAccessNanos == 0`, so the cache is treated as size-evicting with maxWeight 0: the loop condition `segmentCount * 20L <= 0` fails immediately → a single segment with max segment weight 0 (every entry is evicted). — evidence: `CacheBuilder.java:603-608`, `LocalCache.java:287-288`, `LocalCache.java:309`
## Acceptable variations
- Line numbers ±3; citing `android/guava/src/com/google/common/cache/LocalCache.java` (offset by ~4 lines, same logic) is acceptable.
- "Segments" may be called partitions/shards.
- Describing fact 5 as "weight limit of 0, effectively no caching" is fine; the single-segment consequence is the checkable part but an answer that correctly states maxWeight becomes 0 and eviction is per-segment should get most credit.
- Mentioning `initialCapacity` clamping (`LocalCache.java:275-278`) or `Segment.initTable` threshold bump (`LocalCache.java:1998-2004`) is fine extra.
## Common wrong answers
- 64 segments (ignores the size-based cap) or 128 segments ("lowest power of two exceeding" read literally).
- Equal split of 12.5 / rounding everything to 13 (sum 104) or 12 (sum 96).
- Claiming eviction is global across the whole cache (it is per-segment, which is why the ×20 cap exists).
- Default concurrency level 16 (that is ConcurrentHashMap's historical default, not Guava's).
