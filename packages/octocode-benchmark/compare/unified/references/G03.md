# G03 reference
## Question
What bug does nodejs/undici PR #5881 ("fix(pool): ensure that removed clients don't pick up requests") fix, and how does the fix work?

## Key facts (graded)
1. Root cause: on `connectionError`, `Pool` (and `RoundRobinPool`) only spliced the failed client out of `kClients` without closing it (base comment: "Do not use kRemoveClient here, as it will close the client"). Since `kOnDrain` only bails out for `client.closed || client.destroyed`, the still-open client's drain handler kept shifting items off the pool `kQueue`, while `kDestroy`/close only iterated `kClients`, so pool.destroy() could not reach it (pool reported zero connections with a live socket). — evidence: `lib/dispatcher/pool-base.js:57-60` (kOnDrain guard), base `lib/dispatcher/pool.js` connectionError handler (removed lines in PR diff), `lib/dispatcher/pool-base.js:205-214`
2. New `kRetireClient` in `PoolBase`: removes the client from `kClients`, and unless already destroyed or already retiring, records it in a new `kRetiring` Map (client → promise) and calls `client.close(cb)` (callback form, guarded by a `done` flag, since factory dispatchers may not return a promise); the callback deletes the entry and resolves the promise. `kRemoveClient` now delegates to it. — evidence: `lib/dispatcher/pool-base.js:23-24,50-52,269-300`
3. Close/destroy: a new `closeClients(pool)` helper closes every non-destroyed client in `kClients` AND awaits every pending `kRetiring` promise; it replaces the three duplicated close loops (kOnDrain, kDrainQueue, kClose). `kDestroy` additionally calls `destroy(err)` on every client in `kRetiring`. — evidence: `lib/dispatcher/pool-base.js:26-41,86,124,188-190,205-214`
4. Connection-error handlers: `Pool` now calls `this[kRetireClient](target)` for each target still in `kClients` and calls `kDrainQueue` when `resumeQueued || this[kQueued] > 0`; `RoundRobinPool` likewise retires targets and drains when `kQueued > 0`, so queued requests move to another (possibly new) client instead of the retired one. — evidence: `lib/dispatcher/pool.js:136-160`, `lib/dispatcher/round-robin-pool.js:86-101`
5. Because `kRemoveClient` now goes through retirement, clients evicted by the `clientTtl` option (`Pool` get-dispatcher path calls `this[kRemoveClient](client)`) are also tracked: `close()` waits for them and `destroy()` aborts their in-flight requests (covered by new tests in `test/pool-retired-clients.js`). — evidence: `lib/dispatcher/pool.js:186-187,208-209`, `test/pool-retired-clients.js` (tests "destroy() aborts in-flight requests on a client evicted by clientTtl", "close() waits for a client evicted by clientTtl")
## Acceptable variations
- Line numbers ±3.
- Describing kRetiring as "a set/map of closing clients" is fine; it must be clear they're tracked until close completes.
- The PR body is terse; answers that derive the root cause from the diff are expected.
## Common wrong answers
- Claiming the fix destroys (rather than gracefully closes) the failed client immediately.
- Claiming the `kOnDrain` closed/destroyed guard was added by this PR (it pre-exists; the fix makes the client `closed` so the guard applies).
- Claiming only `Pool` changed (RoundRobinPool also changed).
