# L29 reference
## Question
tokio-rs/tokio issue #8541 reports a use-after-free in the semaphore when a tracing subscriber panics. In tokio-rs/tokio at commit facc6fc47e, where is the tracing event that makes this possible, and why does a panic at that point leave a completed waiter linked in the wait queue?

## Key facts (graded)
1. The event: `Waiter::assign_permits` emits `tracing::trace!(target: "runtime::resource::async_op::state_update", permits_obtained = assign, permits.op = "add")` (only with `tokio_unstable` and the `tracing` feature) right after the CAS that subtracts the assigned permits from the waiter's `state`, before it returns `next == 0`. — evidence: `tokio/src/sync/batch_semaphore.rs:551-569` (event at 559-566)
2. The caller: `Semaphore::add_permits_locked` calls `waiter.assign_permits(&mut rem)` on `waiters.queue.last()` and only afterwards removes the waiter with `waiters.queue.pop_back()` and takes its waker. — evidence: `batch_semaphore.rs:306-332` (call at 316, pop at 327)
3. Why the waiter stays linked: if the subscriber panics inside the event, the permits are already assigned (the waiter's `state` is 0) but the waiter was never popped. If the panic is caught, the queued `Acquire` future can be polled again; `poll_acquire` with `queued` sees no remaining permits and completes, and `Acquire` clears `queued` (`batch_semaphore.rs:600-610`). Dropping the `Acquire` then skips unlinking because `queued` is false (`batch_semaphore.rs:690`), so its waiter memory is freed while still in the list, and a later `add_permits_locked` (release) dereferences it.
4. Report and fix: issue #8541 (opened 2026-10-02) needs `tokio_unstable`, the `tracing` feature and an unwinding subscriber. PR #8542 "sync: fix semaphore use-after-free and permit leak on tracing panic" (merged 2026-10-03 into the `tokio-1.51.x` branch as `625c85108da5ad0d482702a21d7d58a56ea06a48`) removes the waiter from the queue before emitting the event, and also fixes permit leaks when the events in `poll_acquire` panic (uncontended path `batch_semaphore.rs:446-464`; contended path around 474-489). — evidence: https://github.com/tokio-rs/tokio/pull/8542

## Acceptable variations
- Line numbers ±3.
- Not naming the fix PR costs completeness only; the question asks for the local site and the mechanism.
- Describing the second problem (permit leak in `poll_acquire`) as extra information.

## Common wrong answers
- Pointing at the `poll_acquire` events as the use-after-free site (those leak permits; the use-after-free comes from `assign_permits` inside `add_permits_locked`).
- Saying the event is emitted after `pop_back`.
- Claiming the bug happens without `tokio_unstable`/`tracing`.
