# G02 reference
## Question
Review pydantic/pydantic PR #13824 ("Add a `counter` core schema"). How does validation of `collections.Counter` fields behave after this PR compared to before?

## Key facts (graded)
1. Before: both `Counter` entries in the type→schema map in `_generate_schema.py` called `self._mapping_schema(..., int)`, i.e. a generic `dict_schema(keys, int, strict=False)` wrapped in a `lax_or_strict_schema` with an after-validator calling `collections.Counter` (strict = isinstance check chained with it), using `MAPPING_ORIGIN_MAP`. After: they call the new `self._counter_schema(keys_type)`, which returns `core_schema.counter_schema(self.generate_schema(keys_type), core_schema.int_schema())` (bare `Counter` uses `Any` keys). — evidence: base `pydantic/_internal/_generate_schema.py:390,431-433,659-699`; merge `pydantic/_internal/_generate_schema.py:390,431,488-489`
2. Python input: strict mode accepts only `collections.Counter` instances (else `counter_type` error "Input should be a valid Counter"); lax mode accepts a Counter (exact match), an exact `dict`, or any `Mapping` (lax match). JSON input: strict (and therefore lax) accepts a JSON object, anything else errors — the comment notes otherwise a Counter could never be built from JSON; string-mapping input rejects strings. — evidence: `pydantic-core/src/input/input_python.rs:491-512`, `pydantic-core/src/input/input_json.rs:254-260`, `pydantic-core/src/input/input_abstract.rs` (`validate_counter` strict/lax dispatch), `pydantic-core/src/errors/types.rs` (`CounterType`)
3. The new `CounterValidator` validates each key with `keys_schema` and each value with `values_schema` (errors on keys get `[key]` location), collects into a plain `PyDict`, then runs `length_check!(input, "Counter", min_length, max_length, output)` and builds the result with `collections.Counter(output)`; supports `fail_fast`. — evidence: `pydantic-core/src/validators/counter.rs:114-186` (length check + construction at `:176-177`)
4. Serialization: `CounterSerializer.to_python` returns a new `Counter` in python mode but a plain dict in JSON mode; non-Counter values fall back with a warning. In inference, `ObType::Counter` is detected via an `isinstance` check placed before the `dict` check (Counter is a dict subclass) and is serialized like a dict for JSON, rebuilt as `Counter` for python. — evidence: `pydantic-core/src/serializers/type_serializers/counter.rs:89-121` (mode switch `:112-115`), `pydantic-core/src/serializers/ob_type.rs:363-368`, `pydantic-core/src/serializers/infer.rs` (ObType::Counter arms)
5. Python-side registries: `'counter'` added to the DICT_CONSTRAINTS schema-type list (so `min_length`/`max_length` annotations apply natively), `collections.Counter`/`typing.Counter` removed from `MAPPING_ORIGIN_MAP` and `collections.Counter` added to `_defaultdict_allowed_default_types` (so `defaultdict[..., Counter]` gets a default factory), `GenerateJsonSchema.counter_schema` delegates to `_common_dict_schema`, and `'counter'` added to the experimental pipeline's length-constrainable types and to schema_gather's dict-like branch. — evidence: `pydantic/_internal/_known_annotated_metadata.py:75`, merge `pydantic/_internal/_validators.py:438` vs base `:520-521`, `pydantic/json_schema.py:1197-1206`, `pydantic/experimental/pipeline.py:~482`, `pydantic-core/src/schema_gather.rs:146`
## Acceptable variations
- Line numbers ±3; citing the PR diff hunk headers is acceptable.
- Describing the old behavior as "a dict schema plus Counter coercion" without naming `lax_or_strict_schema` is fine as long as the `_mapping_schema` path is identified.
- The motivation (constraints not applying properly, issue #13704) may be mentioned but is not required.
## Common wrong answers
- Claiming Counter values are validated as `Any` (values schema is `int_schema()`).
- Claiming strict mode accepts a plain dict from Python input.
- Claiming JSON-mode serialization emits a `Counter` object or a list of pairs (it is a plain dict/object).
- Claiming `typing.Counter` still goes through `MAPPING_ORIGIN_MAP`.
