# L09 reference
## Question
In prometheus/prometheus at commit ea954809ce, how does Prometheus mark series as stale when they disappear from a scrape or when a target stops being scraped?

## Key facts (graded)
1. Tracking: the per-target `scrapeCache` keeps two maps `seriesCur` / `seriesPrev` (map of storage ref → cacheEntry); each successfully appended series is recorded in `seriesCur` via `trackStaleness`, and at the end of each scrape `iterDone` swaps prev/cur and clears the new current. — evidence: `scrape/scrape.go:1019-1021`, `scrape/scrape.go:1163-1165`, `scrape/scrape.go:1101-1103`
2. Detection: `forEachStale` iterates `seriesPrev` and invokes the callback for every ref not present in `seriesCur`. — evidence: `scrape/scrape.go:1167-1175`
3. Writing: `updateStaleMarkers` (called at the end of a successful `append`, only when `err == nil`) appends `math.Float64frombits(value.StaleNaN)` for each stale series at the scrape timestamp, with the reject-early-OOO option, and deliberately ignores `storage.ErrOutOfOrderSample` and `storage.ErrDuplicateSampleForTimestamp` (expected when a target goes away and returns with a new loop). V2 equivalent `updateStaleMarkersV2`. — evidence: `scrape/scrape.go:1753-1768` (Append at 1757, ignore at 1760-1763), call at `scrape/scrape.go:2081-2082`; V2 `scrape/scrape_append_v2.go:68`, `401`
4. Failed scrape: a failed scrape is treated like an empty one — `scrapeAndReport` still calls `append`; an empty body makes `append` call `updateStaleMarkers` and `iterDone(false)`, so every previously seen series gets a marker; if appending the real body failed (e.g. parse error / sample limit) the appender is rolled back and `append` is re-run with an empty body for the same purpose. — evidence: `scrape/scrape.go:1610-1613`, `scrape/scrape.go:1781-1785`, `scrape/scrape.go:1619-1629`
5. End of run: when the loop stops (`run`'s deferred cleanup, only if the parent context is not cancelled and markers not disabled), `endOfRunStaleness` waits for two more ticks of the scrape ticker (recording the first tick time as the marker timestamp) plus an extra `interval/10`, then appends an empty scrape (and `reportStale`) to write markers; it returns early if there was never a scrape (`last.IsZero()`) or the parent context is cancelled (shutdown). — evidence: `scrape/scrape.go:1414-1419`, `scrape/scrape.go:1662-1728` (ticks at 1680, 1689; `interval / 10` at 1696; empty append at 1720; reportStale at 1725)
6. Suppression: `disableEndOfRunStalenessMarkers` sets an atomic flag checked both before starting and again after the wait; it is invoked when a pool restarts loops reusing the cache (`restartLoops` with reuseCache) and via `scrapePool.disableEndOfRunStalenessMarkers` / `Manager.DisableEndOfRunStalenessMarkers`. — evidence: `scrape/scrape.go:1737-1739`, `scrape/scrape.go:1700`, `scrape/scrape.go:1416`, `scrape/scrape.go:364`, `scrape/scrape.go:605-613`, `scrape/manager.go:547-559`

## Acceptable variations
- "About 2.1 scrape intervals" is an acceptable summary of the wait.
- Citing the V2 appender path (`scrape/scrape_append_v2.go:91-98`) instead of v1 is fine.
- Mentioning `updateRef`/`moveStaleness` re-keying tracking when a series ref changes (`scrape/scrape.go:1141-1161`) is a bonus.
- Mentioning that series with explicit timestamps are not tracked unless `track_timestamps_staleness` is on (`scrape/scrape.go:1965`, `1983`) is a bonus.

## Common wrong answers
- Locating this in the TSDB head/compaction or PromQL lookback-delta logic (the marker is written by the scraper).
- Claiming markers are written immediately when a target disappears.
- Claiming markers are written on server shutdown (context-cancelled path explicitly skips them).
- Saying all append errors are ignored when writing markers (only out-of-order and duplicate-timestamp).
