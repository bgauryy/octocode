## Q29
**Answer** — MCP's authorization for HTTP-based transports (including streamable HTTP) is built on **OAuth 2.1** (IETF draft `draft-ietf-oauth-v2-1-13`), specified in `docs/specification/2026-07-28/basic/authorization/index.mdx` — the latest dated, non-draft spec version folder in the repo (siblings: `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, `2026-07-28`, `draft`). The spec states: *"The Model Context Protocol provides authorization capabilities at the transport level, enabling MCP clients to make requests to restricted MCP servers on behalf of resource owners. This specification defines the authorization flow for HTTP-based transports."* Authorization is OPTIONAL overall, but *"Implementations using an HTTP-based transport SHOULD conform to this specification."*
**Discovery**: *"MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients **MUST** use OAuth 2.0 Protected Resource Metadata for authorization server discovery."* Per the spec's own sequence diagram, discovery works as: the client sends an MCP request without a token → the server responds `HTTP 401 Unauthorized` with a `WWW-Authenticate` header → the client extracts a `resource_metadata` URL from it → the client fetches the Protected Resource Metadata document → parses it to find the authorization server(s) → the client then queries that authorization server's own metadata endpoint (`GET Authorization server metadata endpoint`, trying OAuth 2.0 Authorization Server Metadata / RFC8414 and OpenID Connect Discovery in priority order).
**Token acquisition**: after client registration (Client ID Metadata Documents, Dynamic Client Registration, or a pre-registered client ID), the client generates PKCE parameters, includes a `resource` parameter (RFC 8707), opens the browser to the authorization URL, obtains an authorization code via redirect (validating `iss` per RFC 9207), then exchanges it: *"C->>A: Token request + code_verifier + resource; A->>C: Access token (+ refresh token)."*
**Token presentation**: the spec's "Access Token Usage / Token Requirements" section states — *"1. MCP client **MUST** use the Authorization request header field defined in OAuth 2.1 Section 5.1.1:"* followed by the quoted header format:
```
Authorization: Bearer <access-token>
```
*"Note that authorization **MUST** be included in every HTTP request from client to server."* and *"2. Access tokens **MUST NOT** be included in the URI query string."*

## Q30
**Answer** — Chromium's current IPC mechanism between the browser process and its child (renderer/utility/GPU) processes is **Mojo**, top-level documented at `mojo/README.md`. Per that file: *"Mojo is a collection of runtime libraries providing a platform-agnostic abstraction of common IPC primitives, a message IDL format, and a bindings library with code generation for multiple target languages to facilitate convenient message passing across arbitrary inter- and intra-process boundaries."*
**IDL**: the interface definition language is the **mojom Interface Definition Language (IDL)** — *"The [mojom Interface Definition Language (IDL)](/mojo/public/tools/bindings/README.md) is used to generate interface bindings for various languages to send and receive mojom interface messages using Mojo message pipes."* (A companion doc, `mojo/public/tools/mojom/README.md`, independently confirms: *"The Mojom format is an interface definition language (IDL) for describing interprocess communication (IPC) messages and data types for use with the low-level cross-platform Mojo IPC library."*)
**Message pipe establishment**: message pipes are the core Mojo IPC primitive, created via Mojo Core's C System API — *"It exposes the fundamental cross-platform capabilities to create and manipulate Mojo primitives like **message pipes**, **data pipes**, and **shared buffers**, as well as APIs to help bootstrap connections among processes."* Creation is deliberately cheap: *"As an implementation detail, creating a message pipe is essentially generating two random numbers and stuffing them into a hash table, along with a few tiny heap allocations."* Pipe usage is identical whether it crosses a process boundary or stays in-process — *"message pipe usage is identical regardless of whether the pipe actually crosses a process boundary."*
**Message-passing layer vs. interface-binding layer**: Mojo's documented architecture is explicitly layered — Mojo Core at the bottom (exposing raw message pipes/data pipes/shared buffers via the C System API and Platform Support API — the message-passing layer, deliberately service-agnostic: *"Mojo does not deal with services, it only facilitates interface definition, message passing, and other lower-level IPC primitives"*) with the **Bindings APIs** built on top (the interface-binding layer: per-language code generated from `.mojom` IDL files that use those message pipes to send/receive typed interface messages, e.g. C++'s `Remote`/`Receiver` types). The FAQ makes the distinction concrete: *"a `Remote` on one thread sending a message to a `Receiver` on another thread... is effectively a `PostTask`... with the added... costs of serialization, deserialization, validation, and some internal routing logic"* — i.e. the binding layer adds typed serialization/validation on top of the raw message-passing primitive.
