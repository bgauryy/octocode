# octocode vs `gh` — full pass (all 17), 2026-08-05

**Matchup:** `compare/octocode-vs-gh` (17 GitHub research questions).
**Arm A (baseline):** read-only `gh` (search/repo view/pr view+diff/`api` GET on `/contents`,`/commits`). **Arm B (Octocode):** `octocode tools …`.
**Method:** per question, Arm A answers with `gh` only and Arm B with `octocode tools` only, each on its leanest legitimate path; ground truth established by independent current-evidence research. Measured in **characters** (raw CLI output pulled into context), never tokens. Frozen at 2026-08-04/05 UTC.

## Bottom line

**Correctness was an effective tie (both 9.94 mean — identical on 16 questions, both 9 on Q10); the run is decided on the leanness tiebreak, which Octocode wins clearly.** Total characters pulled: **Octocode 152,710 vs gh 286,812** — Octocode pulled ~53% of gh's characters; **gh pulled 1.88× more**. Octocode was leaner on **11 of 17** questions.

gh's character cost is dominated by whole-file / whole-diff pulls that its surface forces (no region read): Q17 `patch-fetch.ts` 50k, Q5 diff 44k, Q12 `events.js` 36k, Q9 27k, Q11 23k, Q8 19k, Q6 19k. Octocode's `matchString`-scoped region reads answer the same questions from ~1k–7k each. gh was leaner on the six questions where a targeted `gh` call (empty repo search, a single small PR diff, a tiny package.json) beat Octocode's discovery cost or JSON-envelope overhead (Q2, Q3, Q4, Q5, Q13, Q14).

## Fairness & methodology caveats

- **Octocode arm ran via the local monorepo build** (`node packages/octocode/out/octocode.js`) rather than `npx octocode`, deviating from the skill's "`npx octocode tools …` only" rule. Same code, faster; no tool logic differs. Flagged for reproducibility.
- **Single runner per arm, single grader** (one operator playing all three roles with role discipline), not three isolated agents. One pass is a snapshot per `SCORING.md`; treat sub-point depth/workflow deltas as noise — the stable signals are the **correctness tie** and the **1.88× character gap**.
- **Chars include Octocode's JSON envelope** (`results` + `next`/clone hints) whereas `gh --json`/`api --raw` is bare. This inflates Octocode on tiny targets (Q4 298 vs 1,920; Q14 5,576 vs 7,210) and is the honest "raw CLI output" measure.
- **Octocode commit-by-SHA handicap (Q3).** Octocode has no get-a-single-commit-diff; the only path to the raw patch was a 99k path-filtered commit listing, so its Q3 answer used current-file + message evidence instead of the diff.
- **`gh`'s char cost is structural, not sloppy.** Where `gh` was heavy (Q17 50k, Q12 36k, Q9 27k, Q11 23k, Q8 19k, Q6 19k) it pulled whole files only because `gh api /contents` returns whole files — it has no `matchString`/region read. That is exactly the capability gap Octocode exploits, and the reason Octocode is leaner on 11/17 at equal correctness.
- **Where `gh` was leaner** (Q2 empty repo search = 0 chars; Q13 tiny `pr diff`; Q3 commit-by-SHA; Q4/Q14 tiny files), a single targeted `gh` call beat Octocode's discovery/listing/envelope cost.
