## The SSRF advisory fixed in 1.7.4

**GHSA-8hc4-vh64-cxmj / CVE-2024-39338**, high, "Server-Side Request Forgery in axios", vulnerable range `>= 1.3.2, <= 1.7.3`, first patched **1.7.4**. A request path built as `` `/${userId}` `` with `userId = '/localhost:4667'` becomes the protocol-relative URL `//localhost:4667`. `isAbsoluteURL` treats it as absolute, so `buildFullPath` keeps it, and the Node HTTP adapter resolved it against `http://localhost`, which sent the request to another host.

The advisory links two merged PRs (#6539 and #6543) and one commit, `6b6b605`. The question names the PR whose merge commit the advisory links:

| | Value |
|---|---|
| PR | **#6543** "fix(sec): CVE-2024-39338 (#6539)", by `levpachmanov`, base `v1.x` |
| Merged | 2024-08-13T18:43:05Z |
| Merge commit | **`6b6b605eaf73852fb2dae033f1e786155959de3a`** (squash; parent `07a661a2a6b9`) |
| Release | `v1.7.4` (tag → commit `abd24a7367726616e60dfc04cb394b4be37cf597`, released 2024-08-13). `v1.7.3...v1.7.4` has 3 commits: `07a661a` (#6539), `6b6b605` (#6543), `abd24a7` (release #6544) |

The change it made, `lib/adapters/http.js:232` (same line at `v1.7.3` and `v1.7.4`):

```diff
     const fullPath = buildFullPath(config.baseURL, config.url);
-    const parsed = new URL(fullPath, 'http://localhost');
+    const parsed = new URL(fullPath, utils.hasBrowserEnv ? platform.origin : undefined);
```

On the server there is no base URL anymore, so `new URL('//localhost:4667', undefined)` throws `TypeError: Invalid URL`. In a browser environment the page's origin is the base. The same commit also:
- restored the `isAbsoluteURL` regex that #6539 had changed. At `v1.7.4`, `lib/helpers/isAbsoluteURL.js:14` is `return /^([a-z][a-z\d+\-.]*:)?\/\//i.test(url);`, so protocol-relative URLs still count as absolute.
- rewrote `test/unit/regression/SNYK-JS-AXIOS-7361793.js`: server-side, the request must throw an error whose message starts with `Invalid URL`. Client-side mode is a separate case.

Background: **#6539** (by `hainenber`, merged 2024-08-13T15:03:25Z, merge commit `07a661a2a6b9092c4aa640dcc7f724ec5e65bdda`) fixed the bug first by dropping the `?` from the regex: `/^([a-z][a-z\d+\-.]*:)\/\//i`. #6543 reverted that regex before 1.7.4 shipped, so the regex change from #6539 never shipped.

## Common wrong answers
- Naming **#6539 / `07a661a`** as the fix, or quoting its regex `/^([a-z][a-z\d+\-.]*:)\/\//i` as the shipped check. #6543 reverted that change before 1.7.4 was released.
- Quoting the `isAbsoluteURL` regex with the `?` as "the code it changed". #6543 only restored the 1.7.3 regex. The fix is the `new URL` base in `http.js`.
- Giving `07a661a` as #6543's merge commit. That is its parent.
- Picking the wrong SSRF advisory: GHSA-jr5f-v2jv-69x6 / CVE-2025-27152 (absolute URL SSRF, fixed 1.8.2), GHSA-3p68-rc4w-qgx5 (NO_PROXY bypass, 1.15.0), or GHSA-m7pr-hjqh-92cm (no_proxy IP alias, 1.15.1).
- Counting 39 by including the 5 withdrawn duplicates.
- Giving a 0.x fix (e.g. 0.31.1) as the first fixed version for 1.7.3.
- A stale or partial list, e.g. only the 2024–2025 advisories (CVE-2024-39338, CVE-2025-27152, CVE-2025-58754), presented as complete.
- Saying the PR targeted `main`. Both PRs targeted `v1.x`.
