### Q44 — Astro vs Next.js: SSR rendering and component model

Using `withastro/astro` and `vercel/next.js`:
1. Find the SSR render entry function in each repo.

3. How does Astro's islands model differ architecturally from Next.js's React Server Components?

## Answer

- Astro SSR entry point: `withastro/astro` defines `renderPage(result, componentFactory, props, children, streaming, route?)` in `packages/astro/src/runtime/server/render/page.ts`.
- Next.js App Router SSR entry area: `vercel/next.js` uses `packages/next/src/server/app-render/app-render.tsx`, where App Router rendering builds RSC/Flight payloads and HTML streams; in the inspected current file it calls React Server Components streaming through `renderToReadableStream` from `componentMod` / `react-server-dom-webpack` and imports helpers such as `continueFizzStream`.
- Astro streaming: `renderPage()` imports `renderToAsyncIterable`, `renderToReadableStream`, and `renderToString` from `./astro/render.js`. If `streaming` is true on Node (but not Deno), it renders to an async iterable and passes it to `new Response`; otherwise it renders to a Web `ReadableStream`. If not streaming, it renders to a full string and computes `Content-Length`.
- Astro can also handle non-Astro page components by rendering to a string with `renderComponentToString` or the experimental queue renderer (`buildRenderQueue` + `renderQueue`) and returning an encoded HTML `Response`.
- Next.js streaming: App Router generates React Server Component payloads (`generateDynamicRSCPayload`/Flight payloads), streams them with `renderToReadableStream` or Node Flight streams, and composes them into `FlightRenderResult`/HTML render results. Its staged rendering code separates static and dynamic stages, tees/replays streams, counts static-stage bytes, and can continue Fizz streams for HTML.
- Architectural difference: Astro's islands model renders pages mostly as static HTML and records explicit `client:*` hydration metadata for individual interactive islands; only those islands load client JavaScript and hydrate.
- Next.js's model is React Server Components plus Client Components: the server renders an RSC tree/Flight stream and React coordinates the client/server component boundary. Hydration and client JS are organized around React component boundaries rather than Astro's explicit island directives.
- In short, Astro optimizes for HTML-first pages with opt-in hydrated islands; Next.js App Router optimizes for React as the component/runtime model, streaming RSC data and HTML so the React client can reconcile server and client component trees.
