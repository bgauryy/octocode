### Q35 — How does Vitest execute a single test? (`runTest`)

In `vitest-dev/vitest`, read `packages/runner/src/run.ts`. What are the key steps in `runTest(test, runner)`, and how does Vitest handle `retry` and `repeat`?

## Answer

- `runTest(test, runner)` is exported from `vitest-dev/vitest` at `packages/runner/src/run.ts`.
- It first calls `runner.onBeforeRunTask?.(test)`. If the test is not in `run` or `queued` mode, it emits `test-prepare` and `test-finished` and returns; if the result already failed early, it emits `test-failed-early` and returns.
- For a runnable test it initializes `test.result = { state: 'run', startTime: unixNow(), retryCount: 0 }`, emits `test-prepare`, registers the running/current test, finds `suite = test.suite || test.file`, and uses `runner.trace` spans.
- Execution is nested loops: `repeatCount` runs from `0` through `test.repeats ?? 0`; inside that, `retryCount` runs from `0` through `getRetryCount(test.retry)`.
- Each try is wrapped in `callAroundEachHooks(suite, test, async (fixtureCheckpoint) => { ... })`; before running the callback it calls `runner.onBeforeTryTask?.(test, { retry, repeats })` and records `test.result.repeatCount`.
- It runs `beforeEach` hooks, then either `runner.runTask(test)` or the test function from `getFn(test)`, both through `limitMaxConcurrency`; after the callback it calls `runner.onAfterTryTask` and marks the result `pass` unless already failed.
- Failures from the test, hooks, task-finished hook, afterEach, fixture cleanup, `onFinished`, or `onFailed` are recorded with `failTask(...)`.
- Cleanup order includes `afterEach`, cleanup hooks returned by `beforeEach`, fixture cleanup from the checkpoint, `onFinished`, `onFailed` for failed tests, `runner.onAfterRetryTask`, and then remaining fixture cleanup from `callFixtureCleanup(test.context)`.
- If the test becomes pending/skipped it sets mode/result to `skip`, emits `test-finished`, clears current/running test state, and returns.
- Retry handling: a pass breaks the retry loop; a fail retries only when `retryCount < retry` and `passesRetryCondition(test, test.result.errors)` is true. It resets state to `run`, increments `test.result.retryCount`, waits `getRetryDelay(test.retry)` if configured, and emits `test-retried`.
- Repeat handling: `repeats` controls the outer loop, so the test body can be executed multiple repeat cycles; retries are evaluated within each repeat cycle.
- At the end, `test.fails` inverts expected-failure semantics, the running/current test is cleaned up, duration is set, `runner.onAfterRunTask?.(test)` is called, and `test-finished` is emitted.
