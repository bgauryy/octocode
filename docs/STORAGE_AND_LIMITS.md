# Octocode home, storage and limits

What Octocode keeps on disk, how long, and which limits are fixed. To change a setting, see [Configuration](CONFIGURATION.md).

## Where everything lives

The **Octocode home** is one folder shared by the CLI, the MCP server, the VS Code extension, and installed skills: `~/.octocode` on macOS and Linux, `%USERPROFILE%\.octocode` on Windows. Its location ignores `XDG_CONFIG_HOME` and `APPDATA` (Octocode reads those only where other tools keep their files: git's global ignore file and editor MCP configs). To move it, set `OCTOCODE_HOME=/custom/path` for every product. Use [cache clearing](OCTOCODE_CLI.md#clear-tool-caches) to remove retained work while preserving checkouts. Current clone outputs live in `clones/`; older versions stored them under `tmp/clone/`. Deleting `credentials.json` and `.key` signs you out.

| Path in the home | Owner | What it holds |
|---|---|---|
| `.octocoderc` | you | Global Octocode settings. See [`.octocoderc`](CONFIGURATION.md#set-a-value). |
| `.env` | you | Trusted environment fallbacks: tokens, the classification key, third-party keys. Only this file may set [home-only keys](CONFIGURATION.md#where-every-value-comes-from). |
| `credentials.json`, `.key` | Octocode | The encrypted GitHub login and its key. `auth logout` removes both. |
| `.credentials.lock` | Octocode | Serializes credential writes between processes. |
| `skills/` | Octocode | Skills installed with `npx octocode skill install`; hosts such as Claude, Cursor, or Codex link to these copies. |
| `clones/` | output | `ghCloneRepo` checkouts, keyed by owner, repo, commit, sparse selection, history depth, and GitHub host. Each is a linked git worktree of a shared store under `clone-store/`. A clean checkout at the resolved commit is reused; one with local edits is refused and kept. |
| `clone-store/` | working state | One shared partial (blobless) bare git store per GitHub host, owner and repository, so a second commit or sparse selection of a repository fetches only the objects it lacks and each checkout costs its files, not another clone. A clone with `historyDepth` above 1 gets a private store per commit and depth, because git cannot shorten a shared store's history. It is outside every read root and closed even when a workspace or `allowedPaths` entry contains the home: tools read the worktrees under `clones/`, never the store. A crashed row's stage worktree under `tmp/clone-tmp` is removed by the next row of that store once its process is gone. Deleting it leaves the worktrees intact but unreadable by git: they are refused as dirty and kept until you delete them, then cloned again. A store that held a credential-named blob is replaced by a new generation, and an old generation is removed once no worktree uses it. |
| `tmp/response-pages/`, `tmp/continuations/`, `tmp/section-assessments/`, `tmp/lsp-answers/`, `tmp/graph-rows/` | retained work | Saved pages, issued continuations, section assessments, the LSP provider evidence selected by a continuation, and the complete ordered rows of a graphQuery `issues`, `impact` or `drift` answer, so its later pages slice them instead of computing them again. Clearing them invalidates their handles; a graph page whose rows are gone computes them again. |
| `tmp/capture/url/` | output | Freshly captured URL text and images exposed through inspection paths, retained for 24 hours. Fresh URL requests fetch again. |
| `tmp/materialize/v3/` | output | Files materialized at an immutable commit SHA for local inspection. Its manifest records each published file's bytes and SHA-256. The snapshot is the only store of these bodies: no saved provider answer keeps them. A repeat materialize keeps a file whose copy still matches the manifest and reads only the others again. |
| `tmp/ratelimit/` | coordination | Last-known GitHub rate-limit state, shared across processes. `ghCloneRepo`'s git transfers read and write the same per-host, per-token file as API calls (secondary cooldowns, open circuits), under the same storage setting. |
| `tmp/clone-locks/`, `tmp/clone-tmp/`, `tmp/git-home/` | working state | Clone locks (one per checkout and one per shared store), staging, and an isolated git home. |

One home holds one user's retained work and outputs. Every clone call checks the caller's GitHub access and resolves the ref to a commit; it fetches that commit unless a checkout of it is already verified (HEAD is the commit, no local changes), which it reuses; local tools can read checkouts under `clones/`. On a host that serves several users or tokens, give each tenant its own `OCTOCODE_HOME`.

Clone git runs without your git config. It keeps `PATH`, the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, either case), and CA bundles (`SSL_CERT_FILE`, `SSL_CERT_DIR`, `GIT_SSL_CAINFO`, `GIT_SSL_CAPATH`, `CURL_CA_BUNDLE`) from the runtime environment; a project `.env` cannot set them.

Native HTTP clients also honor `SSL_CERT_FILE` and `SSL_CERT_DIR` from the process environment. PEM certificates supplement the operating system trust store; unreadable, empty or malformed configured stores fail client construction. Certificate verification stays enabled. `SSL_CERT_DIR` uses the platform path-list separator.

A skill without a project writes reports and state to a named home folder, for example `research/` or `agents-communication/`. Inside a project, skills use `<project>/.octocode/`, which also holds the workspace `.octocoderc` and `.env` and `graph/` (the stored code graph, unless `local.graphHome` moves it into that directory's `octocode-graph/`).

## Cache storage and lifecycle

Fresh local reads, AST, LSP and classification requests recompute their answers. The one exception is a repeated `next.nextCandidatePage` cursor of a classified read: the runtime keeps the page that cursor judged, in memory only (never on disk, in either storage mode), for the idle retention of continuations, and the repeat replays it with no provider call; its receipt reports `calls: 0` and keeps the models and the `remainingInputTokensEstimate` of the original page. The saved page is bound to the cursor, the source content and the provider, so an edited source is refused as stale, never answered from it. A runtime that keeps its state between CLI calls (the daemon) keeps these pages between them; eviction, closing the runtime, a restart or a new process judges the page again, and the receipt shows those calls. A page that left candidates to a provider retry is not kept. GitHub and registry answers are kept under `<OCTOCODE_HOME>/cache/provider-answers-v2`, one credential and origin apart, and the origin decides what a repeat costs: a read named by a commit, blob or tree SHA sends nothing; a `Cache-Control: max-age` answer sends nothing until it lapses; past that, an `ETag` or `Last-Modified` validator asks, and GitHub's 304 is free of its rate limit. GitHub search offers neither, so its answer stands for 5 minutes. A multi-section pull-request read (GraphQL) offers neither too: once this credential has seen a REST read of a pull request, its answer stands for the `max-age` GitHub stated there (60 seconds when last measured), and with no such read or no stated `max-age` a repeat asks again. A renamed repository's redirect (`301` to `/repositories/{id}`) states neither, so its route stands for 5 minutes: a repeat under the old name goes straight to the id, still names the rename, and states `data.observedAt`, the ISO time its route was observed; a route whose repository is gone is forgotten and the old name asked. A `404` is kept only for a path inside a commit GitHub proved to exist in the same request (it returned that commit, a tree or contents at its SHA, or answered a contents read there with a plain not-found while the repository answered), and then like the commit-pinned read it replaces; a missing commit, tree, blob or comparison, a miss at a branch or tag, and a missing repository are asked again. The proof must come from GitHub in that request, where a 304 counts: a replayed answer never proves a repository or commit, even inside its stated `max-age`, so when the repository's saved answer was replayed the miss asks GitHub once to confirm it (a free 304) before it is kept. A kept miss is saved under the name asked and under a rename's id, as a success is. An answer reused within the origin's own `max-age` is current by the origin's statement and carries no notice; one reused without asking inside either window, or served because the origin rate-limited the request, states `data.observedAt`, the ISO time it was observed. An answer any read would redact (one holding a credential), a read of a credential-named file, by contents or blob, and a changed-file list with a patch of one, by its name or a rename's old name, stay in memory only, and an answer unused for 7 days is dropped. `ghGetFileContent` refuses a credential-named file (`.env`, `.env.*`, `.envrc`, key and credential names, and their backups) or a file in a sensitive directory with `pathPolicyDenied` before any request, as a local read does; the home-only `security.credentialFiles: allow` opens credential names, never sensitive directories, with values redacted and the read kept in memory only. Under the same rule, by default, `ghSearchCode` lists such a file by path only, with no lines and no read; a pull request's head text that widens a patch is not read for it; and a lead to read it is dropped with a note. With credential files allowed, search lines and head text come back redacted. `ghStructure` materialize and `ghCloneRepo` never write such files, whatever the setting, and a history item's patch of one stays readable with its values redacted. OSV's advisory answers are not kept at all, because OSV states no lifetime and no validator for them. CLI and MCP also retain the exact evidence and progress behind issued continuations under `OCTOCODE_HOME`; there is no database or editor-local storage. A body held by both a saved answer and a continuation is one file with a hard link in each directory (or two copies where hard links are unavailable), so each keeps it for as long as it needs it.

`storage.mode: "persistent"` is the default. Set `storage.mode: "memory"` in `<OCTOCODE_HOME>/.octocoderc` (all workspaces) or `<workspace>/.octocode/.octocoderc` (one workspace), or set `OCTOCODE_STORAGE_MODE=memory`, to keep continuation state and provider answers in RAM only. Each runtime uses its own resolved policy and home. Persistent state is read from disk without a duplicate memory copy; memory state lasts only within its runtime.

Memory mode disables clone, directory and exact-file materialization (`ghCloneRepo` and `ghStructure` with `materialize` answer `persistentStorageDisabled` before any GitHub request), persisted continuation reads and writes, automatic maintenance, rate-limit mirrors and stats writes. File reads still return content without a materialized `localPath`. Explicit graph builds still publish their requested snapshots under the workspace's `.octocode/graph/` (or `local.graphHome`'s `octocode-graph/`), but keep extraction intermediates in memory and never save `.facts` checkpoints. The setting does not delete existing files or credentials; managed language-server installations, compiled programs, HTTP connections and live language-server protocol state are separate operational resources.

| Concern | Behavior |
|---|---|
| Cleanup | At most one sweep per 24 hours (`tmp/.last-cache-maintenance`). Aged materialized snapshots are removed under their own locks; old tree staging, rate-limit mirrors and URL captures are swept by age. Entry stores enforce their own TTL and byte budgets; the sweep also removes every entry past its TTL (a section plan's source text included), so expired work does not wait on disk for the next write to its store. Clone outputs and `clone-store/` are never expired or evicted. |
| When | Synchronously at native runtime start: once per CLI process and at MCP server start. No background timer. Skipped in `memory` mode or when `tmp/` does not exist. |
| Failure | Best-effort; an unavailable or read-only state home never blocks the CLI or MCP startup. |
| Ownership | Only Octocode-owned directories; other `tmp/` content stays. |
| Manual | Stop separate MCP processes, then run `npx octocode cache clear` from the workspace. It drains warm CLI servers and clears the configured home's retained work plus this workspace's graph extraction checkpoints. See [cache clearing](OCTOCODE_CLI.md#clear-tool-caches). |

Published graph snapshots, materialized files and captures are inspectable outputs. Graph extraction checkpoints support interrupted jobs and are discarded after successful publication. Response pages and section assessments keep settled evidence so pagination does not repeat upstream requests or inference; issuing a new request performs fresh work. Credential selection also reloads its source on every request.

Retained-work limits are derived from one budget, not fixed numbers: memory state shares the process memory budget (an eighth of the memory available to the process, within 512 MiB to 2 GiB; a container's cgroup limit counts), and each store directory's disk budget equals that same value, which is also the largest single entry. They are per store, not a process-memory limit. Disk admission serializes writers and reserves space before publication. Entry headers and bodies count toward the budget; filesystem allocation, bookkeeping and one temporary atomic-write copy do not. Failed writes are reported to the continuation owner, which must return complete evidence or an explicit refusal instead of issuing an unreachable handle. A write a continuation depends on waits out a busy store up to its request's deadline, or until the request is cancelled; without a caller budget that deadline is a 24 h bound on that one wait, a limit of what a deadline can represent that never ends the request itself; a write only later reuse reads waits one second, then goes unsaved, and the call says so in a notice on stderr: the answer it returned is whole, and a later call reads it again. Existing retired result-cache directories can be removed with `cache clear`.

## Fixed internal limits

These are code constants, not settings (one owner: `RuntimeLimits` in `packages/octocode-native/crates/runtime/src/execution/limits.rs`). They have no environment or settings-file overrides.

| Limit | Value |
|---|---|
| Network request timeout (GitHub, registries) | 30 s, a stall limit: connect plus the wait for headers, and each body read, may wait at most 30 s for bytes, so a response still flowing is never cut; the call's deadline and a cancel end the request, retries and slot waits |
| Git clone and fetch transfer (`ghCloneRepo`) | a stall bound, not a wall clock: git ends a transfer that moves under 1 byte/s for the 30 s network timeout (`http.lowSpeedLimit`/`http.lowSpeedTime`), so a transfer still sending data is never cut; the caller's deadline and a cancel end any git step, and no git step has a cap of its own |
| Classification request time | none of its own: the caller's budget, when it sets one, decides; otherwise only a cancel ends it, since a model's time follows its input and the provider documents no limit |
| Retries after a failed request | 3 |
| Automatic response page | 20,000 characters (`responseChars` per call, up to 50,000) |
| URL captures | 24 h retention |
| Classification requests in flight per endpoint | 10 |
| One classification page or `sections` batch | About 131,000 characters of states and questions, at least one unit; the next page takes the rest |
| Language-server memory | 25% of host RAM, between 4096 and 8192 MiB (per-server `maxMemoryMb` overrides) |

Saved-page sizes are fixed too. A tool call has no fixed time budget on any surface (CLI, warm server, MCP): only a caller sets one, today an embedder's `timeoutSecs`, and a call cut by it answers an honest partial with its continuation. Without a caller budget, each layer's own limit ends the work (a hung language server at its request timeout; a URL-capture page or classification provider that sends nothing for 300 s, a stall bound reset by every read, so a slow answer still flowing is never cut; a memory budget), and a cancel stops it. A language server that keeps reporting `$/progress` or using CPU is waited for with no limit; one that spins its CPU without answering is a known residual that only a cancel ends. A cancel is: MCP `notifications/cancelled`, CLI Ctrl-C, or a warm-server client that leaves. The warm-server client waits for its reply as long as the server's budget allows: with none, until the reply, the server closing, or Ctrl-C.

- **GitHub rate limits:** a spent core or GraphQL quota (GitHub meters both over an hour) fails at once with `rateLimited`, its reset and `retryAfter` (plus `next.retry`), and a later call on the same quota is refused the same way before it is sent: the caller decides, and no call holds for that reset. A call waits out a secondary-limit cooldown or `retry-after`, a spent search or code-search quota (minute windows) and search pacing, and fails at once the same way only when that wait ends after the tool call's own deadline; no fixed wait cap or client-side window decides. Without a caller budget that deadline is the 24 h bound one wait can represent, which never ends a request by itself, and a cancel interrupts the wait. `retry-after` wins over the reset header. Waiting does not spend the request timeout. While a wait of a second or more lasts, the call reports it (the limit, seconds left, and why: quota reset or `retry-after`, secondary cooldown, or search pacing) when it starts and every 10 s after: an MCP client that sent `_meta.progressToken` receives each line as `notifications/progress` before the result, so a host that resets its timeout on progress keeps the call alive; a CLI call prints the same lines on stderr (through a warm server, with the call's other notices once it ends). Search and code-search pacing follow the quota GitHub reports for each resource (`x-ratelimit-resource`, `-remaining`, `-reset`): planned searches the remaining quota covers go back-to-back, and only searches beyond it are spread over the time until reset. Until a response reports the `code_search` quota, planning assumes GitHub's documented default for authenticated code search, 10 a minute ([search rate limit](https://docs.github.com/en/rest/search/search#rate-limit)); this is an assumption, not a cap, and the first response replaces it (so does any quota window that has ended). Processes sharing a token share the last quota GitHub reported and the start of each paced search through one file lock on `tmp/ratelimit/` (keyed by host and a token hash, never the token); a start stamp dated more than two minutes ahead is ignored, so a crashed process never wedges it. If the file or its directory cannot be read, written or locked, the call goes ahead under this process's own pacing and one warning goes to stderr.
- **Classification gate:** one process-wide gate per provider endpoint allows 10 requests in flight; one tool call may use up to three quarters. Throttling (429/503/529) halves the gate, `Retry-After` pauses every caller, and the gate recovers gradually.
- **Context selection:** units the budget leaves unassessed stay unknown and never spill into the default evidence body; recovery: [context selection](OCTOCODE_TOOLS.md#context-selection).
