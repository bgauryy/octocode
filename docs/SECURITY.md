# Security

The native Rust runtime shared by CLI and MCP enforces every rule on this page. Interfaces cannot bypass it, and there is no TypeScript fallback.

```text
contract validation → configuration and capability admission → input bounds and dangerous-key checks
  → provider or local path authorization → bounded, cancellable execution → content sanitization
  → output-contract validation and safe rendering
```

A sanitization failure discards the unsafe value and returns a typed error. Bulk rows are isolated, and each successful row passes the same checks.

## Input validation

The generated `@octocodeai/octocode-core` schemas reject unknown fields and invalid operation combinations. Native validation also rejects ordinary parameter strings over 10,000 UTF-16 code units, arrays over 100 entries, nesting deeper than 20 levels, `__proto__`/`constructor`/`prototype` keys, and invalid paths, cursor identities, snapshots, hashes, and numeric bounds.

Clasify literal `content` uses its declared serialized-content limit instead of the ordinary string limit; nested values remain scanned and bounded. Credential-looking object keys are rejected without echoing or renaming them.

Public calls accept `{queries:[...]}` with optional `responseChars`, or an issued `{cursor}`. A cursor saves the complete normalized request and private progress, bound to its target tool, access identity, workspace, configuration, and contract. Caller-supplied private progress is rejected; invalid or expired handles never restart the original work.

Credentials are acquired after request admission and pinned for the request lifetime. Query locators and controls never accept credentials; literal classification content is sanitized before inference.

## Content sanitization

One ordered secret-pattern set and native scanner cover cloud, AI-provider, version-control, package-registry, database, payment, communications, private-key, bearer-token, and connection-string formats (300+ patterns). File-context patterns apply only to matching path classes, to reduce false positives. Text that leaves the process and names no file (`clasify` literal `content`, a saved provider answer, a captured URL) is judged as if it could be any file: every file-context pattern applies to it, except bare shapes that only a named context tells from any other value.

The runtime scans untrusted provider and filesystem content before rendering. Detected values become typed redaction markers with warnings, and only a secret's own bytes are replaced, however long the text around them. A local file's redaction is decided once, over the whole file, and every local tool serves it: a `localSearch` row, an `astSearch` node or capture, an `lspSearch` snippet and a graph fact show what a `localFetch` read of the same lines shows. So a value named a secret by a key on another line (across a comment, a blank line or a wrapped expression) is hidden in each of them, and code is never hidden in one view and readable in another. Each hidden value shows as the same typed marker in every view and in every range of a read; an `astSearch` node that starts partway into a value hidden across lines shows that value's marker too. A declaration name that `astSearch` lists is the identifier as the file writes it, hidden only when the name itself is a redacted value. A file larger than one whole read is judged in windows by `localSearch`. Text a language server writes (a hover, a diagnostic message, a symbol's name or detail) has no place in a file, so `lspSearch` judges it with the files it is about: the file the query names, every file the response names, and for a hover the files that declare the symbol and its type. Each value the whole-file pass replaced in one of those files shows in the server's text as the same marker a `localFetch` read shows. A string literal that a hover, or the quoted code of a diagnostic message, takes from a file none of those locations name shows as `[REDACTED]` with a `serverTextWithheld` warning, because the key that would name it a secret was never read; the same happens to quoted values in symbol names and details when one of those files cannot be judged whole. A single-quoted name in a diagnostic's prose is not treated as a literal. A final recursive pass sanitizes nested strings and keeps continuation and location structures executable. A search answers on raw text, so a guess at a secret can be confirmed by a hit, though no secret text is returned: the row shows the redacted line and a `redactedMatches` warning. Hiding the hit would claim an absence that is false, so this stays a documented low-severity limit. An in-memory `localFetch` `matchString` searches the redacted text. Email masking in GitHub output is opt-in: `OCTOCODE_REDACT_EMAILS=true` or `output.redactEmails`.

`ghSearchCode` never lists GitHub's index fragments. Repo-scoped rows show lines read from the blob and judged with it; the only fragment text used is the top file's read lead, and only when it spells a term the caller searched for. A language server's hover text, symbol names and error messages pass the output gate; its stderr, log messages and symbol details reach no row. A location row quotes the file, so a line of a key block or a private JSON Web Key member is hidden there too.

### What the scanner cannot recognize

Recognition needs a marker or a name in the text. These stay readable, because matching them would redact ordinary text:

- **Base64 with nothing around it:** a key body with its armor cut off, `wg genkey` output on its own, a bare line of a key in a language server's error message, or a JSON Web Key member with no `kty` in its object. Only the shape is left, and a shape rule over this repository's 871,150 tracked lines matched 5 lines, none of them a key.
- **Armor no tool writes:** typographic dashes (`——BEGIN`, from a word processor) or lower case (`-----begin`). No key parser reads either, and a looser marker would match prose such as `---- begin private key section ----`.
- **A Kubernetes Secret in YAML under another file name:** `kind: Secret` in `notes.md`, `deploy.sh` or `secret.yaml.j2` reads as plain text, in a tool's output and a language server's hover alike. That pattern applies to `*.yaml` and `*.yml`, and to text that names no file. As JSON, a Secret names its kind in the object that holds its `data` and `stringData`, so those are hidden in any file, at any nesting and any size.
- **A source over 10 MiB:** it reads in streamed windows, whether whole, by range or by `matchString`, and one pass over every byte looks for a `kty` or `"kind": "Secret"` key, or `kind: Secret` at a `*.yaml` or `*.yml` path. A source that spells one is walked once more, as a whole read's scan walks it, so a Secret's `data` and `stringData` and a JSON Web Key's private members are hidden wherever their `kind` or `kty` lies, and nothing else is. If that walk's structure outruns the memory budget ([limits](STORAGE_AND_LIMITS.md)), every JSON string that is no member's name and every YAML value a window shows is hidden instead, with a warning that says so, and `localSearch` withholds the rows that show one, with their hits still counted. A window is judged by its own text beyond that: a minisign key whose base64 lacks the format's header stays readable, because it can't be told from any other long string, and a secret over 128 KiB whose name lies further from a page than that reads as plain text. The trade runs the other way for a JSON Web Key: in a streamed window, a member named `d`, `p`, `q`, `dp`, `dq`, `qi`, `k` or `priv` holding a long base64url value is hidden even with no `kty` in its object, and at a `*.yaml` or `*.yml` path so is a `name: <base64>` line.
- **The length of a hidden value:** a byte page's offsets count the source's bytes, so a page that ends after a hidden value shows how long it was. Its text never does.
- **A line over 10 MiB:** it reads in byte pages in `localFetch`, and its hits read as text in `localSearch`, whose row holds a window of the line around the hit: the read named in `related` reaches the rest. Search holds that line whole while it judges it, and a line over 64 MiB makes it hold its file, within the 512 MiB line search ceiling. `astSearch` refuses a file over the 10 MiB whole-read limit with `fileTooLarge`, and names no secret.
- **Evidence split across strings:** each string of a `clasify` `content` value is judged alone, so a manifest sent as an array of lines has no line naming both its kind and its value.
- **A key body no format writes:** base64 spaced into groups inside an armor, or, with no END in the file, body lines under 40 characters after a line of prose. Inside an armor only a line shaped like key text is hidden, so that code after a literal marker stays readable, and these lines read as ordinary words.

### Accepted false positives

The scanner fails closed, so these are hidden although they hold no secret:

- **An app config shaped like Docker's:** `{"auths": {"github": {"auth": "oauth"}}}` is hidden, because an `auths` map with an `auth`, `password`, `identitytoken` or `registrytoken` member has Docker's shape and no walk can tell an app's config from Docker's.
- **A regular-expression literal that describes a key shape:** `r'^sk-[A-Za-z0-9]{48}$'` and `"^sk-[A-Za-z0-9]{48}$"` are hidden like any literal under a credential name, because a real key pasted into a pattern must stay hidden and no per-language literal grammar tells the two apart.
- **Shell values:** they are read line by line, without a shell grammar, so a quoted value can be hidden further than its shell scope.

### Classification egress

`clasify` and `classification` send text evidence to the configured provider (`OCTOCODE_CLASSIFICATION_API_HOST`, default Jev, and home-only like every API endpoint, so a repository cannot redirect a key); classification sends nothing without a key. Context selection sends the classifier predicates, optional `classification.context`, and authorized candidate evidence: paths with returned matches, raw text windows with source line numbers, or the selected snippets of result rows. It does not hydrate unseen bodies or widen requested fields, sections, or ranges. Public `clasify` can also send explicitly referenced images. Each evaluation request carries:

- the model and the caller's keyed questions, with optional task `context` and secret-bearing values sanitized;
- one state: the caller's literal `content`, or the complete selected source captured through the authorized reader and sanitized like a direct tool call;
- optional explicitly referenced PNG/JPEG assets, captured internally and sent as their original bytes. Image pixels and metadata are not text-scanned or redacted.

The MCP server reads the key once, at start ([configuration reload](CONFIGURATION.md)). Removing the key from the configuration does not stop a running server from sending evidence with it, and a key added later needs a restart; the CLI reads it on every call. Restart the server to make a removal take effect.

Treat questions and selected evidence as disclosed to that provider. Ordinary calls without `classification` send no evidence. Catalog discovery does not probe the classification provider; an explicit `clasify operation:"models"` request fetches its model catalog without sending source evidence. Source and image locators pass the input and path policy before capture; credential-looking locators are rejected. The credential name rule under [Filesystem policy](#filesystem-policy) applies to local and GitHub sources: a GitHub file with such a name is refused with `pathPolicyDenied` before any fetch, and a classified `ghSearchCode` page leaves such a row unread, unjudged and disclosed in `warnings`, while its other rows are judged. A `ghGetFileContent` read without `classification` sends nothing to the provider and still returns the file, redacted. A URL source is fetched over HTTPS only, under the address policy at connection and every redirect, with bounded size and redirects, and no stored credential is sent to that origin, so it is anonymous and public-only and the name rule does not apply to it. Image bytes stay out of tool responses, which return capture identity and a saved inspection path instead.

### Advisory egress

`securityCheck` is the only tool that contacts OSV (`api.osv.dev`, operated by Google). MCP offers it only once you set `tools.enableSecurityCheck` (`OCTOCODE_SECURITY_CHECKS=true`); that setting is home-only, so a repository can turn it off but cannot turn it on. The CLI always offers it. Either way a call sends OSV only public package coordinates, an advisory id or a commit hash, with no credential, path or request text, and only when it runs. A registry confirms the name first for the ecosystems with a registry reader; for the others the name goes as the caller wrote it. The same calls also read GitHub, with the same GitHub credential as the other GitHub tools or anonymously without one: a package's name and version (GitHub's advisory database) and the `owner/name` its registry names, a GHSA id, and a `repo` with, for `commit`, its hash. OSV never receives a `repo`, and receives a repository's advisory ids only when GitHub says the repository is public. What each operation sends, and what it refuses to send, is listed once in the [tools reference](OCTOCODE_TOOLS.md#securitycheck).

Answers are not stored, because OSV states no lifetime for them. OSV publishes no overall data licence or API terms that we found. Records keep their source databases' licences (GitHub Advisory Database: CC-BY 4.0), so each row names its `source` and links its record, and that attribution should travel with anything you republish.

## Filesystem policy

- Allowed roots are the workspace root (`WORKSPACE_ROOT` / `local.workspaceRoot`, else the process cwd), `ALLOWED_PATHS` / `local.allowedPaths`, and `OCTOCODE_HOME`. The OS home is **not** allowed unless one of these covers it.
- Relative paths resolve against the workspace root.
- Relative traversal and paths outside the allowed roots fail with `outsideAllowedRoots` on every local tool.
- System directories such as `/etc` stay denied even when listed in `ALLOWED_PATHS`.
- Credential filename and extension rules apply to files, not confirmed directories: source folders such as `src/credentials/`, `src/source.pem/`, `src/private/` and `secrets/` remain readable, searchable and listable. Discovery and reads still deny credential-store directories (`.ssh`, `.aws`, `.kube`, `.gnupg`, …) and credential-named files: environment files (`.env`, `.env.*`, `*.env`), private keys and certificates (`*.pem`, `id_rsa`), keystores, credential files, shell history, browser login stores, infrastructure state and wallets. Credential filenames with backup suffixes remain withheld. Credential files are matched by the name shapes tools write, not one exact name. A name holding one of the words `kubeconfig`, `credentials`, `secrets`, `client_secret` or `accessKeys` as a token (bounded by the name's start or end, `-`, `_` or `.`) is withheld when it has no extension or a config extension (`.yaml .yml .json .conf .cfg .config .ini .toml .txt .csv .xml .properties`): `kubeconfig-prod.yaml`, `gcp-credentials.json`, `app-secrets.yaml`, `client_secret_<id>.apps.googleusercontent.com.json`, `<user>_accessKeys.csv`. `service-account`, `service_account` and `firebase-adminsdk` names are withheld as JSON key files. Also withheld: `*.kubeconfig`; kubeadm's `admin.conf`, `super-admin.conf`, `kubelet.conf`, `controller-manager.conf` and `scheduler.conf` in a `kubernetes/` directory; `k3s.yaml` and `rke2.yaml`; SSH keys with a suffix (`id_ed25519_work`, `id_ecdsa_sk`); `_netrc`, `pgpass.conf`, `npmrc` and `htpasswd`; Terraform state under any rotation (`*.tfstate`, `terraform.tfstate.<timestamp>.backup`) and variables (`*.tfvars`, `*.tfvars.json`); and backup, editor and rotation copies of any withheld name (`.bak`, `~`, vim's `.name.swp`, `.tmp`, emacs `#name#`, `.1`). Windows names are judged as Windows opens them (trailing dots and spaces dropped), and every read is judged again by the file's canonical path. A code or docs file that only names a word (`kubeconfig.go`, `credentials.ts`, `secrets.md`) stays readable, as do names that describe a credential rather than hold one: a token `schema`, `template`, `example` or `sample`, Kubernetes `service-account.yaml`, and `secrets` manifests with a `sealed` or `external` token (`sealed-secrets.yaml`, `external-secrets.yaml`), a word inside another word (`secretsmanager-….json`), and credential-worded files in translation folders (`i18n/`, `l10n/`, `locale/`, `locales/`, `translations/`) or `.github/workflows/`. A config-shaped file holding a word elsewhere (`credentials.yaml`) is withheld. `security.credentialFiles: allow`, which only the user's home configuration or process environment can set, lifts the credential-name rule in the workspace and allowed paths; it never lifts the directories above, the Octocode home, or files and dot directories directly in the home directory. Content redaction still applies, though it recognizes secret formats, so a secret in no known format can appear in results. Graph snapshots keep withholding those files, `clasify` and `classification` keep withholding them from local and GitHub sources alike, and results of local reads stay in memory. Names compare as a case-insensitive filesystem compares them, on every filesystem: `.SSH/config`, `KEY.PEM` and `.Env.local` are withheld on a case-sensitive one too. A file such as `secrets/prod.env` or `private/key.pem` stays withheld by its own name; any other file's secret-shaped text is redacted by the content scanner. A hard link to `.env` under another name is read by its own name, since name rules see only the name. The same limit holds for a GitHub repository symlink: GitHub documents that its contents API answers a link to a file in the repository with that file's content, so a link such as `notes.txt -> .env` is judged by its own name. Graph scans disclose paths withheld by policy as coverage gaps without listing their contents or guessing how many files a withheld directory contains.
- Symlinks are revalidated against their canonical targets; escaped descendants are rejected.
- File type, size, mutation, and snapshot checks run before evidence is returned.

Denial messages name the path as requested or relative to `~`; outside-root denials list the allowed roots.

[Configuration](CONFIGURATION.md#tool-availability-cli-and-mcp) controls MCP catalog exposure. Those switches and tool lists do not hide CLI commands. Both interfaces still enforce the path and content protections above, credential requirements, and storage policy when a call runs.

## External processes

Search, AST, providers, response shaping, and bulk orchestration are embedded Rust. External processes run only for:

- system Git for `ghCloneRepo`: HTTPS remotes, plus plain `http` only when the authorized remote itself is a loopback endpoint (`localhost`, `127.0.0.0/8` or `::1`), enforced for every remote, redirect and promisor fetch through `GIT_ALLOW_PROTOCOL`, so `file`, `ssh` and `ext` transports are refused; git 2.36 or newer; every checkout is a worktree of a shared partial store under `<home>/clone-store/`, which is outside every read root and closed in the path policy even when a workspace contains the home (tools read only the worktrees), and a store that ever held a credential-named blob is replaced rather than cleaned; bounded arguments and output, process-group cancellation, staged publication; each run's helper directory is named for its pid, and the next git run removes those whose process is gone. The token is never in argv, a file or `.git/config`: git reads it through an owner-only `GIT_ASKPASS` helper that holds no secret and takes the token from the git process's own environment, answering only the authorized origin's prompts;
- configured language servers, launched without a shell and owned by the native LSP pool. **A language server can run code from the repository it opens:** MSBuild `<Exec>` through csharp-ls, Gradle scripts through jdtls, and a `.cargo/config.toml` `rustc-wrapper` through rust-analyzer. So no server starts on code Octocode fetched itself: a file or workspace root that resolves into its `ghCloneRepo` or `ghStructure materialize` checkouts or URL captures, symlinks followed, or a workspace root that holds any of that code (as `$HOME` does once something is fetched, since servers enumerate dot directories), gets a refusal naming the tools that run nothing (text, AST, and graph from inside that directory), and prewarm and leads skip it. Only `lsp.trustFetchedCode` in your home settings opts in; a workspace `.octocoderc` or `.env` cannot, so a fetched repository cannot trust itself. On a local checkout you chose to open, a server runs as usual, but without running its Cargo build scripts or proc macros: a query whose `rustContext` sets `buildScripts` or `procMacros` is refused (`errorCode:"policy"`, no server started) unless `lsp.allowBuildScripts` (`OCTOCODE_LSP_ALLOW_BUILD_SCRIPTS=true`) is set in your home settings or the process environment, which a workspace `.octocoderc` or `.env` cannot do. Use `lspSearch` only on a repository you would be willing to build; with a `compile_commands.json`, clangd also keeps a background index under `<OCTOCODE_HOME>/lsp-workspaces/clangd/`, in folders only you can read. Each holds a copy of the database with recognized secrets in its flags replaced by a redaction marker, and clangd's shards: compile commands, symbol names and header doc comments of what the project's sources include. A secret in a `.clangd` flag or a header doc comment reaches a shard as written, because clangd writes them itself;
- `gh auth token`, the last GitHub credential source;
- `gh release verify`, for the attestation of an immutable language-server release, and `rustup which`, which asks rustup which toolchain ships `rust-analyzer` (auto-install off). Both are time-bounded and run without a shell.

Language-server provisioning accepts only assets from allowed HTTPS hosts. Each asset is checked against `managed.lock.json`, which is generated from GitHub's own asset digests, against GitHub's live digest (skipped and disclosed when the API is unreachable), and against the SHA-256 and size of the downloaded bytes, all before extraction; an immutable release's attestation must also cover the asset when `gh` can verify it. It uses per-target locks and publishes atomically. The token reaches only the GitHub API host. Details: [LSP server lifecycle](../packages/octocode-native/docs/engine/LSP_SERVER_LIFECYCLE.md#resolution).

## GitHub credentials

Resolution, login, refresh, and logout: [AUTHENTICATION.md](AUTHENTICATION.md). Security properties:

- Tool query fields never accept tokens. An env token goes only to the host of `GITHUB_API_URL`, which only the shell or home config can set.
- `credentials.json` uses AES-256-GCM (16-byte IV, authentication tag, ciphertext) with the key in `.key`. Both are `0600` on Unix; a newly created home directory is `0700`. Writes are locked and atomic. Corrupt or unauthenticated files are rejected and not overwritten; symlinked credential files and Unix hard links are rejected. The adjacent key does not protect against someone who can read both files.
- `gh auth token` runs without Octocode's token variables, bounded to 5 seconds.
- `.octocoderc` never supplies GitHub tokens, and every `.env` file blocks bootstrap variables such as `PATH`, `HOME`, and `NODE_OPTIONS` ([rules](CONFIGURATION.md#where-every-value-comes-from)).

GitHub endpoint, credential, session, and cache identities are partitioned. Pagination redirects must stay same-origin. Retries and rate-limit delays are bounded, response bodies are capped, and GraphQL partial failures stay explicit.

## Cancellation and lifecycle

Requests enter through bounded queues. Cancellation and timeouts propagate through provider requests, filesystem work, Git, and LSP. A dropped caller releases its admission and resources; shutdown joins workers and ends pooled processes. Partial or capped evidence is never labeled complete without an executable continuation or an explicit terminal diagnostic.

## Reporting vulnerabilities

Open a private GitHub security advisory for the Octocode repository, not a public issue.
