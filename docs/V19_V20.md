# Upgrading from Octocode 19 to 20

On 60 research questions, Octocode 20 scored 9.69 out of 10 against 19's 9.34 (5 wins, 3 losses, 49 ties, 3
unresolved). It had far fewer failed tool calls (26% → 5%), read 45% fewer input tokens per question and cost 26%
less. On the 30 GitHub questions, an agent with only the GitHub CLI (`gh`) scored about the same as v20 (9.57 against
9.52) for 36% less. v20 has 15 tools against v19's 10 and ten new skills, and it renames tools, skills and settings.
It no longer reads the v19 setting names, so start with the checklist.

## Upgrade checklist

1. Update prompts and agent instructions that name v19 tools, fields or skills ([tool map](#tool-map),
   [removed skills](#removed-skills)).
2. Rename your v19 settings: v20 ignores the old names. Drop the removed settings; they have no effect
   ([both lists](#renamed-and-removed-settings)).
3. Add each directory outside your workspace that the agent reads to `ALLOWED_PATHS` ([safety](#safety)).
4. Optional: turn on the opt-in tools you want, such as `securityCheck` and `clasify`
   ([settings for new features](#settings-for-new-features)).
5. Restart your MCP client, then run `octocode config list` from the directory where your agent starts Octocode.
   Each setting shows its effective value and the file or variable it came from.
6. Run `octocode auth status`. The output names the GitHub account and the token source that v20 selected.

With the npm launcher, use `npx -y octocode` in place of `octocode`.

## Tools

### Tool map

v19 had 10 tools; v20 has 15. Every v20 tool also runs from the `octocode` command line.

| v19 | v20 | What you get |
|---|---|---|
| `ghSearch` `repositories` | `ghSearchRepo` | Repository search, split out of `ghSearch` |
| `ghSearch` `code` | `ghSearchCode` | Hits with line numbers and the commit, so the next read needs no extra search; a `path` naming a file is read directly and spends no code search |
| `ghSearch` `tree` | `ghStructure` | A repository's tree, branches and tags; tags by pattern (`v7.*`) with their commits |
| `ghGetFileContent`, `ghSearchHistory`, `ghGetHistoryItem`, `ghCloneRepo` | same names | — |
| `npmSearch` | `artifactSearch` (`ecosystem: "npm"`) | **8 registries:** npm, PyPI, crates.io, Maven, NuGet, Go, Packagist, RubyGems; a version leads to its source repository and release |
| — | **`securityCheck`** (new, opt-in) | Known vulnerabilities in **28 ecosystems**, including the 8 registries, GitHub Actions and Linux distributions, with the fixed version and severity |
| `localSearch` | `localSearch` | — |
| `localSearch` operation `structural` | **`astSearch`** | Code by shape in **13 languages**: functions that call, or skip, something; a file's symbol outline |
| `localSearch` operations `files`, `tree` | **`structureSearch`** | Files by name, size, line count or date |
| `localGetFileContent` | `localFetch` | A whole function with its exact lines |
| `lspGetSemantics` (`uri`, `lineHint`, `type`) | `lspSearch` (`path`, `line`, `operation`) | Each hit says whether it is a declaration, call, reference or import; without a language server it answers from syntax and says so |
| — | **`clasify`** (new, optional, billed) | Answers about evidence you have not read ([clasify](#clasify)) |
| `localAnalyzeGraph` | the [Octocode Graph](OCTOCODE_GRAPH.md) package | Imports, cycles and impact, outside the core tools |
| field `goal` | dropped; only `clasify` takes `mainGoal`, for its judge | Other tools drop a `mainGoal` or `reasoning` still sent, and say so once |

### How replies changed

| | v19 | v20 |
|---|---|---|
| A bad request | `Invalid input` | Names the field, lists the allowed ones and gives a working example |
| A missing package | an empty result | `notFound`, with the search to run next |
| Long results | different paging per field | One `next` per unfinished part, to follow until the answer is complete |
| Where the evidence is | in each row | Stated once, first: owner, repo, ref, commit and root; a local search, read or listing inside a git checkout states its `commitSha` |

- A call that sends a line pair, a cursor inside `queries`, or JSON text where a value belongs still runs, silently. A
  warning appears when the reading changed what was asked, such as a regex bracket read as text
  (``read queries[0]: matchString[1] as `def route\(` ``), and when a query's fields arrive without `queries`: they
  run as one row, and the warning says `queries` batches several.
- Continue an unfinished reply with `{"cursor":"…"}` alone, on every host.
- A comparison, a pull request or a commit search lists each commit that has only a SHA, date, author and headline
  as one line: `<sha> <date> <author>: <headline>`. On the 61 commits from axios v1.6.0 to v1.7.0, each commit takes
  29% fewer characters, and v20 lists all 61 where v19 showed 30 per page.
- A pull-request read whose `include` matches no changed file says how many files changed and names the nearest
  changed directories.
- A search hit inside a method names the declarations that hold it, the class included.

### Language servers

`lspSearch` returned the same references as v19 for 7 of the 9 languages measured. For Java v20 found 14 references
against v19's 10, and for C#, with no language server installed, v19 failed and v20 answered at syntax level.
Time to the first answer, one references query per language:

| Language | v19 | v20 |
|---|---:|---:|
| TypeScript | 1.2 s | **0.2 s** |
| Go | 5.0 s | **0.2 s** |
| Rust | 29.1 s | **1.5 s** |
| Scala | 22.3 s | **6.2 s** |
| Python | 0.6 s | 0.6 s |
| Java | **15.0 s** | 28.2 s |
| C | **0.4 s** | 3.7 s |
| C++ | **0.5 s** | 3.4 s |
| C# (no server) | failed | 0.5 s, syntax level |

v20 bundles the TypeScript server only. For other languages, install the server yourself, run
`octocode lsp-server install` for rust-analyzer or clangd, or add a server to your `lsp-servers.json`.

### clasify

`clasify` reads evidence you have not opened (a long file, many search hits, a web page or an image) and answers a
question about it with a score and the lines behind it. It is **off unless you add a provider key, and billed per
provider request** ([setup](OCTOCODE_CLASIFY.md), [settings](#settings-for-new-features)). Before sending, it checks
the planned requests against your `maxRequests` limit and refuses anything over it, without billing.

| Example | Without clasify | With clasify |
|---|---|---|
| Find weight-based eviction in a 4,996-line Java file | read 153k characters | **7k characters** (the answer and the cited lines); 2 billed requests |
| Rank 45 search hits by meaning | read all 45 hits | a 1.7k-character ranking in which the deciding lines rank 2nd and 3rd; 2 billed requests |

Use it when the question is about behavior in a lot of text, not for exact lookups.

### Improved skills

Eight skills are in both versions. The seven in `skills/` (`brainstorming`, `documentation`, `research`,
`rfc-generator`, `roast`, `scraping` and `skills`) changed in the same ways:

| | v19 | v20 |
|---|---|---|
| When the agent loads it | "Use when …" keyword lists | "Load this skill first when asked …", phrased like your request, and it names the neighboring skill for close cases |
| Main file (`SKILL.md`, whole file) | 44 lines on average | **31 lines**: it routes to detail pages and loads only the one the task needs |
| Shared guidance | each skill kept its own copy | one shared source for tool use, evidence rules and report templates, copied into every skill so one installed alone is complete; an outdated copy fails the skill check |
| Tool names | v19 tools (the research skill still taught `localAnalyzeGraph`) | the current tools; research teaches all 15 |
| Results | free-form | every skill defines its output; report skills can save Markdown and HTML reports |
| Where outputs go | a shared `.octocode/tmp/` folder (28 warnings across the 14 v19 skills) | the skill's own `.octocode/<skill>/` folder; its scratch in `.octocode/tmp/<skill>/` |
| Skill check, today's rules | 3 errors, 30 warnings | **none** in the shipped skills; 187 script tests and 78 checker self-tests pass |

`chrome-devtools` moved into its own package. Its trigger names the tasks (log in, fill a form, take a screenshot,
read console errors, inspect network requests, record a performance trace, run raw CDP), it covers what the Pi
`browser-agent` did, it defines its output, and it passes the checker (v19: 7 warnings). Ratings for the eight range
from 4.0 (`chrome-devtools`) to 5.0 (`research`, `skills`). v19 skills were never rated, and how reliably a host picks
the right skill was not measured for either version.

### Settings for new features

| To | Set | Default | Know before you turn it on |
|---|---|---|---|

| Get the CLI's text view in MCP replies | `OCTOCODE_MCP_RESULT=text` | `json` | — |
| Query a private or local package registry | `OCTOCODE_ALLOW_PRIVATE_REGISTRY=true` | off | Lets requests reach private, loopback or link-local addresses. |

### Renamed and removed settings

**Renamed: rename them.** v20 reads only the v20 names. A v19 name is an unknown key or variable and has no effect.

| v19 name | v20 name |
|---|---|
| `ENABLE_LOCAL` | `OCTOCODE_ENABLE_LOCAL` |
| `ENABLE_CLONE` | `OCTOCODE_ENABLE_CLONE` |
| `.octocoderc` local.enableClone (removed) | `.octocoderc` `tools.enableClone` |
| `OCTOCODE_TOKEN` | `GH_TOKEN` |
| `GITHUB_PERSONAL_ACCESS_TOKEN` | `GITHUB_TOKEN` |

**Removed: no effect.** v20 gives no warning for these in your environment; `octocode config` reports the
`.octocoderc` ones as unknown settings.

| v19 setting | Use in v20 | What happens if you keep the v19 name |
|---|---|---|
| `OCTOCODE_OUTPUT_FORMAT` (`yaml`, `json`), `.octocoderc` `output.format` | `OCTOCODE_MCP_RESULT` (`json`, `text`); `--json` on the CLI | MCP replies are JSON |
| `OCTOCODE_OUTPUT_DEFAULT_CHAR_LENGTH`, `.octocoderc` `output.pagination.defaultCharLength` | `responseChars` in each request | The default page size applies |
| `OCTOCODE_LSP_CONFIG`, `.octocoderc` `lsp.configPath` | `lsp-servers.json` in your Octocode home | Your custom servers are not loaded |
| `REQUEST_TIMEOUT`, `MAX_RETRIES`, `.octocoderc` `network.timeout` and `network.maxRetries`, `OCTOCODE_TOOL_TIMEOUT_MS`, `OCTOCODE_BULK_QUERY_TIMEOUT_MS` | none: v20 manages its own timeouts and retries | No effect |
| `OCTOCODE_CACHE_TTL_MS`, `OCTOCODE_MAX_CACHE_SIZE`, `OCTOCODE_MAX_CLONES`, `OCTOCODE_DISK_CACHE*`, `OCTOCODE_ENABLE_STATS` | `octocode cache clear` to empty caches; `OCTOCODE_STORAGE_MODE=memory` to write nothing to disk | No effect |

`TOOLS_TO_RUN`, `DISABLE_TOOLS`, `ALLOWED_PATHS`, `WORKSPACE_ROOT`, `GITHUB_API_URL`, `OCTOCODE_HOME` and
`OCTOCODE_STORAGE_MODE` keep their names.

### Where settings come from

| | v19 | v20 |
|---|---|---|
| Files the MCP server and CLI read | your environment and `~/.octocode/.octocoderc`; `.env` files were read by skills only | your environment, then `.env` and `.octocoderc` in the project's `.octocode/` folder and in `~/.octocode/` |
| Order, highest first | environment → user `.octocoderc` → default | environment → project `.env` → user `.env` → project `.octocoderc` → user `.octocoderc` → default |
| What a project can change | — | each setting states it; for example, a project can turn cloning off but not on |
| GitHub token order | `OCTOCODE_TOKEN` → `GH_TOKEN` → `GITHUB_TOKEN` → `GITHUB_PERSONAL_ACCESS_TOKEN` → saved login → GitHub CLI | environment → project `.env` → user `.env` → saved login → OS credential store → GitHub CLI → anonymous; within one place `GH_TOKEN` → `GITHUB_TOKEN` |
| Inspect and change settings | edit the files | `octocode config list`, `get`, `set`, `unset` and `check`; `octocode config` opens a settings page in a terminal |

Because v20 reads `~/.octocode/.env`, a value you saved there for a skill also applies to the MCP server and CLI.

## Safety

| | v19 | v20 |
|---|---|---|
| What local tools can read by default | **your whole home directory** | your workspace, your Octocode home, and paths you allow in `ALLOWED_PATHS` |
| Credential files (`.env`, `.env.*`, keys) | blocked locally; read on GitHub | blocked locally and on GitHub, including `.env.example`; `OCTOCODE_CREDENTIAL_FILES=allow` lifts both |
| A secret in an assignment (`key = "…"`) | the whole assignment, name and value, is replaced | only the secret value is hidden |
| Searching for a secret's text | finds it | does not; the result says how many secrets were masked |

## What is slower or different

- GitHub allows 10 code searches a minute per token. When several agents share one token and use them up, v20 waits
  for the quota to return instead of failing, so answers take longer; v19 spaced searches 2 s apart and waited only
  after GitHub refused one. Give each agent its own token, or expect the wait.
- An MCP call spends at most about 50 s waiting, since MCP clients give up on a call after 60 s. A GitHub limit
  that needs longer is waited until then: the reply says `rateLimited`, how many seconds are left
  (`retryAfterSeconds`) and the call to run next, which waits out the rest and runs.
- Repeating the same GitHub repository or pull-request search asks GitHub again, because GitHub marks those answers
  as not cacheable. Code search, file reads and PR reads still answer repeats from cache.
- A pull-request summary no longer lists follow-up calls. Ask for what you need with `sections`, such as
  `["files","patches"]` or `["body"]`.

- **Quality.** A gap under about 0.3 in a mean is a tie. v20 gained most where v19 misread structure: v19 scored 1
  on a `package.json`'s dependency sections, 7 on Axios's Node entry chain and 6 on Go callers, where v20 scored 10
  on all three. v20 lost a public-API question (7.5 against 10: it left out exports that arrive through `export *`),
  a Chromium IPC question (7.5 against 10: it left out how a message pipe is created and bound) and a Python module
  outline on disk (7 against 10: its first sentence miscounted the classes that the table below it lists). Against
  `gh`, v20 lost the same Chromium question and won a LangChain graph question (10 against 8), where `gh` got an edge
  wrong and cited the wrong file.
- **Time.** v20's GitHub median includes 103 s of waits, in 6 of its 30 runs, for a code-search quota that six
  parallel sessions shared ([why](#what-is-slower-or-different)); without them it is 19.0 s.
- **Cost.** New input is text the model had not cached, almost all of it written to the cache once; a cached re-read
  costs 1/40 of that. Against `gh`, most of v20's higher cost is new input ($1.03 against $0.61): it reads more tool
  output per question (11.5k characters against 8.5k) and writes each reply to the cache once. Output costs about the
  same ($0.60 against $0.54); cached re-reads add $0.31 against $0.08, mostly the fixed prompt v20 re-reads on every
  model call: about 25k tokens, against 5k for `gh`'s agent and 33k for v19's.

### Failed calls

A failed call is a reply marked as an error or holding an error row. v20's 11, by cause:

| Cause | Calls | What v20 does |
|---|---:|---|
| `operation` sent beside `queries` as well as in each row | 4 | Drops a field beside `queries` that every row already holds with the same value, and runs the rows |
| A `.git/` read | 2 | The refusal points to the `commitSha` that rows inside the checkout already state |
| A tool called by its short name (`structureSearch`, `localSearch`) | 2 | The MCP client refuses it before it reaches Octocode |
| A tree path that does not exist (`dist`) | 1 | `notFound`, naming the path |
| A misspelled field (`after:` in `contextLines`) | 1 | Refuses without running, naming the field to use |
| A regex that spans a line break without `multiline` | 1 | Refuses and says to set `multiline` to on |

Of `gh`'s 20: 11 were shell forms its sandbox refuses (variables, some chained commands, `sleep`), 4 were GitHub
refusing Chromium file reads with HTTP 429, 3 were files not found (HTTP 404), and 2 were other errors.

### How we measured

All 30 of the benchmark's [GitHub questions](../packages/octocode-benchmark/questions/github/README.md) and all 30 of
its [questions on code on disk](../packages/octocode-benchmark/questions/local-core/README.md), on pinned commits.
Each was answered by a fresh agent (Claude Sonnet 5.5) with only one version's tools, or only `gh`, the question and
one sentence asking it to cite its evidence; six sessions ran at a time on one GitHub token. A separate model (Claude
Opus 5.5) graded the answers blind against the source. Every gap of 2 or more points was graded again with the answers
in reverse order; the score is then the mean of both gradings, and only wins that held in both are counted. In a set
of 30, one answer 5 points lower moves the average by about 0.17. Per-question numbers are in the
[round results](../packages/octocode-benchmark/results/rounds/20.2.0-2026-11-24-v19-v20-gh/README.md).

Tokens come from the model provider's usage report for each run: new input (uncached plus cache writes), cached
re-reads and output, summed over every model call. Cost is the provider's reported cost; it implies $4 per million new
input tokens, $0.10 per million cached re-reads and about $10 per million output tokens.

The `gh` agent's shell allowed `gh` commands and text filters to pipe them through (`jq`, `base64`, `head`, `tail`,
`sed`, `grep`, `wc`, `sort`, `uniq`, `cut`, `tr`); none could read or write a file.

Skills were compared from the commit published as 19.1.0 (2026-09-06) against today's, using today's skill checker on
both; 5 errors for a v19 file generated at build time and never kept in git are not counted. Settings were compared
from each version's configuration reference, and the renamed v19 names were confirmed on v20 through MCP and the CLI.

2. Give each arm only its own tools ([tools per arm](../packages/octocode-benchmark/TESTING_ENV.md#tools-per-arm)):

   | Arm | MCP server or shell | Settings |
   |---|---|---|
   | v19 | `npx -y octocode-mcp@19.1.0` | `ENABLE_LOCAL=true`, `ENABLE_CLONE=true`, `DISABLE_TOOLS=localAnalyzeGraph`, `ALLOWED_PATHS=<clones>`, `GITHUB_TOKEN`, and a `HOME` that holds no answer key |
   | v20 | `npx -y octocode-mcp@20.2.0` | `OCTOCODE_ENABLE_LOCAL=true`, `OCTOCODE_ENABLE_CLONE=true`, `OCTOCODE_SECURITY_CHECKS=true`, `ALLOWED_PATHS=<clones>`, `WORKSPACE_ROOT=<clones>`, `GITHUB_TOKEN`; no `clasify` key |
   | `gh` | a shell that runs only read-only `gh` and the filters `jq`, `base64`, `head`, `tail`, `sed`, `grep`, `wc`, `sort`, `uniq`, `cut`, `tr`, reading from a pipe | `gh auth login` |

3. Start a fresh agent (Claude Sonnet 5.5) for each question and arm, with this prompt and nothing else:

   ```text
   <the text under "## Question" in the question file>

   Answer using only your Octocode tools. Cite the repository, file, line and commit SHA behind each claim.
   ```

   For `gh`, the second line reads: Answer using only read-only `gh` commands in Bash. Cite the repository, file,
   line and commit SHA behind each claim. You can pipe `gh` output into jq, base64, head, tail, sed, grep, wc, sort,
   uniq, cut or tr; shell variables, `$(…)`, `<(…)` and `cd` are refused.

   With Claude Code: `claude -p "<prompt>" --model claude-sonnet-5-5 --mcp-config <arm>.json --strict-mcp-config
   --tools "" --allowedTools mcp__octocode --setting-sources "" --no-session-persistence`; for `gh`, replace the MCP
   options with `--tools Bash --allowedTools "Bash(gh:*)" "Bash(jq:*)"` and one `"Bash(<filter>:*)"` per filter.
4. Grade each question with a fresh judge (Claude Opus 5.5) and the [judge brief](../packages/octocode-benchmark/briefs/judge.md): the answers
   as X, Y and Z in a random order, plus the answer key where the set has one. Grade every gap of 2 or more points
   again in reverse order and keep the mean ([method](../packages/octocode-benchmark/METHOD.md#judge)).
5. Count tokens from the provider's usage report: new input, cached re-reads and output, kept apart.
