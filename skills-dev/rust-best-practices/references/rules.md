# Rules: clean code, measured build changes, dependencies

Load when shaping code or architecture, changing build settings or crate layout, or adding a dependency. The always-on rules stay in [SKILL.md](../SKILL.md#rules).

- Keep code clean: small cohesive modules, typed errors at library boundaries, cleanup owned by `Drop` guards, no process-global mutable state, clocks and limits passed in, tests in their own files, and `#[expect(lint, reason)]` instead of `#[allow]`. Keep the architecture clean: crates split along enforced layers with a guarded crate graph, serialization and generated code at the edges, a dispatch-only top crate, a minimal public surface per crate, fixtures only in dev-only crates or `test-support` features, build-wide values passed as parameters, temporary bridges deleted, and no growth of the crate that holds the build's critical path. The [clean-code tools](testing-and-tooling.md#tools-that-keep-code-and-architecture-clean) enforce what they can.
- Change build settings, crate layout or test infrastructure only on measured evidence: CPU (user + sys) and recompiled units, A/B/A/B, never wall time under load. Do mechanical refactors with a replayable script. Do not reintroduce a setting [measured and rejected](build-profiles.md#measured-and-rejected-here) without new evidence.
- Reuse std and established dependencies. Evaluate a new dependency's API, features, MSRV, license, maintenance and build-time effects. Proceed within the user's authorized scope; ask only when an unresolved decision materially changes compatibility or scope. Do not require fresh permission for routine Cargo-managed lockfile updates already implied by the task.
