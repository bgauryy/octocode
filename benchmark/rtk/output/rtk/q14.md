## Answer

From the complete `SECURITY.md` visible through metered `rtk read`:

1. **Trusted vs untrusted inputs:** the document does not explicitly define a “trusted vs untrusted inputs” taxonomy. It does say RTK is a CLI tool that executes shell commands and handles user input, and it requires validating all user input before passing it to `Command`.

2. **Command injection threat model:** shell injection/command execution is treated as a primary risk. The security review process protects against “Shell injection (command execution vulnerabilities)”; critical files include shell execution/system interaction code and rewrite logic because of command injection risk.

3. **Explicit shell execution risk surfaces/patterns:**
   - `Command::new("sh")` — listed as shell injection risk.
   - `Command::new("sh").arg("-c").arg(format!("echo {}", user_input)).output()` — shown as a “DON'T” anti-pattern.
   - The recommended safe pattern is direct binary execution: `Command::new("echo").arg(user_input).output()`.
   - `src/discover/registry.rs` is high-risk because rewrite rules can create command-injection risk.
   - `hooks/rtk-rewrite.sh` / `.claude/hooks/rtk-rewrite.sh` are high-risk because they execute in Claude Code context and intercept all commands.
   - Input validation guidance: validate all user input before passing to `Command`, use allowlists for command flags, canonicalize file paths, and sanitize package names with strict regexes.
