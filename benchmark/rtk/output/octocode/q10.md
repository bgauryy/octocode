### 2. Why the Re-Implementation Was Necessary

PR #826 refactored the `format_pr_view` and `format_issue_view` functions to **return `String`** instead of printing directly via `print!()`. The original fix from #235 was written against the old API where these functions printed inline. After the refactor in #826, the original fix was no longer compatible with the new function signatures, so the fallback note behavior was lost.

PR #2129 re-implemented the same behavior in the new `String`-returning style.

Additionally, the PR notes that the second half of #235 (a `run_api` `.take(20)` single-pass refactor) was **no longer applicable**: `run_api` now does a full passthrough via `run_passthrough` (the behavior had been redesigned entirely).

### 3. The `(body contained only badges/images/comments)` Fallback Note

**What it is**: A user-facing message shown when a PR or issue body contains **only filterable noise** (badge images, HTML comments like `<!-- Auto-generated -->`, image-only lines, horizontal rules) that `filter_markdown_body()` strips entirely to an empty string.

**The problem it solves**: Without this note, when `filter_markdown_body()` returns an empty string from a non-empty raw body, `format_pr_view` and `format_issue_view` would silently skip the body section. Users (and AI agents) would see no body content with no indication that any content existed — they'd have to re-fetch the raw body separately.

**The fix** adds an `else` branch:
- In `format_pr_view`: appends `\n  (body contained only badges/images/comments)\n`
- In `format_issue_view`: appends `\n  Description: (body contained only badges/images/comments)\n`

This note signals explicitly that a body existed but was entirely noise — the agent can decide whether to fetch the raw body if needed.

4 tests were added to cover:
- Badges-only body → shows fallback note
- Real content body → no fallback note
- Empty body → no fallback note (nothing to signal)
- Issue body with badges only → shows fallback note
