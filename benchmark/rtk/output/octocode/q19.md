# Q19 — Safety annotation comments in `src/`

## Result

There are **zero `// SAFETY:` comments** in any `.rs` file under `src/` in `rtk-ai/rtk`.

## Verification

A ripgrep search for `// SAFETY:` across all files in `src/` returned **no matches**.

## Explanation

This is consistent with the `Cargo.toml` configuration:

```toml
unsafe_code = "deny"  # Line 71 in Cargo.toml
```

`unsafe_code = "deny"` is a Clippy lint denial that **prevents unsafe code from being merged into the codebase**. Since unsafe code is denied at the lint level, there are no `unsafe {}` blocks that would require `// SAFETY:` annotations — the project simply does not use unsafe code.

## Exception: `src/main.rs` has 2 `unsafe` blocks with `#[allow(unsafe_code)]`

Two exceptions exist with explicit `#[allow(unsafe_code)]` overrides:

**Line 1364–1366** (`#[cfg(unix)]`):
```rust
#[allow(unsafe_code)]
unsafe {
    libc::signal(libc::SIGPIPE, libc::SIG_DFL);
}
```
This is the standard Unix SIGPIPE signal restoration — a well-known safe pattern for CLI tools to prevent silent exit on broken pipes.

**Line 2315–2327**: Another `#[allow(unsafe_code)]` + `unsafe {}` block (likely another OS-level signal or FFI call).

Neither of these `unsafe` blocks has a `// SAFETY:` comment explaining the invariant. The `#[allow(unsafe_code)]` attribute suppresses the lint without requiring the SAFETY annotation convention.

## Summary

- `// SAFETY:` comments: **0** (none exist)
- `unsafe {}` blocks with `#[allow(unsafe_code)]`: **2** (both in `src/main.rs`)
- `unsafe_code = "deny"` in Cargo.toml: **yes** (project-wide default)
