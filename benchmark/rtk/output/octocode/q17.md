## PR That Introduced the Hooks System

### Hook System Evolution

The hooks system evolved through several stages:

**Pre-PR #1 (original codebase)**: A bash script `hooks/rtk-rewrite.sh` was the original hook. This 204-line script was present in the initial public release (v0.2.0/v0.2.1) before any PRs were merged. It served as a Claude Code `PreToolUse` hook that rewrote known commands to their `rtk` equivalents.

**PR #150** — "feat(hook): native cross-platform (Windows & more) hook-rewrite command"  
This is the PR that **introduced the native Rust hooks system**, replacing the bash hook:
- Author: anonymous contributor (🤖 Generated with Claude Code)
- State: closed (merged into master)
- Changed: Added `src/hook_cmd.rs` (1,126 lines of pure Rust)
- Updated `src/init.rs` to install the native hook command
- Added `build.rs` (8 MB stack size fix for Windows)
- 56 unit tests covering all rewrite patterns, edge cases, command chains

**PR #156** — "Hook Engine + Chained Command Rewriting (PR #131 Part 1)"  
By @ahundt — introduced the **hooks-v2 architecture**:
- New `src/cmd/` directory with `lexer.rs`, `analysis.rs`, `hook/mod.rs`, `exec.rs`
- Binary hook engine with `hook_lookup()` whitelist, Claude Code JSON protocol
- Streaming process execution (`stream.rs`) with bidirectional shim
- 541 tests: hook (22), claude_hook (18), lexer (28), analysis (10), builtins (8), exec (22)
- Replaced the 204-line bash `rtk-rewrite.sh` with a 4-line shim

**PR #536** — "feat: binary hook engine with lexer, streaming, and rewrite_compound integration"  
By @ahundt — merged PR #156's hooks-v2 engine into the `develop` branch.

### The Original Introduction: PR #150

**PR Number**: #150  
**Title**: "feat(hook): native cross-platform (Windows & more) hook-rewrite command"  
**URL**: https://github.com/rtk-ai/rtk/pull/150  

#### 1. Original Design Rationale

From the PR body:

| | Bash hook (`rtk-rewrite.sh`) | Native hook (`rtk hook-rewrite`) |
|---|---|---|
| **Dependencies** | bash + jq required | None (single binary) |
| **Windows** | Requires Git Bash/WSL | Works natively |
| **Performance** | Shell startup + jq parsing | Direct Rust execution |
| **Security** | Shell script attack surface | Pure string manipulation, no shell spawning |
| **Maintenance** | Separate script file to distribute | Built into rtk binary |

The design rationale was to eliminate bash/jq dependencies, enable Windows support without Git Bash/WSL, and improve security by avoiding shell spawning entirely (pure Rust string manipulation).

#### 2. Architecture

The hook reads Claude Code `PreToolUse` JSON from stdin, rewrites known commands to their `rtk` equivalents, and outputs updated JSON to stdout:

```
stdin:  {"tool_input":{"command":"git status"}}
stdout: {"hookSpecificOutput":{"permissionDecision":"allow","updatedInput":{"command":"rtk git status"}}}
```

Fail-open: any parse error → `exit(0)` (original command passes through unchanged).

#### 3. Design Alternatives Discussed

From PR #156 (which reviewed PR #150's approach and proposed hooks-v2):
- PR #150 used a monolithic `hook_cmd.rs` with inline byte scanning
- PR #156 proposed splitting into a proper **lexer + analysis + exec** architecture to support chained commands (`cd /tmp && git status`), which PR #150 could not handle
- The PR #156 body notes that PR #150's approach failed for compound commands: "Before: `cd /tmp && git status` — hook only saw `cd`, missed `git status`"
- PR #156 also addressed the inability to handle shellisms (globs, pipes, subshells) safely

No explicit review comments are available (commentsCount: 0 for both PRs), but the evolution from PR #150 → PR #156 → PR #536 shows the design debate played out through successive PRs rather than inline review discussion.
