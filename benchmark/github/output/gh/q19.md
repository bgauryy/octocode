## Answer

- Astro SSR entry: `withastro/astro` `packages/astro/src/runtime/server/render/page.ts` exports `renderPage(...)`. It calls Astro's renderer helpers from `./astro/render.js`.
- Astro streaming: `renderPage` returns a body as a Node async iterable (`renderToAsyncIterable`) or Web `ReadableStream` (`renderToReadableStream`) depending on environment/route settings, falling back to `renderToString` when streaming is disabled; `packages/astro/src/runtime/server/render/astro/render.ts` defines `renderToReadableStream(...)`.
- Next.js SSR entry: `vercel/next.js` App Router SSR is centered in `packages/next/src/server/app-render/app-render.tsx`; Pages Router has `packages/next/src/server/render.tsx` with `renderToString(element)` calling `ReactDOMServerPages.renderToReadableStream(element)`.
- Next.js streaming: App Router streams React Server Components/Flight with React's `renderToReadableStream`/React DOM Fizz streams and composes HTML/RSC payloads; Pages Router uses React DOM Web Streams then converts to string for non-streaming pages paths.
- Architectural difference: Astro's islands model renders mostly static/server HTML and hydrates only explicitly marked client islands (`client:*`) using per-framework integrations. Next.js App Router is React-centric: the route tree is React Server Components plus Client Components, with Flight data and Suspense streaming coordinating server/client component boundaries across the whole app.
