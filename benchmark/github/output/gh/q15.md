### Q15 — Svelte 5 vs Vue 3: compile-time vs runtime reactivity

Using `sveltejs/svelte` and `vuejs/core`:
1. Where does reactivity live: compiler, runtime, or both?
2. Find the Svelte compiler's output for a `$state` variable vs Vue's `ref()` runtime call.
3. How does each framework know which part of the DOM to update when state changes?
4. What is the fundamental tradeoff between compile-time and runtime reactivity?

## Answer

- Svelte 5 reactivity lives in both compiler and runtime: the compiler rewrites `$state` runes into runtime signal calls, and the runtime implements signals/proxies in `packages/svelte/src/internal/client/reactivity/sources.js` and `proxy.js`.
- Example Svelte output: `packages/svelte/tests/snapshot/samples/state-proxy-literal/_expected/client/index.svelte.js` turns `$state` variables into `let str = $.state('')`, reads into `$.get(str)`, and writes/bindings into `$.set(str, value)`.
- Vue 3 reactivity is primarily runtime API based: user code calls `ref()`/`reactive()` from `packages/reactivity/src/ref.ts` and related files; `ref(value)` returns `createRef(value, false)`, whose `.value` getter/setter track and trigger dependencies.
- Svelte knows DOM updates because the compiler sees which template expressions depend on which state and emits targeted effects/bindings around `$.get`/`$.set`; runtime signals invalidate those emitted effects.
- Vue knows DOM updates because runtime render effects read refs/reactive proxies; `Dep.track` records the active component/effect and `Dep.trigger` re-runs it, causing Vue's VNode patcher to update the DOM.
- Tradeoff: Svelte's compile-time approach can emit smaller, direct DOM update code and needs less runtime bookkeeping, but requires compiler analysis/rune restrictions. Vue's runtime approach is more dynamic and works through normal JS APIs like `ref()`/`reactive()`, but pays runtime dependency tracking and VNode patching overhead.
