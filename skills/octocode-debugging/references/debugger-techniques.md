# Debugger techniques

A failure often becomes visible several calls after the decision that caused it. If a receipt already has the wrong total at serialization, the serializer’s stack tells you who observed it. The next useful observation might be the earlier write, the input to the calculation, or a traceback you already have.

| What would you like to learn? | Debugger feature and how to read it |
|---|---|
| Which invocation takes the wrong branch? | Put a conditional breakpoint at the decision, keyed to the failing item or request. Inspect the operands and caller before the line executes. Step over to see the result, into a call whose behavior is in question, or out to see what the caller receives. A breakpoint with zero resolved locations gives no evidence about whether the branch ran. [LLDB breakpoint locations](https://lldb.llvm.org/use/tutorial.html) |
| Who changed this value? | A watch expression displays the value at stops. A **data watchpoint** can stop on the write itself. Set it while the object is in scope, continue, and inspect the old/new values and writer’s stack. A native stop may display the next source line after the write. Check the old/new values and nearby statement before citing the writer. Watch the pointee when its contents change. In Visual Studio, a managed data breakpoint can follow a supported object property. [Visual Studio data breakpoints](https://learn.microsoft.com/en-us/visualstudio/debugger/using-breakpoints?view=vs-2022) · [GDB watchpoints](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Watchpoints.html) · [LLDB commands](https://lldb.llvm.org/use/map.html) |
| Which callback changed the page or started a request? | In Chrome DevTools, a DOM breakpoint on a node can catch the code that modifies it. An event-listener breakpoint stops in a handler. An XHR/fetch breakpoint matches part of the request URL and stops on the initiating side. Select the application frame and inspect its arguments. [DevTools breakpoint types](https://developer.chrome.com/docs/devtools/javascript/breakpoints) |
| The error is caught and replaced. Where was it raised? | An exception breakpoint can stop before unwinding, while the thrower’s locals are available. Use the exception type or caught/uncaught setting to control noise. For example, JDB supports `catch java.io.FileNotFoundException`. A caught throw can also be expected control flow. [JDB exception stops](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jdb.html) · [Node inspector](node.md#attach-with-chrome-devtools) |
| Which thread or task could unblock this one? | Inspect the waiting stack and the worker expected to release the lock, send the message or finish the job. GDB has `thread apply all bt`. Delve has `goroutines` and `goroutine <id> stack`. An idle worker or a single blocked stack does not establish a deadlock. [GDB threads](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Threads.html) · [Delve CLI](https://github.com/go-delve/delve/blob/master/Documentation/cli/README.md) |
| Does the symptom disappear when execution pauses? | A conditional logpoint can emit an operation ID and scalar value while execution continues. Keep expressions cheap and free of side effects. Getters, method calls and formatting can execute application code, and frequent logging can change timing. [VS Code logpoints](https://code.visualstudio.com/docs/debugtest/debugging) · [GDB expression evaluation](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Calling.html) |

## What survived the failure?

- **Traceback or dump.** Inspect the captured failure before trying to recreate it. Python pdb can enter post-mortem at the exception. For a native core, use the matching executable and symbols. For a .NET dump, `dotnet-dump analyze <dump>` followed by `clrstack` gives managed frames for the selected thread. Identify the first relevant frame and the state the artifact actually contains. Omitted locals or memory remain unknown. [Python pdb](https://docs.python.org/3/library/pdb.html) · [Native cores](native.md#crash) · [.NET dump analysis](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-dump)
- **Recorded execution.** On a supported Linux target, `rr record ./app` captures a run and `rr replay` opens it in GDB. From the bad state, a watchpoint and `reverse-continue` can find the preceding change. WinDbg Time Travel Debugging provides backward navigation for a Windows recording. Both need a recording covering the event. rr serializes threads, which can affect race reproduction. Recordings can retain sensitive process data. [rr record and replay](https://rr-project.org/) · [WinDbg TTD](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/time-travel-debugging-overview)
